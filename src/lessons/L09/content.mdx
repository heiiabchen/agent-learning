L08 解决的是「agent 自己记下来的东西」。这一节解决另一半：**它没记、也记不完的那些。**

一个代码库有几十万行，一套文档有几千页，公司的工单历史有几百万条。这些东西塞不进上下文，也不该抽成事实存起来。要用的时候得**去找**。

这就是检索。而围绕检索的那一坨东西——分块、embedding、向量库、rerank——统称 RAG。

<Key>
**RAG 里最重要的判断不是「怎么检索」，是「该不该检索」。**

这一节会讲全套技术细节，但先把结论放在这里：**大多数 RAG 系统的问题不是检索质量差，是压根不该上 RAG。**

- 语料塞得下上下文 → 全塞进去。检索的收益是省钱，代价是**可能漏内容，而漏了的那部分你不会知道**
- 查询里有精确标识符（错误码、函数名） → `grep`。它精确、免费，而且**失败是响亮的**
- 要找什么本身不确定 → agentic search，多轮
- 剩下的才是经典 RAG

上 RAG 是有代价的：多一套基础设施、多一层可能出错的地方、多一个「答案不对但看不出为什么」的黑箱。这些代价只在第四种情况下值得付。
</Key>

## 一、先算一笔账：你的语料真的塞不下吗

2026 年的上下文窗口普遍在 20 万 token 以上。20 万 token 大约是 **80 万个英文字符，或者 20 万个汉字**。

一个中等规模的 TypeScript 项目，去掉 `node_modules` 和测试，源码通常在 3 到 10 万 token 之间。**它塞得下。**

<Pitfall title="为了「架构正确」上 RAG，然后自己制造了一类新 bug">

全塞和检索的区别不是「贵一点 vs 便宜一点」，是**两种不同的失败模式**：

| | 全塞 | 检索 |
|---|---|---|
| 成本 | 高，但可预测 | 低 |
| 延迟 | 高（首 token 慢） | 低 |
| 漏内容 | 不会 | **会，而且你不知道漏了什么** |
| 调试 | 看输入就行 | 要先复现检索结果 |

最后两行是关键。检索漏掉一个片段的时候，模型不会说「我没看到相关代码」——**它会基于剩下的那些给你一个自信的答案**。

而排查这类问题要先把检索结果 dump 出来，人工判断「本该召回什么」。这一步在生产环境往往做不了，因为你没存当时的检索结果。

所以判断顺序是：**先算语料 token 数，超过预算一半再考虑检索。**

</Pitfall>

`chooseRetrieval` 把这套判据写成了代码，而且**每个分支都要返回 `why`**：

```ts
if (corpusTokens <= budgetTokens * 0.5) return { mode: 'none', why: '...' }
if (hasExactTerms && !needsExploration) return { mode: 'lookup', why: '...' }
if (needsExploration) return { mode: 'agentic', why: '...' }
return { mode: 'search', why: '...' }
```

理由和 L07 的 `choosePattern` 一样：**判据要能被 review，而不能只被执行。** 半年后有人问「为什么这个场景走了全塞」，`why` 是唯一能回答的东西。

## 二、分块：检索质量的第一个瓶颈

假设你确定要检索了。第一步是把语料切成片段。

大多数人在这一步用固定窗口——按字符数切，加一点重叠。这能跑，但对代码来说它是**性价比最低的选择**。

<Key>
**对代码，结构分块的检索质量提升比调任何 embedding 参数的收益都大。**

因为代码的语义单元是**显式的**（函数、类、方法），而固定窗口对它们一无所知。

一个被切成两半的函数，在向量空间里既不像原函数、也不像任何别的东西——**它是一个语义上的噪声**。而且两半都召不回来。
</Key>

对比一下同一个文件的两种切法：

```text
固定窗口（400 字符）              结构感知
──────────────────────           ─────────────────────────
行  1-12  import ... 到函数中间    行  1- 6  path=(文件头)
行 12-24  函数下半 + 下一个签名    行  7-10  path=TokenPayload
行 24-33  函数体 + 下一个签名      行 11-16  path=signToken
                                 行 17-26  path=verifyToken
                                 行 27-33  path=loadSecret
```

块数差不多。差别在**每一块是不是一个完整的语义单元**。

<Note title="重叠不是调参，是补丁">

固定窗口的 `overlap` 参数经常被当成一个「调一调看效果」的超参。它不是。

它存在的唯一理由是：**固定窗口一定会在某个地方把一个完整的语义单元切成两半。** 重叠让被切断的那部分在两个块里都出现一次，于是至少有一个块是完整的。

代价有两个，都实在：

- **存储和检索成本按重叠比例上涨。** 15% 的重叠就是 15% 的额外成本
- **同一段内容会以两个不同的块被召回**，占掉两个名额。所以后面必须去重

结构分块不需要重叠，因为它切在本来就该切的地方。这是它更省钱的一个副作用。

顺带一个实现细节：`overlap >= size` 要**抛错**。不然循环永远推进不了，表现为进程卡死——而卡死比报错难查得多。

</Note>

<Pitfall title="降级必须可见">

结构分块识别不出结构的时候（纯散文、配置文件、你没适配的语言），要退回固定窗口。这没问题。

有问题的是**静默地退回**。

后果是你以为整个语料都在用结构分块，实际上一半文件走了固定窗口。而这一半的检索质量明显更差——于是你去调 embedding、调 `k`、换向量库，全都不对症。

做法很简单：降级的片段在 `path` 里标出来。

```ts
return chunkFixed(text, source, { size: maxSize }).map((c) => ({
  ...c,
  path: '(未识别结构，固定窗口降级)',
}))
```

这样 dump 一遍分块结果就能看出来。**一行代码换一个能被发现的失败。**

</Pitfall>

## 三、两路检索：向量并不总是赢

向量检索的宣传语是「理解语义」。它确实理解一部分，但**远没有大多数人以为的那么多**。

<Key>
**BM25 在代码检索上常常打败向量检索。**

理由是代码里最关键的词是**专有名词**：函数名、变量名、错误码、配置项。它们的语义完全来自约定而不是语言。

`useCallback` 和 `useMemo` 在向量空间里非常近——它们长得像、用法像、出现的上下文像。而它们是两个不同的东西，混淆的后果是答案完全错。

`SECRET_TOO_SHORT` 这种错误码更极端：它在向量空间里和任何一个包含 `SECRET`、`SHORT` 的片段都差不多近，而你要的是**那一个精确匹配**。
</Key>

BM25 是精确的字面匹配加两个统计修正：

- **IDF**——罕见词权重高。`ENOENT` 比 `error` 有信息量
- **长度归一**——长文档不因为词多而占便宜

所以正确的问题从来不是「用向量还是用关键词」，是**怎么把两路合起来**。

<Pitfall title="中文分词：最经典的一种静默失效">

BM25 要先分词。而中文没有空白。

按空白分词的话，「登录偶尔失败用户说点了没反应」会变成**一个 token**。这个 token 匹配不到任何东西，于是 BM25 **安静地返回空列表**。

代码不报错，索引也建起来了，`size` 也对——只是搜什么都搜不到。而你的混合检索退化成了纯向量检索，**而你不知道**。

处理办法是切成单字加二元组：

```text
"登录失败" → 登、登录、录、录失、失、失败、败
```

单字的区分度太低（「的」「是」到处都有，IDF 把它们压到接近 0），所以二元组是必需的——「登录」比「登」加「录」有信息量得多。

英文那边有个对应的坑：**驼峰要切开**。`getUserById` 不切的话，搜 "user id" 匹配不到它，而这是代码检索里最常见的一类查询。

</Pitfall>

<Note title="别只索引正文">

索引的时候把 `source` 和 `path` 拼在正文前面：

```ts
export function indexText(c: Chunk): string {
  return `${c.source} ${c.path ?? ''}\n${c.text}`
}
```

**文件路径本身是最强的检索信号之一。**「登录相关的代码在哪」这个问题，`src/login.ts` 这个路径比文件内容更有指示性——而如果只索引正文，你压根搜不到它。

这一行经常被漏掉，而它的影响比换一个 embedding 模型大。

</Note>

## 四、融合：为什么不能把分数加起来

两路各返回一个带分数的列表。最直觉的合并方式是加权求和：

```ts
score = 0.7 * vectorScore + 0.3 * bm25Score   // 不要这么做
```

<Pitfall title="两路的分数不在同一个量纲上，而且分布形状完全不同">

- **余弦相似度**挤在 0.7 到 0.95 之间。三百个候选的分差可能只有 0.2
- **BM25** 是 0 到几十的长尾。一次精确命中能拿到 15 分，其余的都在 1 以下

相加的结果是 **BM25 完全支配，向量那一路等于没有**。而且这个失效是无声的——你的系统"在做混合检索"，指标也在跑，只是那个权重从来没起过作用。

「那就先归一化」——min-max 归一化对**离群值极其敏感**，而 BM25 的最高分**天生就是离群值**（那正是精确命中）。一次精确命中会把其余所有候选压到接近 0。

</Pitfall>

RRF（倒数排名融合）绕开了这整个问题：**它只用排名，不用分数。**

```text
score(d) = Σ  1 / (k + rank_i(d))         k 惯例取 60
```

量纲问题从根上消失了。而那个 `k` 不是随便取的：

<Note title="k=60 在做什么">

它**压低头部的权重差**。

没有 `k` 的话，第 1 名得 1/1 = 1.0，第 2 名得 1/2 = 0.5——差 0.5。有 `k=60` 的话，第 1 名得 1/61 = 0.0164，第 2 名得 1/62 = 0.0161——差 0.0003。

后果是：**「两路都排进前十」会胜过「一路排第一，另一路没召回」。**

而这正是混合检索想要的行为——两路的共识比任何单路的自信更可靠。

顺带：融合之后同一个 chunk 要标 `via: 'both'`。这个字段是后面重排的一个信号，也是你调权重时唯一能看的东西。

</Note>

## 五、重排：性价比最高的那一步

融合完你有十几个候选。直接全塞给模型是错的，理由在第七节。

<Key>
**检索和重排在做两件不同的事，所以不能用同一个模型。**

- **检索**——从一万个里捞出五十个。要快，所以只能看粗特征（一个向量、一个词频表）
- **重排**——从五十个里挑出五个。可以慢，所以能看细特征（query 和文档拼一起过一遍模型）

真实的重排器是 cross-encoder，或者直接让 LLM 打分。两者都比检索贵一到两个数量级——而因为只跑五十个，总成本反而很低。
</Key>

重排必须做对两件事，都不在算法里：

<Pitfall title="没有 minScore 的「重排」只是重新排序">

排序不解决「召回的全是噪声」这个问题。十个都不相关的片段排完序，还是十个不相关的片段。

必须有一个分数下限，低于它就丢掉——哪怕最后一个都不剩。**「检索不到相关内容」是一个合法的、而且经常正确的结论。**

而 `dropped` 必须带理由：

```text
✓ loadSecret (0.667)
✕ signToken —— 排在第 2 名之后
✕ calcTax   —— 分数 0.031 低于阈值 0.05
```

排查「为什么这段代码没被用上」的时候，这是**唯一有用的东西**。没有它你只能瞎调参数。

</Pitfall>

<Note title="一个具体的实现坑：分数不能为负">

重排的启发式打分里通常有个长度惩罚（片段越长扣得越多）。如果不夹下限，一个完全不相关的长片段会得到负分。

而负分会让 `minScore: 0`（意思是「什么都不过滤」）这个配置**意外地过滤掉东西**。

这种 bug 表现为「检索突然一片都不返回」，而且只在特定输入下出现。`Math.max(0, ...)` 一行解决。

</Note>

## 六、装配：三条硬规则

选出五个片段，拼成给模型看的文本。这一步看起来是字符串拼接，实际上每条规则都对应一类真实故障。

<Key>
一 · **每个片段必须带出处和行号。** 否则模型没法给出可点击的引用，而**不可验证的引用等于没有引用**——用户没法确认，于是只能信。

二 · **被预算砍掉的片段必须报出来。** 静默截断的后果是模型基于不完整的证据回答，而它不知道自己看的不完整，**于是语气一样自信**。

三 · **必须显式写上「没有依据就说不知道」。** 光给材料不给这句话，模型会在材料不够时用它的先验知识补——**而那正是 RAG 想避免的事**。
</Key>

第三条那句话长这样：

```text
<retrieved_context>
  <!-- 以下是检索到的片段。回答只能基于它们。
       ★ 如果这些片段不足以回答问题，直接说"检索到的内容里没有相关信息"，
       不要用你的先验知识补。宁可说不知道，不要编。 -->
  <chunk src="auth.ts:17-26" path="verifyToken">
    ...
  </chunk>
</retrieved_context>
```

它不是客套。**没有这句话的 RAG 系统，在材料不足时的行为和没有 RAG 时一模一样**——只是多了一层「看起来有依据」的包装，而这层包装让错误更难被发现。

<Note title="预算是硬上限，header 和 query 也要扣">

`budget - estimate(header + footer) - estimate(query)`，然后才开始装片段。

不扣的话每次都超一点。而超出的表现是**最后一片被 API 截断**——你看不到那件事发生，只看到模型偶尔答得不对。

还有一个更隐蔽的：`text` 和 `tokens` 要从**同一个字符串**算出来。分两次拼（一次给模型、一次给计数）是个很容易写出来的 bug，两边差一个换行你看不出来，而「预算是硬上限」这个保证就悄悄地不成立了。

</Note>

## 七、引用校验：RAG 里唯一能自动判定的质量信号

模型会编造引用。它会写 `src/auth.ts:120-140`，而那个文件根本不在检索结果里，或者行号是它凑的。

<Key>
**编出来的引用比编出来的内容更有害。**

因为它让答案**看起来可验证**，于是没人去验证。一个没有引用的可疑答案会被人核对；一个带着精确行号的错答案会被直接采信。
</Key>

而这件事**可以自动检查**——把答案里的引用抠出来，和你实际提供的片段对照。这是 RAG 里唯一不需要人工标注、不需要 LLM 打分就能得到的质量信号，所以它的价值远超它的代码量。

两类要分开报，因为处置方式完全不同：

| 类型 | 含义 | 说明什么 | 怎么处置 |
|---|---|---|---|
| `unknownSource` | 文件压根不在检索结果里 | 模型在用先验知识 | prompt 里那句「不许编」没生效 |
| `wrongRange` | 文件对，行号对不上 | 看的是对的材料，引用没抄准 | 可以自动修 |
| `unused` | 召回了但一次都没引用 | 检索召回了噪声 | 调小 `keep` |

<Pitfall title="wrongRange 比 unknownSource 更隐蔽，也更常见">

`unknownSource` 一眼能看出来——那个文件名你没见过。

`wrongRange` 不会：**文件名看着眼熟，于是 review 的人扫一眼就过了。** 而行号是模型凑的，点过去是另一段代码。

把两类混成一个 `fabricated` 字段，等于放弃了这个区分。而这个区分是有行动含义的：前者要改 prompt，后者写个脚本就能修。

</Pitfall>

## 八、agentic search：什么时候真的值得

「让 agent 自己搜」是 2025 年之后的主流叙事，而且它确实更强。但那句话不完整——**它更强，而且更贵，而且在一半的场景里那个「更强」是零。**

`pnpm agentic` 跑的是一个 40 文件、约 100 片段的假仓库上的对照实验。结果：

```text
                    keep=3    keep=8    agentic
定点问题（3 个）      3/3       3/3       3/3
探索问题（2 个）      0/2       1/2       2/2
总成本               ¥0.0035   ¥0.0050   ¥0.0072
```

（Python 版的语料是同一批文件的 Python 写法，排名会略有不同——那边 `keep=8` 一个探索问题都没解决。**这个差异本身就是第三条结论的证据。**）

三条结论：

<Key>
**一 · 定点问题上，多轮检索的收益是零。**

「`fmtBytes` 在哪」第一轮就命中了。agentic 那一行的数字和 `keep=3` **完全一样**——没有第二轮。

这是 L07 那条判据的检索版：**知道要找什么，就别让模型自己探索。**

**二 · 探索问题上，keep 开大解决不了问题。**

「登录偶尔失败」的根因在 `redis.ts` 的连接池上限，而**问题里没有任何词指向它**。`keep=8` 召回的八片全是噪声——它不是排名靠后，是**语义上和问题不相关**。

只有「先看 `login.ts`，发现它调 `getSession`，于是去看 `store.ts`，发现它调 `redis`」这条链能到达。而这条链只能一轮一轮走。

★ **一次性检索的上限不是 keep，是 query。** query 是用户写的，而用户不知道答案在哪——**这才是 agentic search 真正的立足点。**

**三 · 调 keep 是在赌答案的排名。**

`keep` 从 3 开到 8，成本涨 43%，噪声比例从 67% 涨到 83%，换来一个探索问题。它**只能救「答案恰好排在第 4 到第 8 名」的那些问题**——排在第 20 名的照样漏，语义上不相关的开到 100 也漏。

这不是一个可以调优的参数，是一个**赌注**，而赔率取决于你事先不知道的东西。
</Key>

<Pitfall title="噪声的危害不只是浪费 token">

看那个实验里的「噪声」列——`keep=8` 的时候八片里通常有六到八片和问题无关。

那些片段会**稀释注意力**（L05x），并且提高幻觉概率。具体到那个例子：模型看到 `src/auth/password.ts` 里的「登录失败超过 5 次锁定账号」，就可能编出

> 登录偶尔失败是因为触发了防爆破锁定。

**一个完全讲得通、有材料支撑、而且错的答案。**

这是 RAG 最常见的一种自伤：**为了提高召回率而降低了答案质量。** 而召回率涨了这件事在指标上看得见，答案变差看不见。

</Pitfall>

<Drill title="你的 agentic search 是真的多轮吗">

大多数人实现出来的 agentic search 长这样：给模型一个 `search` 工具，让它自己调，最多五次。

跑起来它确实调了五次。但**每次的 query 都差不多**——都是用户原问题的换词版本。

问自己三个问题：

1. 第二轮的 query 里，有没有**第一轮之前不可能知道的词**？（比如第一轮召回的文件里出现的函数名）
2. 如果没有，这五次调用和一次 `keep=15` 的区别是什么？成本差多少？
3. 你的 prompt 里有没有告诉模型「看到什么之后该追问什么」？

★ **判据是这个：agentic search 的价值全部来自「第二轮的 query 依赖第一轮的结果」。** 如果不依赖，你花了 N 倍的钱买了一个更差的 `keep=N×3`。

lab 里的 TODO 2 就是这个实验——把 `followUp` 和 `probes` 清空再跑，看它退化成什么。

</Drill>

## 九、记忆和检索的边界在哪

L08 讲长期记忆，这一节讲检索。它们的边界经常被搞混，而搞混的代价是**同一个事实存了两份，然后不一致**。

<Key>
**判据只有一条：这个事实会不会变，以及变了之后你能不能知道。**

- **抽成记忆**——用户偏好、项目约定这类**不在任何文件里**的东西。它们只存在于对话中，不抽就没了
- **留在原地检索**——文件里写着的东西。`tsconfig.json` 的配置、函数的实现、文档的内容

第二类**永远不要抽成事实存起来**。理由在 L08 说过一次，这里再说一遍，因为它是这两节的共同结论：

**能从文件读到的，读；不能读到的，才抽。** 前者是确定的、可重读的、会随项目更新；后者是概率的、会过期的、而且抽错了没人知道。
</Key>

一个具体的反例：把「这个项目用 4 空格缩进」抽成长期记忆。

三个月后项目改成了 2 空格（`.editorconfig` 里改的）。你的记忆还是 4 空格，而且它的 `confidence` 是 0.9，`hits` 是 47——按 L08 那套淘汰策略，**它是最不可能被淘汰的那一条**。

正确做法是读 `.editorconfig`。每次都读，读不到就说读不到。

## 十条要点

1. **先问该不该检索。** 语料塞得下就全塞；有精确标识符就 `grep`；要探索才 agentic；剩下的才是 RAG。
2. **每个判据都要有 `why`。** 判据要能被 review，而不能只被执行。
3. **对代码，结构分块的收益大于任何 embedding 调参。** 被切成两半的函数是语义噪声。
4. **降级要可见。** 认不出结构就退回固定窗口，但要在 `path` 里标出来。
5. **BM25 在专有名词上打败向量。** 中文要切单字加二元组，英文要切驼峰——这两个漏了都是**静默失效**。
6. **索引要包含文件路径。** 路径是最强的检索信号之一。
7. **融合用 RRF，不要加权求和。** 两路的分数不在一个量纲上，归一化也不解决。
8. **重排必须有 `minScore` 闸，`dropped` 必须带理由。** 没有阈值的重排只是重新排序。
9. **装配三条：带出处、报截断、写「不知道就说不知道」。**
10. **校验引用，而且分两类。** `wrongRange` 比 `unknownSource` 更隐蔽也更常见。
11. **agentic search 的价值全部来自「下一轮的 query 依赖上一轮的结果」。** 不依赖的话，它只是一个更贵的 `keep=N`。

<PyMirror>

Python 版有四处真实差异，每一处都对应一个会静默出错的场景。

**一 · `\w` 在 Python 里默认是 Unicode 语义。**

TS 那边可以写 `s.split(/[^a-z0-9]+/)`——取反字符类，把不要的切掉。搬到 Python，`\W+` 会把中文当成 `\w`，行为完全不同。

解法是统一用**正向匹配**（`finditer` 你想要的字符类），而不是 split 掉你不想要的：

```python
_TOKEN = re.compile(r"[a-z0-9]+|[\u4e00-\u9fa5\u3040-\u30ff]+")
```

正向匹配的行为在两种语言里一致。这是那种「两边代码看起来一样、结果不一样」的差异里最难查的一类。

**二 · 别用内置的 `hash()`。**

Python 对 `str` 的 `hash()` 加了随机盐（`PYTHONHASHSEED`）。同一段文本在两次进程里的哈希值**不一样**。

用它做 embedding 的后果是：**索引一重启就失效。** 而失效的方式不是报错，是「检索结果变差了一点」——没有告警，没有异常，只是慢慢地不对了。

自己写个 31 进制的滚动哈希，六行。`verify.py` 里有一条专门用两个不同的 `PYTHONHASHSEED` 起子进程来测这个。

**三 · `math.hypot()` 对空序列返回 `0.0`。**

归一化的时候除零保护不能省。空文本、极短文本都会走到这条路径，而 `nan` 一旦产生就会顺着余弦传到排序里——**而 `nan` 的任何比较都是 `False`**，表现为「排序结果随机」。

**四 · `Chunk` 和 `Scored` 是 frozen dataclass，改字段要用 `dataclasses.replace`。**

两个地方会踩：结构分块的降级标记、重排产出新分数。原地改在 frozen 上会抛（好事），不 frozen 的话会静默共享——同一批候选跑两次重排结果不一样，而这种 bug 只在「重试」的路径上出现，平时测不出来。

TS 那边因为用了对象展开（`{...c}`）天然没这个问题。

</PyMirror>
