上节课你让一个东西说话了。这节课我们把它拆开。

先看你自己终端里的三行数字——这是你跑 `pnpm stream` 时真实打出来的：

```text
Input tokens:  19
TTFT: 1.056s
Output tokens:  1000
Total time:  28.722 s
```

这四个数字里藏着这节课的全部内容。为什么「详细解释 HTTP/2 相比 HTTP/1.1 的改进」这句话是 **19** 个 token 而不是 17 个字？为什么输出**恰好**停在 1000，而且最后一句话断在「服务器可预测」这个半截词上？为什么首字只要 1 秒，全文却要 28 秒？

<Key>
这节课的目标只有一个：让你看着任何一次模型行为，都能说出「它为什么会这样」。这是初级和高级 agent 工程师之间最硬的那道分界线。
</Key>

## 一、你的输出为什么正好停在 1000

先解决那个最扎眼的。你的代码里写了 `max_tokens: 1000`，模型输出了 1000 个 token,然后被**切断**了——不是说完了，是被踢下台的。

这两种结束方式在协议里有明确区分，就在 `stop_reason` 字段里：

| stop_reason | 含义 | 你该做什么 |
|---|---|---|
| `end_turn` | 模型自己说完了 | 正常处理 |
| `max_tokens` | 撞上你设的输出上限，被截断 | **答案不完整，必须处理** |
| `stop_sequence` | 撞上你指定的停止串 | 按你的约定处理 |
| `tool_use` | 模型要调工具（L04 的主题） | 执行工具，把结果回填 |

你那次跑的是 `max_tokens`。而你的代码——和绝大多数人的第一版代码一样——**根本没看这个字段**。它把一段被腰斩的文本当成完整答案打印了出来。

这在演示脚本里无伤大雅。放进 agent 里就是另一回事了：模型正准备输出一段 JSON，写到一半被截断，你的 `JSON.parse` 抛错；或者它写到一半的代码被你原样写进了文件。

<Pitfall title="max_tokens 不是上下文上限">

这是这门课我见过的最高频的一对混淆，而你已经用真金白银撞过一次了，所以你现在记得会比别人牢。

- **max_tokens** = 这一次**最多生成**多少 token。你设的，是个闸门。
- **context window** = 输入 + 输出**加起来**能有多长。模型定的，是个容器。

两者的关系是：`max_tokens` 必须留在 context window 减去输入之后的空间里。DeepSeek V4 的 context 是 100 万 token、单次最大输出 38.4 万，所以你在这门课里基本撞不到容器的墙，但闸门是你自己天天在设的。

设小了截断，设大了……**其实不花钱**。这一点值得单独说清楚，因为很多人在这里有个错误直觉：`max_tokens` 是上限不是预约，模型只生成它想生成的量，你按**实际生成量**付费。所以在不确定的时候，把它设宽松一点，然后**老老实实检查 `stop_reason`**，比精打细算地设一个小值安全得多。

</Pitfall>

## 二、Token：模型眼里的世界

现在回答第一个问题：为什么「详细解释 HTTP/2 相比 HTTP/1.1 的改进」是 19 个 token？

因为模型看不见字符，也看不见单词。它看见的是**词表里的编号**。分词器（tokenizer）负责把你的字符串切成一串编号，模型自始至终只在跟这串整数打交道。

大致切法是这样的：

```text
"详细"  "解释"  " HTTP"  "/"  "2"  " 相比"  " HTTP"  "/"  "1"  "."  "1"  " 的"  "改进"
```

注意 `HTTP/1.1` 这一小段：它自己就吃掉了大约 5 个 token，因为 `/`、`.` 和数字都各自成 token。**标点和数字是 token 效率最差的东西**，而中文常见词往往两个字才一个 token。这解释了为什么 17 个字符能变成 19 个 token。

<Drill title="为什么要分词，而不是直接用字符或单词">

这是一个纯粹的工程权衡，理解了它，很多奇怪现象就都通了。

两个极端都不可行：

- **按字符切**：词表只要几百个，但序列变得极长。而 attention 的计算量是序列长度的**平方**，序列长 4 倍，计算量就是 16 倍。太贵。
- **按单词切**：序列很短，但词表要几百万，而且遇到没见过的词（新造词、拼写错误、罕见人名）就彻底歇菜。

所以实际用的是折中方案 **BPE（byte pair encoding）**：从单个字节开始，统计语料里最常一起出现的相邻组合，反复合并成新 token，直到词表达到预定大小（通常十万上下）。结果是常见词占一个 token，罕见词被拆成几个片段，而任何输入都不会「无法表示」——最坏情况退化到字节。

这个设计有几个直接后果，值得记住：

**一，模型看不见字母。** 经典的「strawberry 里有几个 r」之所以答错，是因为模型看到的可能是 `straw` + `berry` 两个编号，它压根没有字母级别的视野。同理，模型不擅长反转字符串、数字符个数、处理精确的字符位置。**这不是智力问题，是输入表示的问题。**

**二，语言之间的 token 效率差异很大。** 英文的分词器训练语料以英文为主，所以英文最省，中文次之，稀有语种最亏。同一段意思，中文常常比英文多花 30%~60% 的 token——这直接是钱。

**三，格式也在花钱。** 缩进、重复的 XML 标签、冗长的 JSON key，全都是实打实的 token。到 L06 做上下文压缩时，「换一种更紧凑的表示」是最容易拿到的一笔收益。

</Drill>

<CursorHook>

你有没有遇到过 Cursor 在长文件里改代码时，行号引用出错、或者把某一行数错？这跟 strawberry 数不清 r 是同一件事——模型没有可靠的「行」和「字符位置」概念，它只有一串 token。

所以 Cursor 的编辑工具不是让模型输出「在第 47 行插入」，而是让它输出**要替换的原文片段**和**替换后的内容**，由确定性的代码去做匹配和替换。**把模型不擅长的部分交给代码**，这是工具设计的核心原则，L04 会正式展开，L17 你会自己写一遍这个编辑工具。

</CursorHook>

## 三、Context Window：给了你 100 万，但你不该用满

DeepSeek V4 的上下文窗口是 **1M token**。听起来问题解决了——一整个代码库都塞得下，还要什么上下文工程？

恰恰相反。窗口变大之后，**限制从「装不装得下」变成了「值不值得装」**，而后者是个难得多的问题。有三个理由让你几乎永远不该把窗口填满。

**理由一：钱是线性涨的。** 上下文里的每一个 token，你**每一轮都要重新付一次**钱。下一节会算这笔账，结论会比你预期的难看。

**理由二：首字延迟跟着涨。** 还记得你测的 TTFT 吗？1.056 秒，输入是 19 个 token。输入变成 10 万 token，这个数字会变成好几秒——而且是**每一轮**都要付出的等待。

**理由三，也是最反直觉的：模型会变笨。** 这不是比喻。

<Drill title="lost in the middle：长上下文里的注意力稀释">

有一个被反复复现的实验：把一条关键信息藏进一段很长的上下文里，然后问模型这条信息。把它放在开头，模型答对率很高；放在结尾，也很高；**放在中间，正确率显著下降**。画出来是一条 U 形曲线。

原因可以从两个层面理解。

**机制层面**：attention 的本质是给上下文里每个位置算一个权重，然后加权求和。权重经过 softmax 归一化，**总和恒为 1**。这意味着注意力是一种零和资源——上下文里多一个 token，平均每个 token 分到的注意力就少一分。当你塞进 10 万 token 时，那条关键信息分到的权重被稀释到了很低的水平。

**训练层面**：位置编码让模型对相对位置敏感，而训练语料里长文本的开头（背景设定）和结尾（结论、最近的对话）通常信息密度最高，模型学到了这个先验。

工程含义非常直接，而且和「窗口有多大」完全无关：

- **重要的东西放开头或结尾**，别埋在中间。系统指令放最前，当前任务放最后。
- **短而精的上下文，效果好过长而全的上下文。** 检索时宁可给 5 条高相关的，不要给 50 条沾边的——这条会在 L09 讲 RAG 时反复出现，很多 RAG 系统效果差就是因为召回太多。
- **1M 的窗口是给你留余量的，不是让你填满的。**

L05x 会把 attention 的数学过程完整走一遍。现在你只需要记住这条 U 形曲线。

</Drill>

<CursorHook>

这解释了 Cursor 里两个你可能已经感觉到但没深究的现象。

一是**长对话会变笨**。聊到几十轮之后，它开始忘记你前面定的规矩、重复问已经回答过的问题。那不是「记忆满了」，是前面的内容被稀释到几乎不影响输出了。所以官方建议是任务切换时开新对话，而不是一直往下聊——你现在知道这条建议不是省钱，是保智商。

二是 **Cursor 为什么不把整个项目塞进去**，哪怕上下文放得下。它做的是检索：搜相关文件、只取相关片段。这个决策的依据正是上面那条 U 形曲线。

</CursorHook>

## 四、模型只做一件事：给下一个 token 排概率

现在到了最核心的一层。你调用的那个庞然大物，一次前向计算只干一件事：

**读入到目前为止的所有 token，为词表里的每一个 token 输出一个分数，表示「下一个应该是它」的可能性。**

就这样。没有别的。它不会「思考」、不会「决定要说什么」、不会「查资料」——它输出的是一个长度等于词表大小（约十万）的分数向量，叫做 **logits**。

从 logits 到你屏幕上那个字，中间还有两步：

```text
logits (十万个原始分数)
   │
   │  ÷ temperature        ← 你的旋钮在这里
   ↓
softmax → 概率分布（十万个数，加起来等于 1）
   │
   │  top_p / top_k 截断    ← 你的另一个旋钮
   ↓
按概率随机抽一个            ← 「随机」两个字是关键
   │
   ↓
这个 token 被追加到输入末尾，整个过程重来一遍
```

最后那句是整件事的关键：**每生成一个 token，都要把它接到输入后面，重跑一次完整的前向计算。** 这就是「自回归」，也是 L00 里那条「输出长度主导总时长」的根源。你的 1000 个输出 token，是 1000 次完整的前向计算；而 19 个输入 token 只需要 1 次（这一次可以内部并行）。

1.056 秒对 28.722 秒。现在这两个数字应该完全讲得通了。

### temperature 到底在调什么

`temperature` 是在 softmax 之前给所有 logits 做的一次除法。

- **temperature < 1**：相当于把分数拉开差距，高分的更高，低分的更低。分布变尖，模型更倾向于选那个最可能的 token。输出更稳定、也更平庸。
- **temperature > 1**：分数被压平，冷门 token 也有了机会。输出更多样、也更容易跑偏。
- **temperature = 0**：退化成「永远选分数最高的那个」，这叫贪心解码。

`top_p`（核采样）是另一个思路：把 token 按概率从高到低排，累加到 p（比如 0.9）为止，只在这个集合里抽。它的好处是**自适应**——模型很确定时集合里可能只有 1 个 token，很不确定时可能有几百个。

<Pitfall title="temperature = 0 不等于确定性输出">

这条几乎每个 agent 工程师都会在某次调试里痛苦地学到。

设了 `temperature: 0`，同样的输入跑两次，你仍然可能拿到不同的输出。原因和采样无关，全部来自底层：

- **浮点运算不满足结合律。** GPU 上的并行归约（比如求和）顺序不固定，`(a+b)+c` 和 `a+(b+c)` 会有极微小的差异。绝大多数时候不影响结果，但当第一名和第二名的 logits 差距极小时，这点误差足以让排名反转。一旦某个 token 选择不同，后面整段就分道扬镳了——这是典型的混沌系统。
- **批处理会改变计算路径。** 你的请求和其他用户的请求被打包在一起计算，批次大小不同，kernel 的选择和归约顺序就不同。而你完全无法控制自己被分到多大的批次里。
- **MoE 模型还多一层。** DeepSeek V4 是混合专家架构，每个 token 由路由器决定送给哪几个专家。某些实现里路由会受同批次其他 token 影响，于是你的输出和「同一批里恰好有谁」有关。

所以正确的心态是：**temperature: 0 是「尽量稳定」，不是「保证一致」。**

这条直接决定了 L12 evals 那节课的整个方法论：你**不能**用「输出等于某个固定字符串」来做断言，那样的测试会随机地红，然后你会开始忽略它，然后它就没用了。评测必须建立在**语义**或**结构**层面——JSON 能不能解析、必需字段在不在、数值在不在合理区间、多次采样的通过率是多少。

</Pitfall>

<CursorHook>

你在 `stream.ts` 里收到的那些 `thinking_delta`，就是这套机制的一个应用。DeepSeek V4 默认开启思考模式，模型先生成一段推理过程，再生成正式回答。

值得想清楚的是：**那段思考不是模型「内部的想法」被暴露出来了，它就是普通的输出 token**，一样按输出价格计费，一样占用生成时间。你那次 28 秒里有相当一部分花在思考上。

这带来一个真实的取舍——推理能提升复杂任务的准确率，但要付延迟和 token 的代价。L03 会讲什么时候值得开、什么时候纯属浪费。

</CursorHook>

## 五、幻觉是这个机制的必然产物

现在你有了足够的背景，可以正面回答那个所有人都会问的问题：为什么模型会一本正经地编造事实？

因为**它从来就没有在「陈述事实」，它一直在「续写最像样的下一个 token」**。

把前面几节连起来看：模型的每一步都是从概率分布里采样。当你问它一个它确实知道的事情，正确答案的概率会非常高，采样几乎必然选中它。当你问它一个它不知道的事情——比如一个不存在的 API、一篇虚构的论文——**它的输出层里并没有一个「我不知道」的选项**。它只能在剩下的候选里挑一个「看起来最像那么回事」的。

于是你得到一个语法完美、格式正确、引用规范、而且完全是假的答案。**流畅度和真实性在这个机制里是两件毫不相干的事**，这正是幻觉最危险的地方：它不会以「看起来可疑」的形式出现。

<Drill title="为什么模型不会说「我不知道」">

再往下一层，有两个原因。

**一，训练目标里没有这个东西。** 预训练的目标函数是最大化「给定前文，预测出真实下一个 token」的似然。语料里几乎没有「关于这个问题我没有把握」这种文本模式，模型学到的是「像人类一样把话说完整」。RLHF 阶段会补一些「拒绝回答」的样本，但那是在原有能力上贴的一层补丁，不是机制层面的改变。

**二，模型对自己的「不确定」缺乏可靠的自我认知。** 你可能会想：既然有概率分布，那分布很平坦（熵高）不就说明模型没把握吗？这个思路方向是对的，工业界确实有基于 logprobs 做置信度估计的做法。但它不可靠，因为**模型可以对一个错误答案非常自信**——如果训练语料里某个错误说法反复出现，模型就会以很高的概率输出它。分布的尖锐程度反映的是「这个说法在语料里有多常见」，不是「这个说法有多正确」。

哪些场景幻觉率会飙升，值得当成清单记住：

- **长尾知识**：小众库的 API、冷门人物、地方性规定。语料里出现少，概率分布平坦。
- **精确数字**：日期、版本号、统计值、价格。这些在语料里高度分散，模型只能"编一个像样的"。
- **引用和链接**：论文标题、文献编号、URL。格式感极强而内容任意，是幻觉的重灾区。
- **较新的信息**：训练截止之后的一切。模型不知道自己不知道。

四条里有三条是 agent 的日常。所以整个 agent 领域的很多设计，本质上都是在对抗这一条。

</Drill>

工程上的对策只有一个思路，但有三种形态，你会在后面的课里逐个实现：

- **把事实搬进上下文**，让它不需要回忆。这是 RAG（L09）。
- **给它工具去查、去算、去验证**，把「回忆」换成「执行」。这是 tool use（L04）。搜索、读文件、跑测试，本质上都是在用确定性的手段替换概率性的猜测。
- **在输出之后做验证**，不信任单次结果。这是 evals 和自我校验（L12、L17）。

<Pitfall title="三个看起来管用、其实没用的做法">

**「在 prompt 里写『不要编造，不确定就说不知道』。」** 有一点效果，但很弱，而且它是在跟机制对着干。这句话只是改变了输出分布的一点偏置，模型仍然没有「知道自己不知道」的能力。它甚至会产生新的问题：对它确实知道的事情也开始过度推辞。

**「把 temperature 调到 0 就不幻觉了。」** 完全无效，而且是个很常见的误解。temperature 影响的是**从分布里怎么挑**，不影响**分布本身**。如果错误答案本来就是最高概率的那个，temperature=0 反而保证你每次都拿到它。

**「换个更大的模型就好了。」** 会降低幻觉率，但不会消除——机制没变。而且大模型的幻觉更危险，因为它编得更像真的。

真正有效的只有一件事：**减少它需要「回忆」的部分**。凡是能从上下文里读到、能用工具查到的，就别让它凭记忆答。

</Pitfall>

## 六、无状态：这门课后面一半内容的起因

最后一个性质，也是工程影响最大的一个：**模型 API 是完全无状态的。**

服务端不记得你上一次说了什么。所谓「多轮对话」，完全是你在客户端维护一个数组，每一轮把**整个历史**重新发一遍：

```ts
// 第 1 轮
messages = [{ role: 'user', content: '你好' }]

// 第 2 轮：整个历史重发
messages = [
  { role: 'user', content: '你好' },
  { role: 'assistant', content: '你好！有什么可以帮你的吗？' },
  { role: 'user', content: '刚才我说了什么？' },
]
```

第二轮之所以答得出「你刚才说了你好」，不是因为模型记得，是因为你**又告诉了它一遍**。

这个设计本身是好的——无状态让服务可以水平扩展、任意重试、不用维护会话。但它把一个代价转嫁给了你。

### 把这笔账算出来

一条贯穿全课的判据：**会算账 = 算完之后敢下结论**。这次我们真算。

假设一次 20 轮的对话，system prompt 200 token，用户每轮说 100 token，模型每轮回 500 token。用 DeepSeek V4 Flash 的价格（输入 1 元 / 百万，输出 2 元 / 百万）。

第 n 轮的输入 = 200（system）+ 100n（用户历史）+ 500(n−1)（助手历史）。把 n 从 1 加到 20：

| | token 数 | 单价 | 小计 |
|---|---|---|---|
| 累计输入 | 120,000 | 1 元/M | 0.12 元 |
| 累计输出 | 10,000 | 2 元/M | 0.02 元 |
| **合计** | | | **0.14 元** |

两个结论，都和直觉相反。

**第一，输入的花费是输出的 6 倍**，尽管输出的单价是输入的 2 倍。因为输入被反复重发，总量是输出的 12 倍。**你以为在为「模型说的话」付钱，其实主要在为「你重复告诉它的话」付钱。**

**第二，这个增长是平方级的。** 每一轮的输入都比上一轮多 600 token，累计下来是 O(n²)。20 轮花 0.14 元，40 轮不是 0.28 元，而是 0.52 元。

对比一下：如果 API 是有状态的、每轮只需要发新增的那部分，累计输入只有 2,200 token。**无状态让你的输入 token 涨了大约 54 倍。**

<Note title="所以 prompt caching 才是最值钱的那个优化">

现在看一个数字：DeepSeek 的**缓存命中**输入价是 0.02 元/百万，未命中是 1 元/百万。整整 **50 倍**的差距。

这个比例和上面那个 54 倍的膨胀，在数量级上几乎正好抵消——这当然不是巧合。prompt caching 这个特性存在的全部理由，就是因为所有人都在做同一件事：把几乎相同的长前缀一遍遍重发。缓存把这部分变成近乎免费。

所以在 agent 里，**保持前缀稳定**（system prompt 和早期历史不要随便改动，新内容只往后追加）会直接换来一个数量级的成本差异。这是 L15 的核心内容，但从现在开始你就该有这个意识：**每次你往对话历史的中间插东西，都在让后面所有轮次的缓存失效。**

顺带说，这也是为什么我要求你从第一节课就打印 `usage`。不看账的人做不出这类决策。

</Note>

Python 侧的对应写法，差异仍然只在命名。值得注意的是 `usage` 的字段名两边完全一致，因为那是协议规定的，不是 SDK 决定的。

```python
msg = client.messages.create(
    model="deepseek-v4-flash",
    max_tokens=1000,
    temperature=0,
    messages=[{"role": "user", "content": "详细解释 HTTP/2"}],
)

print(msg.stop_reason)              # 'end_turn' | 'max_tokens' | ...
print(msg.usage.input_tokens)       # 和 TS 侧一模一样的字段名
print(msg.usage.output_tokens)

# 多轮：同样是你自己维护列表，同样每轮全量重发
messages.append({"role": "assistant", "content": msg.content[0].text})
messages.append({"role": "user", "content": "那 HTTP/3 呢？"})
```

真正需要留意的 Python 差异在别处：生态里的 agent 框架（LangChain、LangGraph）会把 `messages` 数组包装成它们自己的 `Message` 对象，于是你读源码时经常看不出「哦，底下其实就是这个数组」。**记住底层永远是这个数组**，看框架代码时就不会迷路。L11x 会专门拆这件事。

## 这节课的收尾

回到开头那四个数字，现在它们应该全都讲得通了：

- **19 个 token** —— 因为分词器按 BPE 切，标点和数字特别费。
- **TTFT 1.056 秒** —— 输入可以一次并行处理完，所以首字快，但会随输入长度增长。
- **恰好 1000 个输出 token** —— 撞上了你设的闸门，`stop_reason` 是 `max_tokens`，而你的代码没检查。
- **28.722 秒** —— 1000 次串行的前向计算，每次生成一个 token。

而这节课真正要你带走的，是下面这四条：

- **模型只会给下一个 token 排概率，然后随机抽。** 所有让你困惑的模型行为，追根溯源都在这一句。
- **幻觉不是缺陷，是这个机制的必然输出。** 对策不是求它别编，是让它不需要回忆。
- **上下文是有成本的注意力预算，不是免费的内存。** 窗口 1M 也一样。
- **API 无状态，历史是你重发的，成本按平方涨。** 后面一半的课都在处理这件事的后果。
