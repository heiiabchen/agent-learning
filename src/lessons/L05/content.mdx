这一节是整门课的顿悟点，所以我先把结论摆出来，你可能会觉得受骗了：

```ts
while (true) {
  const res = await callModel(messages)
  messages.push({ role: 'assistant', content: res.content })

  if (res.stop_reason !== 'tool_use') return res      // 它说完了
  const uses = toolUsesOf(res.content)
  const results = await Promise.all(uses.map((u) => toolbox.execute(u.name, u.input)))
  messages.push(toolResultMessage(uses, results))
}
```

**这就是 agent。** 十行。你在 L02 学了怎么发请求，L04 学了怎么处理工具，这个 `while` 把它们连起来，就得到了一个能自主做多步任务的东西。

<Key>
「Agent」不是一种模型，是一种**控制流**。模型提供每一步的决策，循环提供持续性。理解了这一点，你就理解了这个领域里 90% 的框架在干什么——它们包装的就是这十行，以及围绕它的一圈生产化设施。
</Key>

真正难的部分不在这十行里。难的是：**这个 `while (true)` 什么时候停。**

上面那段代码在生产环境里会破产，而且是三种不同的破产方式。这一节剩下的部分全在讲怎么让它不破产。

---

## 一、五个终止条件，缺一个都会出事

`stop_reason !== 'tool_use'` 只是其中一个，而且是最乐观的那个。完整的清单：

| 终止条件 | 缺了会怎样 |
|---|---|
| 模型给出最终答案 | —— 这是唯一的正常出口 |
| 步数超上限 | 死循环烧到你发现为止 |
| 累计成本超预算 | 一次跑挂一个月的额度 |
| 挂钟时间超时 | 用户面前转圈转到超时 |
| 外部取消 | 用户点了停止，它还在跑 |

五个里面有四个是**保护性**的。这个比例本身就是一条信息：**agent loop 的代码里，大部分不是在实现功能，是在防止失控。**

而且它们要**同时**生效，检查点在循环顶部：

```ts
for (let step = 1; ; step++) {
  if (step > maxSteps) return stop('step_limit')
  if (ledger.totals().yuan > maxYuan) return stop('budget')
  if (Date.now() - t0 > maxMs) return stop('timeout')
  if (signal?.aborted) return stop('cancelled')
  // …正常流程
}
```

<Pitfall title="终止时必须返回「为什么停」，不能只返回结果">

这条看起来是小事，但它决定了你的 agent 能不能被调试和被评估。

```ts
// ✗ 调用方无法区分「答完了」和「被掐了」
async function run(task: string): Promise<string>

// ✓
interface AgentRun {
  text: string
  reason: 'done' | 'step_limit' | 'budget' | 'timeout' | 'cancelled' | 'error'
  steps: number
  usage: Totals
  transcript: Message[]
}
```

第一种签名的问题：撞上步数上限时，你返回的是模型最后一次说的话——**那句话看起来像一个答案**，可能还挺像样。调用方拿去用了，用户拿去信了。

而这个 bug 的表现形式是「agent 偶尔给出不完整的答案」，你会怀疑 prompt、怀疑模型、怀疑工具，最后才想到去看是不是撞上限了。

L12 做 evals 时，`reason` 的分布会是你最先看的指标之一：**如果 20% 的运行是 step_limit，那你的成功率数字全是假的。**

</Pitfall>

## 二、死循环的四种成因

死循环不是「偶尔会有的意外」，它是 agent 的**默认行为**，除非你专门设计了防线。四种成因，我按见到的频率排：

**成因一 · 你把 `tool_use` 块从历史里丢了。**

L04 那个 Pitfall 的具体后果。模型下一轮看不到自己刚才要求过什么，于是**重新要求一次**。它每轮都在做同一个决定，每轮都合理，整体是个死循环。

这种循环的特征是：完全一样的工具调用，参数都不变。**在日志里最容易认，因为它太整齐了。**

**成因二 · 工具报错但没给出路。**

`ENOENT: no such file or directory` 这种错误信息，模型读完的最优策略往往就是重试。它不知道还能干什么。L04 那条「错误信息要给出路」防的就是这个。

**成因三 · 两个工具互相撤销。**

模型 `write_file` 写了一版，然后 `read_file` 读出来觉得不对，又写回去。这种循环有变化、有进展的表象，但状态在振荡。

这种最难发现，因为每一步单独看都是合理的。

**成因四 · 任务本身不可能完成，但模型不肯放弃。**

「把测试跑通」——而测试因为环境缺依赖根本跑不起来。模型会一直尝试新的角度，因为它的训练目标里没有「承认做不到」这个高概率选项。

<Drill title="为什么模型不擅长放弃">

这个现象有很实在的原因，值得知道，因为它改变你的 prompt 写法。

预训练数据里，「解决了问题」的文本远多于「我放弃了」的文本。技术博客、Stack Overflow 的采纳答案、教程——**语料本身是成功偏置的**。RLHF 阶段进一步强化：标注员更偏好有帮助的、积极的回答。

结果就是「继续尝试」的概率总是显著高于「宣告失败」。这不是它嘴硬，是分布如此。

三个可操作的推论：

**一，你必须在 prompt 里明确地给「放弃」授权，而且要给形式。** 不是「不确定时可以停下」，而是：

```text
如果连续两次尝试同一个方向都失败，停止尝试，输出：
<blocked>你尝试了什么、观察到什么、需要什么才能继续</blocked>
```

给了明确的输出格式，「放弃」才成为一个它认得的动作。**没有格式的授权等于没有授权**——这和 L03「约束要配一条出路」是同一条。

**二，别指望 prompt 能兜住。** 这是概率手段，你的步数上限才是硬保证。两个都要有：prompt 降低触发频率，上限兜住最坏情况。

**三，`<blocked>` 这个出口本身是有价值的产物。** 它告诉你 agent 在哪类任务上卡住，而这正是 L12 做 evals 时最有用的信号之一——比「失败了」这个结论信息量大得多。

</Drill>

<Pitfall title="检测重复调用：一个二十行的防线">

比步数上限更精准的一招，实现成本很低：

```ts
const seen = new Map<string, number>()
const key = `${use.name}:${JSON.stringify(use.input)}`
const n = (seen.get(key) ?? 0) + 1
seen.set(key, n)

if (n > 2) {
  // 不要静默跳过——那样模型不知道发生了什么，会继续困惑
  return {
    isError: true,
    content: `你已经用完全相同的参数调用了 ${use.name} ${n} 次，结果不会变。换个思路，或者说明你卡在哪。`,
  }
}
```

三个设计点：

**一，返回给模型，而不是静默跳过。** 静默跳过等于给它一个空结果，它会更困惑。要让它知道自己在打转。

**二，阈值是 2 而不是 1。** 重试一次是合理行为（可能是瞬时错误）。第三次就不是了。

**三，`JSON.stringify` 的 key 不稳定。** 对象字段顺序变了 key 就变了，这个防线就漏了。生产环境里要做规范化——**这就是那种「写完觉得搞定了，三个月后发现一直没生效」的 bug**。

</Pitfall>

## 三、预算控制：三个维度，别只看步数

步数上限是最容易实现的，也是最不精确的。因为**每一步的成本差异极大**：一次 `list_dir` 和一次读进 50KB 文件的调用，成本差两个数量级。

三个维度都要有上限，各自防不同的东西：

| 维度 | 防什么 | 典型值 |
|---|---|---|
| 步数 | 逻辑死循环 | 15~30 步 |
| token / 钱 | 单次运行的成本失控 | 按业务定，要能配置 |
| 挂钟时间 | 用户等待与资源占用 | 交互式 60~120 秒 |

而且要**在花钱之前检查**，不是花完之后：

```ts
// ✗ 已经花掉了才发现超预算
const res = await callModel(messages)
if (ledger.totals().yuan > maxYuan) return stop('budget')

// ✓ 先估算，超了就不发
const estimated = estimateInputTokens(messages)
if (ledger.totals().yuan + priceOf(estimated) > maxYuan) return stop('budget')
const res = await callModel(messages)
```

<Note title="上下文增长是这里真正的成本引擎">

回到 L04 那个练习里你算过的数字：每轮的输入包含**之前所有轮的全部内容**，包括所有工具结果。

第 1 轮：500 token
第 5 轮：8000 token
第 15 轮：60000 token —— 而且已经接近上下文窗口了

因为 API 是无状态的（L02 第一条），每一轮都要把整个历史重新发一遍。**这是 O(n²) 的**：n 步任务的总输入 token 和步数的平方成正比。

这个平方增长解释了三件事：

1. **为什么步数上限这么重要。** 30 步不是 15 步的两倍成本，是四倍。
2. **为什么 L06 上下文工程是独立的一整节。** 不压缩上下文，长任务在数学上就不可行。
3. **为什么工具输出要裁剪。** 一个塞进 20KB 日志的工具结果，在剩下的每一轮里都要重新付费。L04 那个 `truncate` 和 `read_file` 的行号区间参数，现在你知道它们为什么存在了。

</Note>

## 四、框架到底包装了什么

你现在写完了一个 agent loop。那 LangChain、LlamaIndex、各种 Agent SDK 在干什么？

诚实的答案：**它们包装的就是你刚写的这些，加上一圈生产化设施。**

| 框架提供的 | 你自己写要多少代码 | 值不值得依赖 |
|---|---|---|
| agent loop | 十几行 | 不值。自己写你才控制得住 |
| 工具注册与 schema 生成 | 你在 L04 写了 | 有点值（Pydantic / zod 那层确实省事） |
| 多种 LLM 的适配 | 每家几十行 | **值。** 这是真正的脏活 |
| 流式与事件回调 | 你在 L02 写了 | 不值 |
| 记忆 / 向量库集成 | 不少 | 值，但耦合很深（L08、L09 会讲） |
| 追踪与可观测性 | 不少 | **值。** 见 L13 |
| 各种预制的 agent 模式 | 看情况 | 通常不值——抽象层次不合你的需求 |

我的立场，说清楚以免你觉得这是反框架宣传：

**agent loop 自己写，周边设施用现成的。** 理由是**调试**。当 agent 行为不对时，你需要看到确切的 messages 数组、确切的每一次请求。框架把这些藏在几层抽象后面，出问题时你在读框架源码而不是在解决问题。

而适配层、追踪、向量库这些，接口清晰、行为可预测、自己写没有额外收益，用现成的。

<CursorHook>

Cursor、Claude Code 这类工具的核心，就是你刚写的那个循环。差异全在外围，而且这些外围差异恰好就是这门课后面的目录：

- **上下文里放什么**（打开的文件、光标位置、最近的编辑）→ L06
- **工具集怎么设计**（编辑用精确替换而不是写全文）→ L04 你已经做过判断
- **UI 怎么展示中间过程**（工具调用可折叠、diff 可预览）→ L16
- **哪些操作需要人工确认** → L14
- **上下文超了怎么办**（压缩、开新会话）→ L06

你在 Cursor 里遇到过「它开始重复同样的操作」吗？那就是这一节讲的死循环。你按停止键的那个动作，对应的是第一节里那个 `signal?.aborted` 检查。

</CursorHook>

这一节的 verify 用的是**脚本化的假模型**——`shared/fake.ts` 里那个。这个东西本身值得注意：

**测 agent loop 不能用真模型。** 真模型不确定、慢、花钱，而且你没法让它按你想要的方式失败。假模型能：让它连续三次要求同一个工具，看你的重复检测有没有响；让它永不给出最终答案，看步数上限有没有兜住。

L12 做 evals 时你会大量用到这个思路。**能用假模型测的东西，就不要用真模型测。**

</Lab>

<PyMirror>

Python 这边有一个 TS 没有的实际问题：**取消**。

TS 的 `AbortSignal` 是一等公民，`fetch` 原生支持，传下去就行。Python 的取消是通过 `asyncio.CancelledError` 实现的，而它是**异常**，这带来两个真实的差异：

```python
try:
    result = await run_agent(task)
except asyncio.CancelledError:
    # ★ 必须重新抛出，否则你破坏了整个取消链
    #   吞掉 CancelledError 是 asyncio 里最经典的一个错误
    await cleanup()
    raise
```

第一个差异：**`except Exception` 抓不到它**（`CancelledError` 从 3.8 起继承自 `BaseException`，不是 `Exception`）。这个设计是故意的，就是为了防止你用宽泛的 except 意外吞掉取消。但如果你写的是 `except BaseException` 或者裸 `except:`，你会吞掉它，然后表现为「点了停止但它还在跑」。

第二个差异：取消是**协作式**的，只在 await 点生效。一段纯计算的循环里没有 await，取消信号进不去。TS 那边同理（单线程），但 Python 里更容易写出这种代码，因为同步和异步可以混写。

`shared/agent.py` 里我用的是显式的 `cancelled` 回调而不是依赖 `CancelledError`，理由是**agent loop 需要在取消时返回部分结果**——已经做了几步、花了多少钱，这些信息不该丢。异常路径上带出部分结果是能做的，但很别扭。

</PyMirror>

## 五、这节课的纪律

1. **循环即 agent。** 剩下的都是防止失控。
2. **五个终止条件同时生效**，检查点在循环顶部。
3. **必须返回「为什么停」。** 撞上限和答完了，看起来是一样的。
4. **重复调用检测**比步数上限精准，二十行就能写。
5. **预算在花钱之前检查**，三个维度都要有。
6. **明确授权「放弃」，并给它一个格式。** 没格式等于没授权。
7. **循环自己写，周边用现成的。** 判据是调试的时候你要看到什么。

你现在有一个能干活的 agent 了。但它有个硬上限：跑十几步之后上下文就爆了。
