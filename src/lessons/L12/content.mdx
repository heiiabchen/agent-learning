前面十二节里，你做过很多次二选一的判断。

L03 改 prompt 的写法，L06 选压缩策略，L07 挑编排模式，L09 配检索参数，L11 定扇出宽度。每一次你都在两种做法之间选了一种，**而你没有任何手段判断选对了没有。**

这一节就是补这个洞的。它被称作分水岭不是因为技术难——它的数学全是本科水平——而是因为它是"我觉得这样更好"和"我知道这样更好"之间的那条线。

但真正的难点不在打分。

<Key>
**评测的难点不是怎么打分，是怎么不骗自己。**

因为评测有一个很坏的性质：**它产出数字，而数字自带权威。**

一个错的评测比没有评测更糟——没有评测的时候你至少知道自己在猜。有了一个错的评测，你会做很多错决定，并且每次都觉得自己有数据支持。
</Key>

所以这一节的每一小节，讲的都是同一件事的不同侧面：**一个看起来完全正常的数字，为什么是空的。**

## 一、"一致率 85%" 可能等于零信息

先看最常见的那个错误，因为它同时是最容易修的。

你要评测的东西里总有一部分没法用规则判——"这个解释清楚吗"、"这个回答有帮助吗"。于是你写一个 LLM judge，然后拿它和人工标注对一下，算出**一致率 85%**。

听起来可以用了。

<Pitfall title="一个什么都不看的 judge 也能拿到 80%">
你的评测集里 80% 的样本人工标注是"通过"。

现在考虑这个 judge：

```python
def judge(output):
    return "pass"
```

它的一致率是**多少**？80%。

它什么都不看，不调模型，不花钱，一致率 80%。

而你那个真的在判断的 judge 拿到 85%。**这两个数之间的 5 个百分点，就是你全部的证据。**
</Pitfall>

原始一致率的问题是它把"猜对的"和"判对的"算在一起。修法是扣掉猜对的那部分：

<Key>
    kappa = (观测一致率 − 偶然一致率) / (1 − 偶然一致率)

其中偶然一致率是：两个评判者各自保持自己的标签比例、但**完全随机**地贴，能撞对多少。

    chance = Σ_label  P(judge 贴这个标签) × P(人贴这个标签)

那个永远说 pass 的 judge，kappa 恰好是 **0**。
</Key>

这个量叫 Cohen's kappa，1960 年提出的。它不新，但在 LLM 评测里被漏掉的频率高得惊人。

差距有多大值得看一眼实测数据。2026 年一项覆盖 21 个 judge、54 万次判断的普查给出了这个结果：

| 指标 | 数值 |
|---|---|
| 原始一致率高估偶然校正后一致性 | **33.8 到 41.3 个百分点** |
| 出现这种高估的模型数 | 21 个里 **21 个** |
| 表现最好的那个 judge 的原始一致率 | 0.849 |
| 同一个 judge 的 kappa | **0.511** |

<Key>
**21 个模型无一例外。** 而这个差距的大小主要取决于**你的标签分布**，不取决于 judge 好坏。

标签越不均衡，raw 越虚高。而生产日志天然极度不均衡（下面第八节会讲这件事的另一个后果）。

所以规矩很简单：**报告里 kappa 是主指标，原始一致率只能当辅助。**
</Key>

kappa 的阈值大致是这样，记住 0.4 这条线就够用：

- 0.8 以上：很好，可以拿来当自动门禁
- 0.6 到 0.8：可用，但重要决策还是要人看一眼
- 0.4 到 0.6：只能当粗筛
- 0.4 以下：**不足以做上线决策**

<Pitfall title="chance 等于 1 的时候分母是 0">
如果人工标注**只有一个标签**（全是 pass），偶然一致率就是 1，kappa 的分母是 0。

别让它变成 `NaN`，也别抛异常。**那种情况本身就是一个要报出来的问题**——它说明你这个评测集没有任何区分度，任何 judge 在上面都拿不到有意义的分数。

它不是一个计算错误，是一个评测集设计错误。
</Pitfall>

## 二、七成的判据根本不需要 judge

上面那一节可能给了你一个印象：judge 很麻烦。对的，所以下一个问题是**能不用就不用**。

绝大多数人上手评测的第一件事就是写一个 LLM judge，而其中大半根本不需要：

| 判据 | 该用什么 | 为什么 |
|---|---|---|
| 严重级别分类对不对 | 精确匹配 | 有唯一正确答案 |
| 输出是合法 JSON 且有 severity 字段 | 结构检查 | 解析一下就知道 |
| 回答里带没带引用编号 | 正则 | 形式要求，不涉及语义 |
| 不能出现内部服务名 | 正则（**反向**） | 同上 |
| 解释能不能让非技术同事看懂 | judge | 确实需要判断 |

这三类确定性断言合起来通常占判据的七八成，而它们的共同点是：**确定、免费、不会漂。**

<Key>
judge 的代价不只是钱。真正贵的是另外三样：

- 它自己会错，而且错得**有系统性**（下一节会量出来）
- 它的输出会随模型版本漂移，于是你的**历史分数不可比**
- 它慢，于是你不会想在每次提交时跑它——而一个不在 CI 里跑的评测，三周之后就没人看了
</Key>

路由的优先级：`expect`（精确）> `fields`（结构）> `pattern`（正则）> `semantic`（judge）。都给了就选更便宜更确定的那个。

<Pitfall title="反向断言写成正向，含义会正好反过来，而测试全绿">
"不能出现内部服务名"是一条**反向**断言：命中就算失败。

如果你的检查框架假设所有正则都是"必须匹配"，这条判据的含义会**正好反过来**——它会要求输出里必须有 `internal-`。

而这个 bug 不会被任何测试抓住，因为大多数输出里确实没有内部服务名，于是断言"失败"，于是评测报告里这一条一直是红的，你会以为是模型的问题。

安全相关的判据大半是反向的。所以判据结构里得有一个显式的 `negate` 标记。
</Pitfall>

还有一个兜底情况值得单独想：一条判据什么依据都没给，既没有期望值也没标 semantic。

<Key>
比如"回答质量要好"。路由到 judge 是对的，**但这通常意味着判据本身没定义清楚。**

一条你自己都说不出怎么验的判据，judge 也判不了。它只会给你一个看起来像分数的数字。

所以这个兜底分支应该在 `why` 里说出来。评测框架的一部分职责是**告诉你哪条判据是你没想清楚的**。
</Key>

## 三、五步体检，而每一步只抓得住一种退化

judge 上线之前要做五件事：

1. **偶然校正的一致率**（kappa，不是 raw）
2. **位置偏见**（AB+BA 成对问，`|P(排在前面的赢) − 0.5| > 0.10` 就有问题）
3. **冗长偏见**（长度差与判决的相关性，`|r| > 0.05` 就有问题）
4. **重测信度**（同一个 prompt 跑多次，低于 0.9 就有问题）
5. **一致性—偏见悖论**（下面单独讲）

看起来像一张例行检查表，可以照着打勾。**但它的真正结构不是这样的**——这五步不是五道难度递增的关卡，而是五个**互相看不见对方**的探照灯。

下面三个 judge，每一个都只被其中一步抓住：

| judge | 实现 | kappa | 重测信度 | 位置偏见 | 谁抓住了它 |
|---|---|---|---|---|---|
| 甲 | 永远选 A 这个答案 | **0.000** | 1.000 | 0.000 | 只有 kappa |
| 乙 | 永远选**排在前面**那个 | 1.000 | 1.000 | **0.333** | 只有位置互换 |
| 丙 | 真的在判断，偶尔抖 | 1.000 | **0.786** | 0.000 | 只有重测 |

<Key>
**judge 乙 是这张表的全部意义。**

kappa 完美 1.000，和人工标注一条不差。重测信度完美 1.000，问一百次答案都一样。

而它的实现是"**永远选排在前面的那个**"。

它的 kappa 那么好看，只是因为你测试的时候更好的答案恰好多数排在前面。上线之后顺序一换，它的判断**全部反过来**——而 kappa 完全看不出这件事。
</Key>

所以五步一步都不能省。少查任何一项，就会有一类 judge 带着漂亮的数字上线。

而这里面第五步最反直觉，值得单独说：

<Key>
**重测信度高不等于 judge 可靠。**

因为这两个量测的是**两种不同的扰动**：

- 重测信度：**同一个 prompt** 问多次 —— 答案稳不稳
- 位置偏见：把两个答案**换个顺序** —— 一个语义上完全无关的扰动，答案变不变

一个只看位置的 judge，在第一种扰动下是满分（它完全确定），在第二种扰动下也是满分（它只看位置）。

**确定性在第二种扰动上一分钱都不值。**
</Key>

这不是假想的失效。2026 那项普查里有两个**已经在生产环境部署**的 judge 正好落在这个格子：

- 一个重测信度 0.992，位置偏见 0.192
- 另一个重测信度 0.988，位置偏见 0.125

论文的原话值得记下来：**最可复现的 judge 恰恰是最不可信的那些。**

<Note title="为什么这一类失效特别难被发现">
因为"我的评测每次跑分都一样"听起来完全像是一件好事。

它是团队里会被拿出来说的那种指标——稳定、可复现、看着专业。于是没有人会想去查它。

而位置偏见需要你**主动构造一个对称的实验**才能测出来。它不会自己冒出来。
</Note>

顺便说一下位置偏见的实测分布，因为它推翻了一个常见的偷懒理由：

- 最好的 judge 是 0.002，最差的 0.192，**差近两个数量级**
- **同一家的两个型号能差 70 倍**（一个 0.002，一个 0.125）
- 小模型、便宜模型显著更严重
- 推理型模型会降低但**不会消除**——三个里只有一个降到 0.05 以下

<Key>
所以"我用的是好模型所以没有位置偏见"是不成立的。同一家的相邻型号都能差 70 倍。

**这件事必须实测。** 而实测很便宜：每条样本 AB、BA 各问一次。
</Key>

## 四、冗长偏见：一条过时的常识

这一条单独拎出来，因为它是个很好的例子，说明**评测领域的"常识"会过期**。

2023 年的研究里冗长偏见很显著，报告的量级在 20% 到 40%。于是"judge 偏爱长答案，记得在 rubric 里压一下"成了标准建议，写进了很多团队的规范。

而 2026 那项 21 个 judge 的普查里，**所有 21 个模型的冗长偏见都低于 0.011**。这一条基本上被修掉了。

<Pitfall title="但「被修掉了」不等于「不用测了」">
两件事要注意：

第一，那是在**单一成对 rubric** 下测的。换 rubric、加参考答案、要求 judge 写理由，都可能把它带回来——原论文自己在局限性里写了这一点。

第二，也是更重要的：**测它很便宜**（一个相关系数），而"我读过的文章说这个问题不存在了"**不是证据**。

这一节从头到尾在讲的就是这件事：把"我觉得"换成"我测了"。这条常识本身也不例外。
</Pitfall>

## 五、位置偏见那个式子，最自然的写法是错的

这一小节讲一个具体的实现坑，因为它非常典型：**写错之后测出来的数看起来完全正常。**

成对判决的数据结构长这样，注意最后一句注释：

```ts
interface PairedVerdict {
  ab: 'A' | 'B' | 'tie'  // AB 顺序下判谁赢
  ba: 'A' | 'B' | 'tie'  // BA 顺序下判谁赢（已换算回原来的 A/B 命名）
  lenA: number
  lenB: number
}
```

直觉的实现是这样：

```ts
// ✗ 错的
const aWins = decided.filter((v) => v === 'A').length / decided.length
return Math.abs(aWins - 0.5)
```

<Pitfall title="它测的是内容分布，不是位置偏见">
因为 `ab`/`ba` 已经换算回**内容**命名了。

于是当答案 A 真的比 B 好、judge 也两次都正确地选了 A 时，`P(A 赢)` 是 1，这个式子会报出 **0.5 的"位置偏见"**——而这个 judge 一点位置偏见都没有。

换句话说 `|P(A 赢) − 0.5|` 测的是"**A 这个答案有多常赢**"。那是内容分布。

只有在胜负恰好五五开的数据集上，这两件事才碰巧数值相等。**而这就是为什么这个 bug 很难被发现**——你构造测试数据的时候会很自然地做成对半，于是它一直是对的。
</Pitfall>

正确的算法要看**位置**：

```ts
// ✓ 对的
for (const v of verdicts) {
  if (v.ab !== 'tie') { decided++; if (v.ab === 'A') firstWins++ }  // AB 里前面是 A
  if (v.ba !== 'tie') { decided++; if (v.ba === 'B') firstWins++ }  // BA 里前面是 B
}
return Math.abs(firstWins / decided - 0.5)
```

这样内容偏好会自动抵消：一个只看内容的 judge，在 AB 里选 A（前面赢）、在 BA 里也选 A（后面赢），一前一后正好抵平。

由此还能推出一条很有用的关系：

<Key>
    位置偏见 ≤ 位置翻转率 / 2

证明一行：`ab === ba` 的那些对必然一前一后各贡献一次，完全中和，所以只有**翻转的对**才能推动这个数。

它的用处是把两种完全不同的失效分开：

| 翻转率 | 位置偏见 | 诊断 | 修法 |
|---|---|---|---|
| 40% | 0.20 | 翻转**全朝一个方向**，系统性偏爱某个位置 | AB+BA 对称化，不一致的算 tie |
| 40% | 0.01 | 翻转方向**随机**，这不是偏见，是噪声 | 降温度 / 给参考答案 / 多数投票 |

只看位置偏见这一个数是分不出这两种情况的，而它们的修法完全不同——**对称化消不掉噪声。**
</Key>

## 六、涨的那 2%，是真的吗

judge 查完了，现在假设你的评测能给出可信的分数。下一个问题是这个分数的**抖动有多大**。

这件事的直觉几乎所有人都是错的。小样本的置信区间宽得超乎想象：

| 样本量 | 成功率 80% 的 95% 置信区间 | 区间宽度 |
|---|---|---|
| 50 | [69%, 90%] | 21 个百分点 |
| **150** | **[74%, 87%]** | **13 个百分点** |
| 500 | [76%, 84%] | 7 个百分点 |
| 2000 | [78%, 82%] | 4 个百分点 |

<Key>
看 150 条那一行——这是很多团队评测集的实际规模。

区间宽 13 个百分点。**你测出 80%，真值在 74% 到 86% 之间都不奇怪。**

那么"改动后从 80% 涨到 82%"意味着什么？**什么都不意味着。**
</Key>

算法叫 bootstrap，全部内容就这么点：

    重复 iters 次：从原样本里**有放回**地抽 n 个，算均值
    把这 iters 个均值排序，取 2.5% 和 97.5% 分位

<Pitfall title="随机数必须带 seed">
评测结果必须可复现。不然"跑分变了"这件事你分不清是改动导致的还是 bootstrap 自己抖的。

这一条听起来很琐碎，但它就是这节课的主题本身——**你在给自己造一个测量工具，而测量工具的第一要求是它自己不能乱动。**
</Pitfall>

看最后一行还有个更实际的结论：要把区间压到几个百分点，样本量得上千。而攒一千条标注好的样本是个大工程。

<Key>
所以现实的做法不是"攒一个巨大的评测集"，是**成对比较**。

对着 `diffs[i] = after[i] − before[i]` 这个序列做 bootstrap，而不是对两次的均值各自算区间。

成对能消掉"样本本身难易不同"那部分方差，在同样的样本量下功效高得多。下一节的函数就是这么做的。
</Key>

## 七、净涨 2%，背后可能是换了一批 bug

这是这一节最重要的一个结论，而它不需要任何统计知识。

"净涨 2 个百分点"可以是下面任意一种情况：

| 情况 | 明细 | 该做什么 |
|---|---|---|
| 干净的改进 | 修好 3 个，弄坏 0 个 | 合并 |
| **换了一批 bug** | 修好 13 个，**弄坏 10 个** | **停下来看那 10 个是什么** |
| 纯抖动 | 修好 0 个弄坏 0 个，两三个 case 波动 | 什么都没发生 |

<Key>
第二种是最需要被看见的：净值是正的，看起来该合并，**但你实际上是在拿 10 个能用的 case 换 13 个。**

而如果那 10 个里有付费客户在走的路径，这个改动是**净负的**。

**净值会把这件事藏起来。所以必须报明细。**

`fixed` 和 `broken` 两个列表比那个 delta 重要得多。
</Key>

而实现这个函数的时候有一个很隐蔽的顺序问题：

<Pitfall title="最自然的判断顺序会让这句话永远不出现">
直觉的写法是先分"显著 / 不显著"，再在显著的那一支里报"换了一批 bug"：

```ts
if (!significant) {
  verdict = '不显著，看不出效果'
} else if (broken.length > 0 && fixed.length > 0) {
  verdict = '★ 修好 N 个的同时弄坏了 M 个'   // ← 这句永远不会出现
}
```

为什么永远不出现：**换一批 bug 的净值恰恰很小**（修好 13 弄坏 10，净值 +3%），所以它总是落进"不显著"那一支。

于是最需要被看见的那种情况，被一句"不显著"盖掉了。

正确的顺序是**先看弄坏了多少，再谈显著性**。因为"弄坏了 10 个 case"是一件**确定发生了**的事，不需要统计检验来确认。显著性检验管的是那个净值，不是那两个列表。
</Pitfall>

<Pitfall title="只能比两边都有的 id">
少了哪一边就没法成对。

而"评测集换了一批样本之后跑分涨了"是最经典的自欺——尤其是当那批被换掉的样本恰好是不过的那些。
</Pitfall>

## 八、随机抽样会给你一个 90 分的废评测集

前面几节都在讲怎么正确地测。这一节开始讲**测什么**，而这里的坑更隐蔽。

假设你决定从生产日志里抽样来建评测集。这个思路是对的。但要注意生产日志的形状：

    一个还算健康的 agent，日志里 90% 以上是成功的正常路径。

于是随机抽 150 条，你会拿到 135 条正常路径和一把零星的失败。

<Pitfall title="问题不是「分数太高」">
这个评测集会给你一个 90 分以上的基线。

而它真正的问题不是分数高，是**任何改进都只能在剩下那 10% 里体现**。信噪比极差——你改动带来的效果，几乎全被那 135 条"怎么改都过"的样本稀释掉了。

而失败恰恰是你要评测的东西。
</Pitfall>

修法是分层抽样：按失败模式分层，每层取够数。这不复杂。真正需要设计的是**返回值**：

<Key>
分层抽样要返回三样东西，而**第三样最重要**：

- `picked` —— 抽出来的样本
- `coverage` —— 每个分层实际取到几条
- `gaps` —— **★ 没取够的分层**

`gaps` 为什么最重要：**"某个失败模式在评测集里一条都没有"这件事，不会以任何形式表现出来。**

你的评测会跑得很干净，分数会很好看，而那个失败模式在生产上继续发生。
</Key>

取到 0 条的分层要单独说一句——那不是"少了几条"，是"**这一类不存在**"。这两件事的处理方式不一样：少几条是统计功效问题，一条都没有是覆盖率问题。

## 九、评测集会腐化，而原因是你在正确地工作

最后一个失效模式，也是唯一一个**必然**发生的。

你照着评测集修 bug。修完之后那些 case 就永远通过了。于是：

- 可用的信息在**单调减少**
- 而总分在**单调上升**

半年之后你有一个 96 分的评测集，其中 90% 的条目对任何改动都不敏感。

<Key>
**那 96 分是真的，也是没用的。**

而这件事最坏的地方在于，它发生的原因正是你在正确地工作——你在照着评测集修 bug，这完全是该做的事。

所以它不会以"出了个问题"的形式出现。它就是正常工作的副产品。
</Key>

要定期把评测集按历史表现分三类：

- **还有区分度**（有时过有时不过）—— 这些才在提供信息
- **一直全对** —— 已经腐化，该换新的了
- **从来没过** —— 单独看，见下面

<Pitfall title="「从来没过」那几条可能是标注错了">
一个永远失败的 case 比一个永远成功的 case 更值得花五分钟人工确认。

因为如果它的期望答案标错了，它会让你**去修一个不存在的问题**——而且会一直让你修，因为它永远是红的。

这是评测集里唯一一类"会主动误导你去写代码"的条目。
</Pitfall>

而"持续给评测集补货"这件事，需要你能从生产流量里捞出有代表性的失败案例——这正是下一节（L13 可观测性）一半的用途。

## 十、门禁：五道闸，以及顺序为什么是故意的

把前面所有零件接起来，就是这一节要交出去的东西：一道会让 CI 变红的门。

而"会让 CI 变红"是关键。一个只输出报告的评测，三周之后就没人看了。门禁的价值在于它 **exit 非 0**。

门禁最难的部分不是判断逻辑，是**判什么才不会被绕过**：

| 闸 | 查什么 | 对应的绕过方式 |
|---|---|---|
| 一 | 基线样本有没有消失 | **删掉几条不过的样本** |
| 二 | judge 过不过体检 | 用一个偏的 judge 出分 |
| 三 | 有没有弄坏原本通过的 case | 只看净值 |
| 四 | 评测集还有没有区分度 | 拿一个已腐化的集出分 |
| 五 | 这一轮看了几个指标 | 多看几个指标直到有一个好看 |

<Key>
五道闸的顺序是故意的：**先查评测本身可不可信，再看跑分。**

因为一个坏了的评测会给出一个好看的分数。而如果你先看了分数，你已经有了立场，之后再去评估评测质量就很难客观了。

这是流程设计，不是技术设计。但它是这道门里最重要的一个决定。
</Key>

第一道闸值得单独说，因为它是最有效也最不引人注目的绕过方式：

<Pitfall title="删样本能让任何跑分变好看，而 diff 里看不出异常">
删掉几条一直不过的样本，跑分立刻上去。

而在代码审查里，那几行只是从一个 JSON 文件里消失了。没有任何东西看起来是坏的。

所以这一条要拦，而且要在报告里写清是哪几条 id 消失了。删样本本身是合理需求（判据过时了、标注错了），但它得**单独提 PR 并写明理由**，不能混在一个改 prompt 的改动里。
</Pitfall>

而最后一道闸是唯一一道你没法靠改代码通过的：

<Key>
它查的不是数据，是**你的行为**。

你改了一个 prompt，然后顺手看了：总成功率、三种任务各自的成功率、平均步数、P95 延迟、token 花费。

**那是 7 个比较。** 而在 α=0.05 下，"至少一个看起来显著"的概率是：

    P(至少一个假阳性) = 1 − (1 − α)^k

| 指标数 k | 至少一个假阳性的概率 |
|---|---|
| 1 | 5% |
| 5 | 23% |
| **7** | **30%** |
| 20 | 64%  ← 一次 A/B 面板上的指标数量级 |

也就是说你三次里有一次会"发现"一个不存在的改进——**而且你会觉得自己有数据支持。**
</Key>

Bonferroni 校正（把 α 除以 k）是补救办法。但更重要的建议是另一条：

<Key>
**事前声明唯一的主指标。**

校正是补救，而且它有代价——阈值被除以 k 之后，真实存在的改进也测不出来了（功效下降）。

事前声明主指标没有这个代价。其余指标当作探索性观察，不用来做决策。
</Key>

## 十条要点

1. **评测的难点不是打分，是不骗自己。** 一个错的评测比没有评测更糟，因为数字自带权威
2. **原始一致率会高估 33 到 41 个百分点**（21 个 judge 无一例外）。kappa 是主指标，raw 只能当辅助
3. **七成判据不需要 judge。** 而 judge 真正的代价是系统性错误、版本漂移、和慢
4. **五步体检里每一步只抓得住一种退化。** 一个 kappa 1.0、重测 1.0 的 judge 可以是"永远选排在前面那个"
5. **重测信度和位置偏见测的是两种不同的扰动。** 确定性在第二种上一分钱都不值
6. **`|P(A 赢) − 0.5|` 是错的**，它测的是内容分布。要看位置，而且 `位置偏见 ≤ 翻转率 / 2`
7. **150 条样本的置信区间宽 13 个百分点。** "涨了 2%"什么都不意味着
8. **净涨 2% 背后可能是换了一批 bug。** `fixed`/`broken` 两个列表比 delta 重要
9. **随机抽样会给你一个 90 分的废评测集。** 而 `gaps` 是分层抽样最重要的返回值
10. **评测集必然腐化，原因是你在正确地工作。** 它不会以"出问题"的形式出现

TODO 8「多重比较」**只在 Python 侧有**，而理由不是语言差异，是**工具链差异**：

多重比较校正的成熟实现在 `statsmodels.stats.multitest` 里（Bonferroni、Benjamini-Hochberg、Holm 都有），JS 生态没有等价物。同样地，bootstrap 在真实项目里该用 `scipy.stats.bootstrap` 而不是自己写循环。

这正是 L11x 第八节那个结论的具体化：

    agent 的运行时可以是 TypeScript，
    而评测和优化跑在 Python 里。

这一节的 Python 侧还有一个语言特有的坑，它非常适合出现在评测代码里：

```python
raw = sum(1 for j, h in zip(judge, human) if j == h) / n
```

`zip` 默认会在**短的那个耗尽时静默截断**。两组标签长度不一致时，你会算出一个看起来完全正常的数字，而它是错的。

修法是 `zip(judge, human, strict=True)`（3.10+），或者在函数开头显式检查长度。

★ 而这个坑的性质和这一节讲的所有东西一样：**它不抛异常，它给你一个数字。**
</PyMirror>
