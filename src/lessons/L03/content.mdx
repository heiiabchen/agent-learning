L02 结束时你手上有两个模块：账本和流式读取器。基础设施齐了，可以开始教模型干活了。

这一节讲 prompt。但不是「十个让 AI 听话的咒语」那种——那些东西的问题不是不管用，是**你不知道它为什么管用，所以也不知道它什么时候会失效**。

<Key>
Agent 的 prompt 和聊天的 prompt 是两种东西。聊天的 prompt 追求「这次答得好」，agent 的 prompt 追求「一万次里有九千九百次结构正确」。前者可以靠感觉调，后者必须靠**约束**——你要减少的不是错误率，是**方差**。
</Key>

## 一、先把「prompt 工程」这个词拆开

你在 Cursor 里写需求的时候，其实一直在做两件不同的事，只是没分开：

| | 你在做什么 | 失败长什么样 |
|---|---|---|
| **写指令** | 告诉模型要什么 | 它做了别的事 |
| **给上下文** | 告诉模型现状 | 它做对了，但基于错的前提 |

这两件事的优化方向完全相反。指令要**短、硬、可验证**；上下文要**准、全、可追溯**。把它们混在一坨自然语言里，是新手 prompt 最典型的形态，也是最难调试的形态——出问题时你不知道该改哪一半。

所以第一条纪律，在你写任何 prompt 之前：**把指令和数据在结构上分开。**

L02 已经给了你第一层分离（system 放不变的，messages 放变的）。这一节做第二层：在一条消息**内部**继续分。

## 二、结构化：为什么 XML 标签打得过自然语言

先看一个真实的对比。同一个任务，两种写法。

自然语言版：

```text
请你审查下面这段代码，找出其中的 bug，然后给出修改建议。
代码是：function add(a, b) { return a - b }
注意只关注逻辑错误，不要提风格问题。
```

结构化版：

```text
<task>审查代码，找出逻辑错误</task>

<constraints>
- 只报逻辑错误，不报风格问题
- 每个问题给出行号
</constraints>

<code>
function add(a, b) { return a - b }
</code>
```

第二种更好，但**理由不是「看起来更整齐」**。三个具体的机制：

**一，边界消歧。** 第一种写法里，「代码是：」之后到哪里结束？如果用户提交的代码里恰好有一行注释写着「注意只关注逻辑错误」，模型分不清那是指令还是数据。标签给了明确的闭合边界。这不是理论问题——**这正是 prompt 注入的基本原理**（L14 的主题）。

**二，可寻址。** 结构化之后，你的代码可以精确地操作某一段。「把 constraints 换掉」是一个字符串替换，「把那句关于风格的话换掉」是一次祈祷。**agent 的 prompt 是要被程序拼装的，不是被人手写的**，能寻址就能测试。

**三，训练分布。** Anthropic 的模型在训练数据里见过大量 XML 风格的结构化输入（他们的官方文档从头到尾都在推荐这个）。这不是玄学，是**你在往模型熟悉的模式上靠**。

<Note title="为什么是 XML 而不是 JSON">

给模型看的结构，和给程序看的结构，最优解不一样。

JSON 要求严格转义。你的输入里有一个引号、一个反斜杠、一个换行，就得转义——而**代码里全是这些东西**。把一个 TypeScript 文件塞进 JSON 字符串，模型看到的是 `\"const x = 1\\n\"` 这种东西，可读性大幅下降，token 也变多了。

XML 标签不要求转义内容。`<code>` 到 `</code>` 之间原样放，模型看到的就是代码本来的样子。

反过来，模型**输出**要给程序解析时，JSON 更好——因为你有现成的 parser 和 schema 校验。

一句话：**输入用标签，输出用 JSON。** 这两个方向的约束不同，别用同一套。

</Note>

<CursorHook>

你在 Cursor 里贴代码的时候，Cursor 并不是把你的文字和代码简单拼在一起发出去。它会把文件内容包进带路径的结构里，大致是这个意思：

```text
<file path="src/utils.ts">
...文件内容...
</file>
```

这解释了一个你可能有过的体验：**直接把代码粘进聊天框，效果通常不如用 @ 引用文件。** 不只是因为 @ 引用能带上更多上下文，还因为它走的是结构化通道——模型清楚地知道哪里是文件、文件叫什么名字、边界在哪。你手动粘贴的那一段，在结构上和你的问题是同一坨东西。

同理，`.cursor/rules` 里那些规则之所以比在聊天里说一遍更稳，一半原因是 L02 讲的 system 位置，另一半就是它有稳定的结构位置。

</CursorHook>

## 三、Agent prompt 的六个部件

这是我实际在用的骨架。不是唯一正确的，但每一段都有存在理由，你可以照着改。

```text
<role>
你是一个代码库维护助手，在真实仓库上工作。
</role>

<capabilities>
你可以使用工具读文件、列目录、运行测试。
你没有网络访问，也不能安装依赖。
</capabilities>

<rules>
1. 修改任何文件之前，必须先读它。
2. 不确定的时候，用工具查证，不要猜。
3. 一次只改一个文件。
4. 改完必须跑测试。
</rules>

<output_format>
每一步先说你要做什么，再调用工具。
最终答案包在 <answer> 标签里。
</output_format>

<examples>
（一到两个完整的正确示例）
</examples>

<context>
（这次任务相关的动态信息）
</context>
```

前五段放 system（不变，可缓存），最后一段放 messages（变）。这个划分就是 L02 那条「不变的往前放」的具体落地。

四段值得单独说：

**`<capabilities>` 里要写「不能做什么」。** 这是新手最常漏的一段，而它解决的是一个具体的失败模式：**模型会编造它没有的能力**。你没告诉它不能上网，它就会说「我去查一下最新文档」然后编一段出来。L04 会看到这个现象的工具版本——模型调用一个不存在的工具。

**`<rules>` 要可验证。** 对比这两条：

```text
✗ 请仔细处理错误情况
✓ 每个 catch 块必须记录 error.message 和当前操作名
```

第一条你没法判断模型有没有遵守，所以也没法测。**写不出检查方法的规则，等于没写。** 这条判据在 L12 会变成 evals 的基本功。

**规则用编号列表，不用段落。** 编号让你能在日志里引用「违反了规则 3」，也让你能在 eval 里逐条统计违反率。散文体的规则没法做这件事。

**`<output_format>` 决定了你的解析器能不能写。** 想清楚再写——这一段变，你下游的所有代码都要变。

<Pitfall title="别写「不要」，写「要」">

这条有实证依据，而且原因和 L01 讲的机制直接相关。

模型在生成时是在预测下一个 token。当 prompt 里出现「不要输出 markdown」时，`markdown` 这个概念被激活了——它进入了上下文，提高了相关 token 的概率。你在试图压制它，但**你首先把它请进来了**。

所以：

```text
✗ 不要用 markdown 格式，不要加代码块，不要写解释
✓ 输出一行纯文本，内容是文件路径
```

第二种更短、更明确、而且没有把你想避免的东西写进去。

例外：**当「不要做的事」是一个具体的、反复出现的错误行为时，明确禁止是有效的**，因为这时候你需要的正是让模型注意到这个具体行为。判据是：能不能改写成一条正向的指令？能就改写，不能就明确禁止，但要写得具体（「不要在 src/ 之外创建文件」这种可验证的禁止是好的）。

</Pitfall>

## 四、few-shot：最被高估也最被低估的技术

被高估的部分：很多人以为 few-shot 是「给模型看几个例子让它学会做这件事」。不是。模型早就会做这件事了，它是在预训练里学的。

被低估的部分：few-shot 真正在做的是**指定输出的形状**。

<Drill title="few-shot 到底在模型内部做了什么">

从机制上说，few-shot 不是「学习」——模型的权重一个都没变。它是**条件化**（conditioning）。

回想 L01 的核心：模型算的是 `P(下一个 token | 前面所有 token)`。当前面的 token 里有三个「输入 → 输出」的样例时，「输出的格式长这样」变成了上下文里的一个强信号。模型不需要理解你的意图，它只需要**接着这个模式往下续写**。

这解释了三个可观察的现象：

**一，例子的格式比例子的内容更重要。** 如果你的三个例子都以 `- ` 开头，第四个输出几乎必然以 `- ` 开头。你在无意中规定了格式。

**二，例子里的错误会被忠实复制。** 你的例子里有个 typo、日期格式不一致、某个字段偶尔省略——模型会把这些当成模式的一部分。**few-shot 的例子必须是你能拿出手的最干净的版本**，因为它是规范，不是参考。

**三，例子的分布决定输出的分布。** 三个例子全是「有问题」的样例，模型倾向于在第四个也报问题——哪怕它没问题。这叫**样例偏置**，处理方法是让例子覆盖各种情况，**包括「什么都不用做」的情况**。

第三条是实战里最容易踩的。一个只见过「发现 bug」样例的审查 agent，会开始编造 bug。

</Drill>

所以 few-shot 的实操规则：

1. **两到三个就够。** 边际收益掉得很快，而每个例子都是每轮都付的输入成本（L02 的账本会告诉你具体多少钱）。
2. **必须包含边界情况。** 特别是「正常」「无需处理」这一类，否则模型学到「总是要做点什么」。
3. **格式绝对一致。** 你希望输出稳定，就不能让例子的格式有方差。
4. **放 system 里。** 它不变，它应该被缓存。

## 五、Prefill：把输出的开头替你写掉

这是 Anthropic 协议里一个很有用的技巧，L02 的探测里你已经见过它了。

原理：`messages` 数组最后一条如果是 `assistant`，模型会**接着这句往下写**，而不是重新开始。

```ts
messages: [
  { role: 'user', content: '把这段代码的问题列出来' },
  { role: 'assistant', content: '{"issues": [' },   // ← prefill
]
```

模型只能接着 `{"issues": [` 往下写，于是它没法先来一段「好的，我来帮你分析这段代码」。**你用结构堵住了它的废话。**

三个实用场景：

| 场景 | prefill 内容 | 效果 |
|---|---|---|
| 强制 JSON | `{` | 不会有前后的解释文字 |
| 强制标签结构 | `<answer>` | 配合 `stop_sequences: ['</answer>']` 干净截断 |
| 跳过客套 | `分析结果：` | 直接进正文 |

<Pitfall title="但在你的端点上，prefill 不是真的 prefill">

L02 的 `anatomy` 探测已经查出来了：DeepSeek 兼容端点上，prefill 的内容会被**重新说一遍**。

我给的是 `1. 苹果\n2.`，官方端点会只返回续写部分，这个端点返回的是完整的 `1. 苹果\n2. 香蕉\n3. 橙子`。

所以在这个端点上，你不能直接 `prefill + response` 拼接，那样会得到重复内容。可行的做法有两条：

**一，不拼接，只把 prefill 当「格式提示」用。** 你依然获得了「输出以 `{` 开头」的效果，只是解析时以返回内容为准，不做拼接。这是我推荐的做法——它在两种端点上行为一致。

**二，检测并去重。** 如果返回内容以 prefill 开头就切掉。能用，但它是一个**依赖端点行为的补丁**，换端点就要重新验证。

这件事本身比这个技巧更值得记住：**任何依赖端点具体行为的技巧，都要有一个「换端点会怎样」的答案。** 你手上那张 L02 跑出来的差异表，就是干这个用的。

</Pitfall>

## 六、思维链：它不是免费的

「让我们一步一步思考」这句话现在几乎成了民间信仰。它确实有效，但代价被系统性地忽略了。

<Drill title="CoT 为什么有效，以及它到底花了什么">

L01 讲过：模型每次前向传播的计算量是固定的。一个 token 的思考深度有上限。

思维链绕过这个限制的方式很朴素——**把中间结果写出来，变成下一步的输入**。写出来的 token 进入上下文，下一步就能 attend 到它。等于用**序列长度**换**计算深度**。

这就解释了代价：

**一，输出 token 直接变多。** L02 那条延迟公式：总时长 ≈ TTFT + 输出 token × TPOT。CoT 让输出翻几倍，延迟就翻几倍。而且输出是最贵的那一档单价。

**二，它占的是 `max_tokens` 的额度。** L02 那个坑你已经踩过了：思考吃光预算，正文一个字都没写出来。

**三，中间步骤会污染最终答案。** 模型写下一个错误的中间结论后，这个结论进了上下文，后面的推理会**基于它继续**。CoT 放大了早期错误——它不只是没帮上忙，是主动把错误传播下去。

所以现代模型（包括你在用的 DeepSeek V4）把思考放进独立的 `thinking` 块，而不是混在正文里。这不只是为了显示好看：**它让思考内容可以被单独丢弃，不进入下一轮的历史**。

</Drill>

实操上的三条：

1. **模型自带思考模式的话，别再手写「一步一步思考」。** V4 默认开着，你那句话只是在已经思考的基础上再要一段废话。
2. **简单任务显式关掉或压缩思考。** 「提取这个 JSON 里的 id 字段」不需要思考，思考只是在烧钱和时间。
3. **agent loop 里尤其要控制。** 十步任务，每步都长篇思考，总输出会失控。L05 会给出具体的控制手段。

<Note title="一个反直觉的结论">

**在 agent 里，「让模型思考」经常不如「让模型查证」。**

CoT 是让模型在自己的参数里做更多推理。但 agent 有工具——它可以去读文件、跑测试、查真实状态。

一次工具调用得到的是**事实**，一段思考得到的是**推测**。当你能用工具的时候，用工具。这也是为什么 L04 的工具设计比 prompt 技巧更重要：**能让模型闭嘴去查的地方，就不要让它想。**

</Note>

## 七、把 prompt 当代码管

这是这节课最重要的一段，也是区分「会写 prompt」和「会做 agent」的地方。

prompt 是你系统里**唯一没有类型检查、没有版本控制习惯、没有测试的核心逻辑**。这不合理。

四条纪律：

**一，prompt 是文件，不是字符串字面量。** 别把它埋在 `.ts` 文件的模板字符串里。单独放，可以 diff、可以 review、可以在不重新部署代码的情况下改。

**二，拼装要有类型。** 把可变的部分做成明确的参数：

```ts
interface AgentPromptVars {
  cwd: string
  tools: string[]
  maxSteps: number
}
```

这样漏参数是编译错误，而不是 prompt 里留一个字面量 `{cwd}`。**没渲染的模板变量是最尴尬的一类 bug**——它不报错，模型只是收到一句它看不懂的话，然后表现变差。

**三，改动要有记录。** 一个 prompt 从 v1 改到 v2，效果变好了还是变差了？没有版本和测量，你就是在随机漫步。L12 会把这件事做成 eval 流程。

**四，稳定的部分和动态的部分物理分开。** 这既是缓存要求（L02），也是可测试性要求：动态部分能被换成固定的测试数据。

<Lab title="本节的三个任务">

```bash
# TypeScript 主通道
pnpm prompt         # 任务一：可测试的 prompt 模板
pnpm variance       # 任务二：测方差，不是测「好不好」
pnpm structured     # 任务三：让模型稳定输出可解析的 JSON
pnpm verify:l03     # 验证

# Python 副通道
uv run python -m l03.prompt
uv run python -m l03.variance
uv run python -m l03.structured
uv run python -m l03.verify
```

任务二是这节课的重点，也是和「背咒语」区别最大的地方：**同一个 prompt 跑二十次，看输出的方差**。你会得到一个数字，而不是一个感觉。

先跑 `VERIFY_TARGET=shared` 确认尺子是准的，还记得吧。

</Lab>

<PyMirror>

这一节的 Python 对照有一处特别值得看，因为它是「标准库看起来刚好合适，但不能用」的一个干净例子。

Python 自带 `str.format`，占位符语法恰好就是 `{name}`，而且缺 key 时会抛 `KeyError`——正好是我们要的「漏传要响」。对比 TS：模板字符串里漏一个变量，你会静默得到字符串 `undefined`。**这一局 Python 明显更好。**

但它不能用，原因是一个具体的冲突：

```python
tmpl = '<output_format>形状：{"task": string}</output_format>'
tmpl.format(cwd="/repo")
# KeyError: '"task"'
```

`str.format` 把模板里**所有**花括号都当占位符。而 `<output_format>` 段里几乎一定有 JSON 形状说明。要用它就得把这些花括号全写成 `{{` 和 `}}`，于是你的 prompt 源文件和实际发给模型的内容不再长得一样——**review 的时候看到的是转义后的版本**，这在 prompt 上是很糟的一件事，因为 prompt 的正确性全靠人读。

所以两边都用了一条收紧过的正则。有意思的是这个冲突和 TS 那边 `assertRendered` 的误报是**同一个根源**：JSON 形状说明里的花括号，和模板占位符长得一样。我第一版的正则就把它当成未渲染的占位符给拦下来了，verify 里那条 `JSON 样例里的花括号不该被误判` 就是这么来的。

真实项目里 Python 侧的事实标准是 **Jinja2**，它的强项是循环和条件（拼「有 N 条规则」的段落比 `.map().join()` 干净）。但它有一个同类的坑，而且更隐蔽：**默认对 HTML 转义**。你的 prompt 里全是 `<tag>`，忘记关转义的表现是模型收到 `&lt;rules&gt;` 然后完全看不懂你的结构。L11x 会讲 LangChain 的模板层里这个坑的对应版本。

一句话收：**模板引擎的转义规则是为 HTML 设计的，prompt 不是 HTML。** 每次引入一个模板工具，先问它拿花括号和尖括号怎么办。

</PyMirror>

## 八、这节课的纪律

1. **指令和数据在结构上分开。** 用标签，不用「以下是：」。
2. **规则必须可验证。** 写不出检查方法的规则等于没写。
3. **few-shot 的例子是规范，不是参考。** 包括「无需处理」的样例。
4. **prompt 是代码。** 单独成文件、参数有类型、改动有记录。
5. **能查证就别推理。** 工具给事实，思考给推测。

下一节让模型伸出手。你会发现 L03 这些结构纪律在工具的 schema 设计上原封不动地再来一遍——**工具描述就是 prompt，只是它长在 JSON Schema 里。**
