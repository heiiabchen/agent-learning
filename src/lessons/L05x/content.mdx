这一节是选修。跳过它你照样能写出能用的 agent——L05 已经证明了。

但读完它，你能回答一切「为什么模型会这样」的问题。这在面试里是分水岭：**知道现象的人很多，能解释机制的人少。** 而在工程上，它让你的猜测变成推理。

<Key>
这一节唯一的目标：把一次推理从输入文本走到输出 token，中间不留黑盒。走完之后，L01 到 L05 那些「记住这个规律」的地方，你会看到它们是同一套机制的不同侧面。
</Key>

## 一、文本 → 数字：嵌入

L01 讲过分词：文本被切成 token id。现在这些 id 要变成向量。

```text
"上下文"  →  [12844, 3129]  →  两个向量，各 d 维（d 通常几千）
```

这一步就是一张查找表：`embedding[token_id]` 直接取一行。没有计算，只有索引。

<Drill title="为什么嵌入维度这么大">

d 通常是 4096 或更大。为什么不是 100？

因为这个向量要编码的东西非常多：这个 token 的语法角色、语义、常见搭配、在多语言里的对应关系、它是词首还是词中……**所有这些信息要挤在同一个向量里。**

高维空间有一个反直觉但关键的性质：**它非常"宽敞"**。在 4096 维里，你可以找到远超 4096 个互相近似正交的方向。这意味着不同的语义特征可以各占一个近乎独立的方向，互不干扰。维度低了就装不下，特征会互相纠缠。

这也顺便解释了一件实际的事：**为什么词表大小和模型能力关系不大，但嵌入维度关系很大。** 词表决定切多细，维度决定每个 token 能携带多少信息。

</Drill>

## 二、位置：模型怎么知道谁在前面

到这里有个问题：`[12844, 3129]` 和 `[3129, 12844]` 的嵌入集合完全一样。attention 本身是**置换不变**的——它看不出顺序。

而顺序显然重要。「猫追狗」和「狗追猫」不是一回事。

解法叫位置编码。现代模型主流用 **RoPE**（旋转位置编码），思路是：**把位置信息编码成向量的旋转角度。**

不用懂数学也能抓住关键性质：RoPE 让两个 token 之间的 attention 强度**只依赖它们的相对距离**，不依赖绝对位置。第 5 和第 7 个 token 的关系，与第 1005 和第 1007 个 token 的关系，在形式上是一样的。

<Note title="这解释了两件你可能遇到过的事">

**一，为什么模型能处理比训练时更长的上下文，但会变差。**

相对位置的形式在任何长度下都成立，所以模型"能"处理没见过的长度。但它没在那些距离上训练过——旋转角度进入了陌生的区域，表现下降。

这就是所谓的长度外推问题。各种「把 4K 模型扩到 32K」的技术（位置插值之类）本质上都是在**压缩旋转角度**，让长距离看起来像模型熟悉的短距离。代价是分辨率下降：相邻位置的区分变模糊了。

**二，为什么「把重要信息放在开头或结尾」有效。**

这个建议流传很广，但通常没人说为什么。一部分原因在这里：训练数据里，开头和结尾的位置模式最一致（文档总有开头，指令常在结尾）。中间位置的模式最杂。

另一部分原因在下一节的 attention 稀释。**「lost in the middle」不是一个 bug，是两个机制叠加的结果。**

</Note>

## 三、Attention：整个架构的核心

现在每个 token 有了一个带位置信息的向量。attention 要做的事是：**让每个 token 去看其他 token，按相关性加权地吸收信息。**

三个矩阵变换，把每个 token 的向量投影成三个新向量：

| | 直觉 | 类比 |
|---|---|---|
| **Q**（query） | 我在找什么 | 搜索框里输入的词 |
| **K**（key） | 我能提供什么 | 每篇文档的标题 |
| **V**（value） | 我实际的内容 | 文档正文 |

然后：

```text
score(i, j) = Q_i · K_j / √d        ← i 对 j 的关注度
weights = softmax(scores)            ← 归一化成和为 1
output_i = Σ_j weights(i,j) × V_j   ← 按权重取内容
```

<Drill title="softmax 归一化：注意力是零和的">

`softmax` 让权重加起来等于 1。这个约束是整个 L06 上下文工程的**数学根源**，值得盯一会儿。

一个 token 的注意力总量是固定的 1。它多看一个地方，就必须少看别的地方。**这是严格的零和。**

具体化一下。假设你的 prompt 里有一条关键指令，上下文里还有 100 个别的 token：

- 上下文总长 200 时，那条指令平均能分到 1/200 的注意力
- 上下文总长 20000 时，它平均只能分到 1/20000

**指令一个字都没变，但它的"声音"小了一百倍。**

这就是 L01 说的「长上下文让模型变笨」的确切机制。不是模型累了，是注意力被稀释了。

三个直接的工程推论：

1. **上下文里放无关内容有真实代价**，不只是 token 费用。它在抢注意力。
2. **重复关键指令是有效的**——重复给它多个分配点，总权重更高。这解释了为什么很多生产 prompt 会在开头和结尾各说一遍。
3. **上下文压缩不只是省钱，是提升准确率。** L06 会看到具体的效果。

</Drill>

## 四、O(n²)：所有长上下文问题的根源

看 `score(i, j)`：每个 token 对每个 token 都要算一次。n 个 token 就是 n² 个分数。

这个平方是**架构层面的**，不是实现不够优化：

| 上下文长度 | attention 分数个数 | 相对 1K |
|---|---|---|
| 1K | 100 万 | 1× |
| 8K | 6400 万 | 64× |
| 32K | 10 亿 | 1024× |
| 128K | 164 亿 | 16384× |

这一张表解释了一长串现象：

- **为什么长上下文贵。** 不只是 token 多，是每个 token 的处理成本也在涨。
- **为什么 TTFT 随输入长度超线性增长。** L02 那个「首字延迟主要由输入长度决定」的观察，根源在这。
- **为什么上下文窗口的扩张这么慢。** 从 4K 到 200K 花了几年，因为代价是平方级的。
- **为什么 FlashAttention 这类工作影响巨大。** 它们优化的是**内存访问**而不是计算量——把中间结果不落地，从 O(n²) 内存降到 O(n)。计算量没变，但内存墙被推开了。

<Note title="面试常问：能不能突破 O(n²)">

能，但都有代价，而且代价的位置很一致。三类主流思路：

**稀疏 attention**——只让每个 token 看一部分（滑动窗口、跳跃、少量全局 token）。代价是**有些远距离依赖看不到了**。

**线性 attention / 状态空间模型**（Mamba 这一族）——用一个固定大小的状态压缩历史，复杂度降到 O(n)。代价是**状态容量固定**，历史长了必然有损。

**分层 / 检索式**——把长上下文放外面，按需检索一小部分进来。代价是**检索错了就完全看不到**。而这正是 L09 要讲的 RAG。

一句话总结这三类的共性：**它们都在用"选择性遗忘"换复杂度。** 完整的全对全注意力就是 O(n²)，这没有免费的绕法。

顺便：**你在 L06 做的上下文压缩，本质上是同一件事的手工版本。** 你在替模型决定忘掉什么。区别只是你用的是业务知识，而它们用的是架构。

</Note>

## 五、KV Cache：为什么第二个 token 比第一个快得多

生成是自回归的：一次一个 token，每个新 token 都要重新跑一遍网络。

朴素做法：生成第 n 个 token 时，把前 n-1 个全部重新算一遍。总成本 O(n³)，完全不可行。

关键观察：**前面那些 token 的 K 和 V 不会变。** 第 3 个 token 的 K 和 V，在生成第 4、5、100 个 token 时都是同一个值。

所以缓存它们。这就是 KV cache。

```text
第 1 步：算 token 1 的 K/V，存起来
第 2 步：只算 token 2 的 K/V，和缓存里的拼起来
第 n 步：只算 token n 的 K/V
```

于是每步的增量成本从 O(n) 降到 O(1)（相对于重算）。这是让自回归生成可行的关键工程。

<Drill title="KV cache 解释了三件你已经知道的事">

**一，TTFT 和 TPOT 为什么差那么多（L02）。**

TTFT 要做 **prefill**：一次性处理整个输入，建立 KV cache。这一步是 O(n²) 的并行计算。

TPOT 是 **decode**：每个 token 只做一次 O(n) 的增量计算，但要**串行**做。

两个阶段的瓶颈完全不同：prefill 受**算力**限制，decode 受**内存带宽**限制（每步都要把整个 KV cache 读一遍）。这也是为什么批处理能大幅提升吞吐——多个请求共享同一次内存读取。

**二，prompt 缓存为什么能省 50 倍（L02）。**

「prompt 缓存」就是**把 prefill 阶段算出的 KV cache 存下来复用**。你以为它是在省重复的输入 token 费，其实它省的是重算 KV 的算力。

这也解释了那个**前缀必须逐 token 一致**的严格要求：KV cache 是按位置累积的，第 k 个位置的 K/V 依赖前 k-1 个。中间改一个 token，从那里往后全部作废。

**不是"差不多就行"，是从第一个差异点开始全废。** L03 那道改错题里放在第二行的时间戳，毁掉的正是它后面的全部缓存。

**三，长上下文为什么吃显存。**

KV cache 的大小 = 层数 × 头数 × 序列长度 × 每头维度 × 2（K 和 V）× 精度字节数。

对一个中等模型，128K 上下文的 KV cache 可以是几十 GB——**比模型权重本身还大**。

这解释了服务端的真实约束：并发数受 KV cache 显存限制，而不受算力限制。你的长上下文请求挤占的是别人的并发额度，所以长上下文的定价往往不是线性的。

</Drill>

## 六、Logits → Token：随机性从哪来

网络最后一层输出一个长度等于词表大小的向量，叫 **logits**。每个位置对应一个 token 的"原始分数"。

```text
logits = [..., 2.3, -1.1, 5.7, 0.4, ...]   ← 长度 = 词表大小（十万量级）
```

四步变成一个 token：

**一，温度缩放。** `logits / T`

- `T < 1`：差距放大，高分的更高 → 更确定
- `T > 1`：差距压缩 → 更随机
- `T = 0`：退化成直接取最大值（argmax）

**二，softmax。** 变成概率分布。

**三，截断。** `top_p`（累积概率到 p 为止）或 `top_k`（前 k 个）。**这一步是在删除长尾。**

**四，采样。** 按剩下的概率随机抽一个。

<Drill title="为什么 temperature=0 还是不完全确定（L01 那个坑）">

L01 说过这个现象，现在可以给出确切原因。`T=0` 时是 argmax，理论上完全确定。实际不是，有三个原因，全是工程性的：

**一，浮点加法不满足结合律。**

`(a + b) + c ≠ a + (b + c)`，在浮点数里这是事实而非近似。GPU 上矩阵乘法的求和顺序取决于**线程调度和 kernel 选择**，而这些会随批次大小变化。

于是不同的求和顺序给出略微不同的 logits。绝大多数时候不影响 argmax，但当前两名分数极接近时，`5.7000001` 和 `5.7000002` 的顺序可能翻转。**一个 token 翻转，后面整段就分叉了。**

**二，批处理组成会变。**

你的请求和谁一起被批处理，影响 kernel 选择和归约顺序。而这取决于同一时刻别人在发什么请求——**你完全无法控制**。

**三，MoE 模型的路由。**

混合专家模型要为每个 token 选专家。批次内的负载均衡会影响路由决策，同一个 token 在不同批次里可能走不同的专家。**这个偏差比浮点误差大得多。**

而 DeepSeek V4 就是 MoE 架构。

所以那条纪律的准确表述是：**`temperature: 0` 给的是"低方差"，不是"可复现"。** 需要真正的可复现性时，唯一可靠的手段是**缓存输出**——把 (输入 → 输出) 存下来。这也是 L12 做 evals 时必须固定的东西：如果你的 eval 依赖模型每次给同样的答案，那它测的是运气。

</Drill>

<Note title="约束解码：把「格式一定对」变成硬保证">

L03 讲过用 prompt 和 prefill 提高 JSON 输出的可解析率。**约束解码能把它变成 100%。**

机制是在采样这一步介入：根据 JSON 语法（或者你的 JSON Schema），算出当前位置**哪些 token 是合法的**，把其余的 logits 全设成负无穷。于是非法 token 的概率是 0，不是"很小"。

代价有三个，都值得知道：

1. **需要服务端支持。** 这在采样层，客户端做不到。OpenAI 的 structured output、各种本地推理框架（vLLM、llama.cpp）都提供，但很多兼容端点没有。
2. **可能降低内容质量。** 强行禁止某些 token 会把模型推向它本来不倾向的路径。语法一定对，语义可能变差。
3. **schema 越复杂，开销越大。** 每一步都要算合法集合。

判断顺序：**能用约束解码就用**（格式问题彻底消失）；不能用就 prompt + prefill + 健壮的解析器（你在 L03 写的那个 `extractJson`）。

这也是为什么 L03 那个练习值得做：**在没有硬保证的环境里，你的容错解析器就是那道防线。**

</Note>

## 七、把整条链串起来

```text
文本
 ↓ 分词（BPE）                    ← L01：CJK 更耗 token
token id
 ↓ 嵌入查表
向量
 ↓ RoPE 位置编码                  ← 长度外推的来源
带位置的向量
 ↓ ┌─ N 层 ────────────────────┐
   │ attention（Q·K/√d, softmax）│  ← O(n²)，注意力零和 → L06
   │   ↑ KV cache               │  ← prompt 缓存 → L02 的 50 倍
   │ FFN                        │
   └────────────────────────────┘
logits（词表长度）
 ↓ /T → softmax → top_p → 采样    ← 非确定性的来源 → L01
下一个 token
 ↓ 拼回输入，重复
```

现在回头看这门课前面立的那些纪律，它们都落到了这张图上：

| 纪律 | 出处 | 机制根源 |
|---|---|---|
| CJK 更耗 token | L01 | BPE 在英文语料上训练 |
| 长上下文让模型变笨 | L01 | softmax 归一化，注意力零和 |
| `T=0` 也不可复现 | L01 | 浮点归约顺序 + MoE 路由 |
| 缓存前缀必须逐 token 一致 | L02 | KV cache 按位置累积 |
| 输入长度主导 TTFT | L02 | prefill 是 O(n²) |
| 重复关键指令有效 | L03 | 多个注意力分配点 |
| 工具输出必须裁剪 | L04 | 每轮重发 + 注意力稀释 |
| 上下文压缩是必需的 | L06 | O(n²) + 零和注意力 |

</Lab>

<PyMirror>

这一节的 Python 对照不是「翻译一遍」，而是**同一段逻辑在两种语言里的表达差距**。

TS 版算 attention 分数：

```ts
for (let i = 0; i < n; i++) {
  for (let j = 0; j <= i; j++) {
    let dot = 0
    for (let d = 0; d < dim; d++) dot += Q[i][d] * K[j][d]
    scores[i][j] = dot / Math.sqrt(dim)
  }
}
```

Python 版：

```python
scores = (Q @ K.T) / np.sqrt(dim)
scores = np.where(mask, scores, -np.inf)     # 因果掩码
```

两行。而且**第二行那个掩码是 TS 版容易漏掉的东西**——因果掩码（每个位置只能看到自己和之前的）在三重循环里是 `j <= i` 那个条件，藏在控制流里；在 numpy 里它是一个显式的对象，你能打印它、检查它。

这个差距解释了为什么整个 ML 生态在 Python 上：**不是 Python 快，是它让向量运算的意图可见。** 而当你的代码在表达数学时，意图可见比执行快重要——真正的计算反正在 C/CUDA 里。

顺带一个你会在真实代码里反复见到的记号：einsum。

```python
scores = np.einsum('id,jd->ij', Q, K) / np.sqrt(dim)
```

`'id,jd->ij'` 读作「Q 的 i 和 d 维、K 的 j 和 d 维，对 d 求和，输出 i×j」。第一次看很怪，但它是 attention 实现里的通用语——**因为多头 attention 有四五个维度，靠 transpose 和 reshape 排列组合非常容易出错，而 einsum 把维度用名字标出来了。** 读得懂它，你就读得懂大部分开源模型的 attention 代码。

</PyMirror>
