L11x 是 Python 为主、TS 对照的那一节：读懂 LangGraph 和 DSPy，判断哪些设计该抄。这一节反过来，TS 是主通道，Python 只观测。问题也换了。前十几节你已经手写过停止原因、错误回填、幂等键、审批记忆、事件日志和 tracing，这一节把它们一件件对到主流 TS 框架里，回答三件事：框架替你写了哪一段，哪些默认值会咬人，你的不变量接在哪个扩展点上。

先看一组数。同一个永远失败的工具，配一个每次都重试的模型，在七个入口的默认值下各跑一遍（`pnpm eco19` 的实验一）：

```text
入口                      默认上限  模型/工具  证据        结束方式
ai-sdk/generateText       1         1/1        E1-B 实测   返回：finishReason=tool-calls，text 为空
ai-sdk/ToolLoopAgent      20        20/20      E1-A 实测   返回：finishReason=tool-calls，text 为空
ai-sdk/WorkflowAgent      无        50/50      文档        没有上限，第 50 次被外部掐断
mastra/Agent.generate     5         5/5        E3 实测     返回：finishReason=tool-calls
openai-agents/run         10        10/10      E6-A 实测   抛：MaxTurnsExceededError（error.state 还在）
claude-agent-sdk/query    无        50/50      E5-A 实测   没有上限，第 50 次被外部掐断
langgraph.js              25        25/25      源码常量    抛：GraphRecursionError
```

**从 1 到无穷大**，撞上限之后有三种结局：正常返回、抛异常、根本不停。「框架会帮我兜住死循环」这个直觉成不成立，取决于你用的是哪一家，以及同一家的哪个入口。

<Key>

这一节的中心论点：**框架真正省下的是四样脏活**，即 provider 适配、流协议编解码、schema 校验、会话序列化。承重的五处（终止、错误回填、幂等、tracing、审批），四家框架没有一家的默认值满足课程的不变量；「L08 幂等键」那一行，四家全空。

所以选型题的答案不是「用哪个框架」，而是拿它的 provider 层，把你在 L05–L19 写过的不变量写成**适配器**，接到它开放的扩展点上。lab 的六个 TODO 就是六个适配器：接在 `stopWhen` 上的停止原因，`execute` 包装和 `errorFunction` 共用的错误出口，只消费一次的审批恢复，MCP 结果到文本的转换，以服务端日志为准的历史重建，以及把一份 Dify DSL 读成代码计划。

</Key>

## 三、终止：默认步数从 1 到无穷大

### 3.1 三种停法，同一个 finishReason

L05 的不变量是终止时必须返回为什么停（`AgentRun.reason`）。AI SDK 的返回值里只有**最后一步**的 `finishReason`，取值是 `stop`、`length`、`content-filter`、`tool-calls`、`error`、`other`。撞上步数上限时，最后一步是 `tool-calls`；停在审批请求上、调了一个没有 `execute` 的工具，也都是 `tool-calls`（E1-A、E1-E 实测）。撞默认上限时，唯一的信号是一条 warning：

> "The tool loop stopped because it reached the default stopWhen condition, isStepCount(20). To allow more steps, set stopWhen to isStepCount(...) with a higher limit or provide a custom stop condition."

L05 第一节的 Pitfall 说：「撞上步数上限时，你返回的是模型最后一次说的话——那句话看起来像一个答案。」在 AI SDK 里更糟，`text` 直接是空串。而裸 `generateText` 带工具时默认 `isStepCount(1)`，执行完第一次工具调用就返回（E1-B：1 次调用、1 次执行、`text` 为空）。从 `generateText({ tools })` 起步的人，第一天看到的就是「工具执行了，但是没有回答」。

另外三家：

- **Mastra** 的 `Agent.generate` 默认 5 步，正常返回，`finishReason` 同样是 `tool-calls`（E3）
- **OpenAI Agents SDK** 默认 10 轮（`DEFAULT_MAX_TURNS = 10`），超限抛 `MaxTurnsExceededError`，`error.state` 还在。要正常返回得配 `errorHandlers.maxTurns`，E6-E 加了 handler 之后返回 `finalOutput: '已到步数上限，停止'`
- **Claude Agent SDK** 是四家里唯一在返回值上直接给出停止原因的：`result.subtype` 区分 `success`、`error_max_turns`、`error_max_budget_usd`、`error_during_execution`、`error_max_structured_output_retries`。但 `maxTurns` 和 `maxBudgetUsd` 的默认值都是 No limit，预算还是事后检查："Spend can therefore pass the cap by up to the cost of that one response, plus anything that subagents still running at that moment spend before they stop."

<Pitfall title="续跑时漏传 maxSteps，会被静默截到小默认值">

Mastra 自己的 harness 控制器把 `maxSteps` 设成了 1000，旁边留了一段注释：

> "Options that every harness-driven agent run must carry — the initial stream AND every `resumeStream`. Centralized so the two paths can't drift: a missing `maxSteps` on resume silently caps the resumed run at the agent's small default and ends it mid-task"

`resumeStream` 不沿用初次运行的配置。L19 说「续的是 checkpoint，不是新作业」，这里是它的反面：checkpoint 续上了，配置没跟着走，续跑在半路按默认的 5 步停下，而且不报错。

</Pitfall>

### 3.2 isStepCount(0) 永远不触发

`isStepCount(n)` 的实现是 `steps.length === stepCount`，严格相等。正常用没问题；但如果配置里有人把 `maxSteps` 写成 0，意思是「不许多步」，传进去之后它**永远不会触发**。实验一的后半段：

```text
课程的停止条件（maxSteps 8，maxRepeat 3），喂同一段 20 步的历史：第 3 步停，reason=repeat
每步换一个 path：第 8 步停，reason=max_steps
isStepCount(0)：20 步里一次都没触发；课程 maxSteps 0：第 1 步停，reason=max_steps
```

同一个 0，三处三种含义：AI SDK 的 `isStepCount(0)` 永不触发，等于没有上限；Google ADK 的类型注释写明 `maxLlmCalls` "Less than or equal to 0: This allows for unbounded number of llm calls."；课程的 `maxSteps` 用 ≥ 比较，0 在第 1 步就停。

<Drill title="stopWhen 在什么时候求值">

`ai@7.0.137` 的 `src/generate-text/generate-text.ts`，循环的尾部：

```ts
} while (
  // Continue only after all client tool calls have been executed or denied,
  // and if there are client results or pending deferred provider results.
  clientToolOutputs.length + deniedToolApprovalResponses.length ===
    clientToolCalls.length &&
  (clientToolCalls.length > 0 || pendingDeferredToolCalls.size > 0) &&
  // continue until a stop condition is met:
  !(await isStopConditionMet({ stopConditions, steps }))
);
```

能读出三件事：

1. **停止条件在一步做完之后才求值**，位置是 do…while 的尾部。由此推出：用 `stopWhen` 写预算条件，只能在这一步的钱花完之后才停（推论）。L05 第一节把检查点放在循环顶部、先查后花，预算检查就不能只挂在这里。Claude Agent SDK 的 `maxBudgetUsd` 也是事后检查，它的文档自己承认会超
2. 多个条件用 `Promise.all(...).some()` 并行求值，任何一个为真就停
3. 继续的前提是这一步有工具调用、而且全部执行或拒绝了。所以停在审批请求上、调了没有 `execute` 的工具，循环自然结束，`finishReason` 照样是 `tool-calls`

</Drill>

### 3.3 TODO 1：停止原因接在 stopWhen 上

`stopWhen` 只回答停不停，原因得你自己记。shared 里的接法：

```ts
// shared/tsecosystem.ts
export function courseStopWhen(o: StopOpts): (steps: Step[]) => boolean {
  return (steps) => courseStopReason(steps, o) !== 'running'
}
// generate 返回之后，用同一个函数对 result.steps 再算一次 reason，记进你的运行记录
```

`Step` 只取 AI SDK `StepResult` 里和终止有关的三个字段：`toolCalls`、`finishReason`、`approvalRequested`。`myCourseStopReason` 的优先级从上到下：

| 条件 | 原因 |
|---|---|
| 没有步 | `running` |
| 最后一步要审批 | `approval` |
| `finishReason` 是 `length` | `truncated`：工具参数可能被截断，L16 第 1.2 节那条不带错误信号的路 |
| `finishReason` 是 `error` | `error` |
| 最后一步没有工具调用 | `done` |
| 最近 `maxRepeat` 步的调用签名全部相同（`maxRepeat` 至少为 2） | `repeat` |
| 步数 ≥ `maxSteps` | `max_steps` |
| 其余 | `running` |

和 L05 的 `AgentRun.reason` 对一下：`max_steps` 就是 `step_limit`；`approval`、`truncated`、`repeat` 是这一节补上的，因为框架把它们都压进了 `tool-calls` 或 `length`；`budget`、`timeout`、`cancelled` 不是从步里算出来的，它们来自循环外面，在发请求之前查。

| 典型错法 | 后果 | 断言 |
|---|---|---|
| 上限照抄 `isStepCount`，用 `===` | `maxSteps` 为 0 时永远不停 | S5 |
| 调用签名用 `JSON.stringify` | `{a,b}` 和 `{b,a}` 算两个调用，重复检测漏掉。这是 L05 第二节那个 Pitfall 的第三点 | S3 |
| 数整段历史里出现过几次，而不是看最近 N 步是否全同 | `x,x,x,y` 也被判成 `repeat`。L05 那个计数是用来给模型回填提示的，作为停止原因要看最近 N 步 | S4 |
| 一步里的调用先排序再比 | `[x,y]` 和 `[y,x]` 被当成同一步 | S4 |
| 先查 `max_steps` 再查 `repeat` | 第 3 步撞上限时原因写成 `max_steps`，看不出是在打转 | S5 |
| 先查 `length` 再查审批 | 停在审批上的那一步被报成 `truncated` | S2 |

S6 用你的实现重跑实验一的后半段：同一段 20 步历史第 3 步 `repeat`，每步换参数第 8 步 `max_steps`。

## 四、错误回填：三家泄密，一家抹掉

### 4.1 实验二

```text

框架              is_error  证据         回填文本

                                         体检：leaks-secret no-tool-name no-next-step
```

四家的来源各不相同：

- AI SDK 把 `execute` 包在 try/catch 里，异常变成 `error-text`，值是 `error.toString()`，所以带 `Error:` 前缀
- Mastra 用 `error.message`，没有前缀。is_error 那一格写「未核实」：E3 用的是 mock 模型，截到的是交给模型层的 `error-text`，没有经过 Anthropic provider 发出去
- Claude Agent SDK 的实测工具抛的是 `EACCES ... (secret=sk-123)`，回填 `error.message` 加 `is_error: true`；表里按同一个异常统一换算
- OpenAI Agents SDK 的默认 `errorFunction` 原文注释是 "Returns a fixed message without inspecting the exception."，返回固定文案

体检是 `auditBackfill` 拿课程的要求去量：泄密（`leaks-secret`）、看不出是失败（`no-error-signal`）、没有工具名（`no-tool-name`）、没有「下一步：」（`no-next-step`）、叫模型原样重试（`retry-as-is`）、超过 400 个码点（`too-long`）。三家把带 key 的原始异常塞进上下文；一家把信息全抹掉，还叫模型再试一次，叠加 10 轮上限，就是 E6-A 里那 10 次一模一样的失败。L05 第二节死循环的成因二，「工具报错但没给出路」，在这里是框架的默认值。

OpenAI 那一家还有一层：默认 `errorFunction` 下，trace 里的错误详情被替换成 `REDACTED_TOOL_ERROR_MESSAGE`，只有自定义了 `errorFunction` 才会带上详情。**默认配置下，你在 trace 里也看不到工具为什么失败**。

### 4.2 DeepSeek 不看 is_error

### 4.3 接在哪

OpenAI Agents SDK 有现成的口子：每个工具的 `errorFunction`，签名是 `(ctx, error) => string`，把 `courseToolError` 的结果返回就行。

AI SDK 没有对应的钩子，口子是 `execute` 本身：在外面包一层 try/catch。两种包法在线上的差别，从这两段源码就能推出来：

```ts
// ai@7.0.137 src/prompt/create-tool-model-output.ts
if (errorMode === 'text') {
  return { type: 'error-text', value: getErrorMessage(output) };
}
// @ai-sdk/provider@4.0.26 src/errors/get-error-message.ts
if (error instanceof Error) { return error.toString(); }
// @ai-sdk/anthropic@4.0.78 src/convert-to-anthropic-prompt.ts
is_error: output.type === 'error-text' || output.type === 'error-json' ? true : undefined,
```

- catch 之后把课程的文本**作为正常结果返回**：线上块没有 `is_error`。在 DeepSeek 上无所谓，在真 Anthropic 端点上丢了一个信号
- catch 之后 `throw new Error(courseToolError(e, ctx))`：AI SDK 把它变成 `error-text`，带 `is_error`，代价是文本前面多一个 `Error: `

两种都满足体检。选哪种取决于你要不要同时支持不忽略 `is_error` 的端点。

### 5.1 E6-B：同一份 RunState

### 5.3 TODO 3：myResumeOnce

键是 `approval:${approvalId}`，值有两种：`in-flight`，或者 `done:决定:结果`。

| 当前记录 | 动作 | 返回 |
|---|---|---|
| 没有 | 先写 `in-flight`，再调 `resume()`；成功写 `done` | `ran` 加结果 |

## 七、历史是谁的

### 7.1 UI 遮罩改写下一轮

`ai@7.0.137 src/ui-message-stream/to-ui-message-stream.ts:29`：

```ts
onError = () => 'An error occurred.', // masks errors except provider-executed tool execution errors
```

客户端执行的工具报错时，UI 消息里的 `errorText` 是这个函数的返回值。`useChat` 的标准模式下，服务端每一轮都从客户端发来的消息重建历史，文档原话：

> "In the standard `useChat` pattern, the server rebuilds the conversation from the messages the client sends each turn. The server does not persist conversation state between requests. This means the message history is client-controlled input."

实验四：

```text
第 N 轮模型看到       "Error: ENOENT a.ts; 试试 src/a.ts"
UI 消息的 errorText   "An error occurred."
第 N+1 轮模型看到     "An error occurred."   ← 历史被改写了
传 onError: s => s    第 N+1 轮 "Error: ENOENT a.ts; 试试 src/a.ts"（不变）
```

同一个工具错误，第 N 轮带着出路（试试 `src/a.ts`），第 N+1 轮只剩一句 `An error occurred.`。**历史不是只追加的**，它在序列化往返中被改写了。这同时打破两条：L04「错误信息要给出路」，出路在下一轮丢了；L15「前缀稳定才能命中缓存」，同一个位置的 tool_result 变了，L15 第三节的失效定位会报在这里，此后的前缀全部失效。DeepSeek 忽略 `cache_control`、做自动前缀缓存，断点放在哪无所谓，但前缀变了照样不命中（推论）。

<Pitfall title="onError: s => s 修好了漂移，也把原始异常送进了浏览器">

`errorText` 是发给客户端的。照抄原始异常，异常里的 key、内部路径、SQL 都进了用户的浏览器，下一轮再原样回到模型的上下文。要传就传第四节那段脱敏过的课程文本。

更根本的修法是不让客户端当历史的真相源：服务端持久化模型消息（`response.messages`），下一轮从服务端日志重建，客户端发来的 UI 消息只用来对账。这就是 TODO 5。

</Pitfall>

### 7.2 审批也走这条路

`useChat` 模式下，审批记录同样在客户端发来的历史里。AI SDK 的安全章节写得很直接：

> "However, without additional protection, a client that crafts a valid-looking approval for a schema-conforming input can bypass the human-in-the-loop step."

办法是 `experimental_toolApprovalSecret`（HMAC 签名），但 "No secret configured: approvals work as before (backward compatible)"，**默认不签名**。L14 第十节和 L19 第七节的立场是审批状态存服务端、deny 优先；AI SDK 的默认是审批状态存在一份客户端可以随便改的消息列表里。

Mastra 的默认方向正相反：

> "When you use memory with a client application, send only the new message instead of the full conversation history. Mastra loads previous messages from storage."

两个框架拼在一起用（Mastra 有官方的 AI SDK 集成指南），谁是历史的真相源必须显式决定。Mastra 的处理是 "When message IDs match, it uses the stored copy as the base"。

同一节还有两条会改写前缀的默认值。Mastra 的 memory 默认保留最近 10 条消息，官方原话承认它 "changes the start of the prompt and invalidates the provider prompt cache"，而且这 10 条连工具调用和工具结果一起数，一个带三次工具调用的回合就占掉 7 条。AI SDK 的 `prepareStep` 返回的 messages "becomes the base for later steps"，是 L06 压缩的挂载点，但返回之后不可逆，原始消息要自己留一份。

- `drifted`：两边都有，但 UI 的种类（`output-error` 对 `error`）或文本和日志不一致。c2 被遮罩了
- `forged`：UI 里有、日志里没有。c9 是客户端造出来的一条 `approved`，正是上面那种伪造的审批
- `dropped`：日志里有、UI 里没有。c3 被客户端丢了
- UI 里同一个 id 出现多次，只看第一次

| 典型错法 | 后果 | 断言 |
|---|---|---|
| 以 UI 消息为准，只把遮罩文本换回来 | 伪造的工具结果和审批照样进历史 | H2 |
| 只比文本，不比种类 | 一条失败被改成「成功」、文本没动，对账看不出来 | H3 |
| 重复 id 取最后一次 | 客户端在后面追加一条改过的，就能覆盖前面那条 | H4 |
| `drifted`、`dropped` 按 UI 顺序 | 报告顺序跟着客户端走，不可复现 | H5 |

## 八、还有八处会咬人的默认值

实验六：

```text
INV-14 AI SDK abort: 抛 AbortError，返回值里没有已完成的步 → onStepEnd 里自己落盘 [E1-D 实测]
INV-17 AI SDK 模型重试: 429 共 3 次调用后 AI_RetryError，不带幂等键 → 幂等键放在工具层 [E1-F 实测]

INV-26 Agents SDK handoff: 整段对话历史交给下一个 agent → inputFilter [文档]
INV-27 Agents SDK tracing: traceIncludeSensitiveData=true；伞包 import 即注册 OpenAI exporter → 只装 agents-core，exporter 自己设 [E6-F 实测 + 源码]

```

INV 编号是调研报告反转清单里的编号。审批那一条第七节讲过，其余按课程部件分四组。

### 8.1 中断和重试：L08 与 L19

E1-D 在第 3 步 `abort()`，`agent.generate()` 直接抛 `AbortError`，前两步的 `steps`、`response.messages` 都不在返回值里，只有 `onStepEnd` 回调里记到了 `[0,1]`。L08 的不变量是中断之后历史里剩什么必须确定、而且能续跑；在 AI SDK 里，这件事要你自己在 `onStepEnd` 里落盘。

模型请求重试默认 `maxRetries: 2`，指数退避从 2000ms 起、每次乘 2，尊重 0 到 60 秒内的 `retry-after`。重试的单位是一次模型调用，不重放工具，所以它本身对工具是安全的；但 SDK 一层幂等键都不生成，L19 第四节的三层 key 全要自己做。

### 8.2 guardrail 和 handoff：L14 与 L11

`defineInputGuardrail` 的签名里写着 `runInParallel = true`。文档原话："Concurrent execution minimizes latency, but the model may already have consumed tokens or run tools if the guardrail later triggers." E6-D 让 guardrail 在 50ms 后触发：默认配置下抛 `InputGuardrailTripwireTriggered` 时模型已经被调用了 1 次；`runInParallel: false` 时是 0 次。那次实测里副作用工具没跑到，但文档明说可能会跑，不要依赖这一次的时序。L14 的原则是先拒后放，这里的默认是**先放后拦**。另外，输入 guardrail "run only for the first agent in the chain"，handoff 之后的 agent 不受它约束。

handoff 原文："By default a handoff receives the entire conversation history." L11 讲 sub-agent 要隔离上下文，这里的默认是整段交出去，要裁剪得配 `inputFilter`。

### 8.3 tracing：L13

伞包 `@openai/agents` 的 `dist/index.mjs` 前五行里有一行 `setDefaultOpenAITracingExporter();`。只要 import 它，进程就注册了 OpenAI 的 tracing exporter，导出端点是 `https://api.openai.com/v1/traces/ingest`。敏感数据默认包含：`traceIncludeSensitiveData ?? true`，E6-F 实测为 `true`。官方文档："Tracing is enabled by default in server runtimes (Node.js, Deno, Bun). It is disabled by default in browsers and when `NODE_ENV=test`."

后一句意味着**测试环境和生产环境行为不同**：测试里看不到的上传，在生产里发生。E6-F 还发现，调用 `setTracingDisabled(true)` 之后，`new Runner().config.tracingDisabled` 仍是 `false`，全局开关和 Runner 级开关是两个东西。L13 的立场是 span 去哪由你决定，这里的默认是 span 已经有去处了。AI SDK 的 telemetry 也是 "Enabled by default when a telemetry integration is registered"，输入记录默认开。

<Pitfall title="环境里恰好有 OPENAI_API_KEY">

没有 key 时 exporter 只打一句 `No API key provided for OpenAI tracing exporter. Exports will be skipped`。反过来，如果别的功能恰好在用 `OPENAI_API_KEY`，而 agent 的模型走的是 DeepSeek，那么 DeepSeek 上的对话内容会作为 trace 上传到 OpenAI。这一条是从上面三条一手事实推出来的，没有实测（推论）。lab 的修法写在实验六里：只装 `@openai/agents-core`，exporter 自己设。

</Pitfall>

### 8.4 输出上限和 reset-step：L15 与 L16

`@ai-sdk/anthropic@4.0.78` 的 `getModelCapabilities` 最后一个分支：

```ts
} else {
  // Non-Claude models (e.g. served through Anthropic-compatible APIs)
  // keep conservative defaults.
  return {
    maxOutputTokens: 4096,
    supportsStructuredOutput: false,
    ...
```

E1-G 用 `baseURL` 指向 DeepSeek 的 Anthropic 端点、模型 `deepseek-v4-pro`，每一步都打一条 "The model "deepseek-v4-pro" is unknown. The max output tokens have been limited to 4096. Set maxOutputTokens explicitly to override this limit."。thinking 加上一段长代码编辑很容易超过 4096，`stop_reason` 变成 `max_tokens`，工具参数被截断。这就是第三节的 `truncated`，也是 L16 第 1.2 节那条不带错误信号的撤回路径：**换了 provider 不改 `maxOutputTokens`，capstone 的编辑工具会随机截断**。

L16 第一节引用了 UI message stream 协议里的 `reset-step`。在 `ai@7.0.137` 的 `src/` 里全文搜它，只有两处：schema 定义和客户端的处理函数。`streamText`、`ToolLoopAgent` 的服务端路径从不发它，文档写明发它的是 `WorkflowAgent` 的重试。而 `streamText` 自己的流内重试（`streamRetries`，默认关）注释原文：

> "Partial output from a failed attempt that was already emitted cannot be retracted and remains in consumer-facing streams. It is excluded from the recovered step result, structured output parsing, response messages, and subsequent model steps."

打开 `streamRetries` 而不用 `WorkflowAgent`，得到的正是 L16 实验三那个只会追加的前端：UI 上重复半句话，模型历史里没有。UI 和模型消息又一次分叉。

<Drill title="thinking 签名：同一个问题，两条路径行为相反">

E4 用真 `@ai-sdk/anthropic` 加假 `fetch`，对 thinking 块有没有 `signature` 和流式、非流式各跑一遍：

| 响应形态 | 有签名 | 结果 |
|---|---|---|
| 非流式 | 有 | 第二次请求回传 `["thinking","tool_use"]` |
| 非流式 | 无 | `AI_APICallError: Invalid JSON response` |
| 流式 | 有 | 回传 `["thinking","tool_use"]` |
| 流式 | 无 | thinking 块被丢弃，只回传 `["tool_use"]`，一条 warning `unsupported reasoning metadata` |

非流式报错，是因为响应 schema 里 `signature: z.string()` 是必填；流式丢弃，是因为转换函数遇到既没有 `signature`、也没有 `redactedData` 的块就整块扔掉。前者响亮，后者静默。

L16 第 5.4 节说 thinking 块必须原样回传。DeepSeek 的 OpenAI 格式文档写得更硬："If your code does not correctly pass back `reasoning_content`, the API will return a 400 error."。两件事调研没能确认：DeepSeek 的 Anthropic 端点返回的 thinking 块带不带 `signature`（文档没写，零网络验证不了）；Anthropic 格式下漏传是否同样 400（兼容表只写了 Supported）。

`@ai-sdk/deepseek`（OpenAI 格式）显式处理了回传，但判断是不是 V4 靠模型名字符串：`includes('deepseek-v4') || startsWith('deepseek-flash') || startsWith('deepseek-pro')`。经网关改了名（比如 one-api 里叫 `ds-v4`），就会被当成 R1，历史 reasoning 被丢掉。

</Drill>

## 九、跑一个 Claude Code 二进制意味着什么

### 9.1 它不是一个纯 TS 库

`@anthropic-ai/claude-agent-sdk@0.3.296` 的 `optionalDependencies` 是 8 个平台包；`darwin-arm64` 那个的二进制叫 `claude`，240664432 字节，约 240MB，`linux-x64` 约 257MB。官方的定位就一句："A library that runs the Claude Code binary, with Claude Code's capabilities, such as built-in tools, permissions, sessions, and hooks."

由此推出几件事（推论）：agent loop 不在你的进程里，你只能通过 options、hooks、`canUseTool` 这些它开放的口子影响循环，L05 那句「自己写你才控制得住」在这里是字面意义上的控制不住；每个会话一个子进程、每个镜像多二百多 MB、要匹配 libc，和 Serverless 天然冲突；版本是两层的。许可不是开源："© Anthropic PBC. All rights reserved."，商用受 Commercial Terms 约束。README 还写着 "we collect feedback, which includes usage data (such as code acceptance or rejections), associated conversation data"。

默认值几乎每一项都是继承你机器上的 Claude Code：

- `settingSources`："When omitted, all sources are loaded (matches CLI defaults)."。服务器上的 `query()` 会读运行用户的 `~/.claude/settings.json`、项目的 `.claude/` 和 CLAUDE.md
- `env`："this value REPLACES the subprocess environment entirely"。不传，子进程继承服务器进程的全部环境变量，而子进程里跑着 `Bash` 工具；传了，`PATH` 没了，二进制里的 `git`、`rg` 都找不到
- `persistSession` 默认 `true`，每个会话的完整 transcript 写进运行用户 home 下的 `~/.claude/projects/`
- 默认 system prompt 不是 Claude Code 的那一大段，只有一句 "You are a Claude agent, built on Anthropic's Claude Agent SDK."，要完整行为得显式传 `systemPrompt: { type: 'preset', preset: 'claude_code' }`

### 9.2 实验七

```text
不传 permissionMode → auto：每次主循环请求后跟着 10 次分类器请求（max_tokens 64 五次、8192 五次）
分类器的 model=claude-sonnet-5，不是你设的 deepseek-v4-pro；它的花费不进 total_cost_usd
分类器的 system 开头："You are a security monitor for autonomous AI coding agents."
分类器答不上来时回填给主模型：
  "Auto mode could not evaluate this action and is blocking it for safety — run with --debug for details. This is not a judgment that the action is unsafe. This is usually transient — wait briefly and try this action again as-is; don't rewrite it."
  体检：no-error-signal no-tool-name no-next-step retry-as-is

运行                        session_id    messages  total_cost_usd
A2                          e1027878…     5         0.0012
B：resume A2                e1027878…     8         0.0018
C：resume A2 + forkSession  9afbad74…     11        0.0024
fork 的成本从父会话的累计值接着算：0.0024 包含了 0.0018——按会话汇总会重复计算
成本里不含什么："Internal helper calls outside the query pipeline (e.g. the permission classifier, token-count probes) are excluded"
```

这一组的证据等级最需要分开读：

| 说法 | 等级 |
|---|---|
| 干净环境（没有任何 settings 文件）下 `init.permissionMode` 是 `auto` | E5-A 实测。有 settings 文件时，它会被里面的 `permissions.defaultMode` 改掉 |
| 每次主循环请求后跟 10 次分类器请求，`model` 写死为 `claude-sonnet-5` | 实测，但对着的是一个本地假服务器，它不按分类器要求的 `<severity>N</severity>` 协议作答。真分类器答得上来时是几次，没有测 |
| 分类器失败即拒，回填叫模型原样重试；没有轮数上限，于是死循环 | 实测：45 秒后手动 abort；第一次没加保护时跑到 Node 堆溢出 |
| 接 DeepSeek 时，分类器会落到 `deepseek-flash` | 推论。依据是 DeepSeek 文档的映射规则 "Models starting with claude-haiku or claude-sonnet are mapped to `deepseek-flash`"，没有真网络验证 |
| `deepseek-flash` 能不能稳定按 `<severity>` 协议作答 | 未知，没有一手来源 |
| 分类器的花费不进 `total_cost_usd` | 一手：`sdk.d.ts` 的注释原文 |
| `total_cost_usd` 对 `deepseek-v4-pro` 算出非零值，但用的不是 DeepSeek 的价格 | 非零是实测（每次 100 输入、10 输出 token 记 0.0006 美元）；它用的是哪张价目表，是推论 |

失败即拒这一半本身没错，它符合 L14 第十节第 2 条「任何失败都是拒绝」。出问题的是另外两半：拒绝文案叫模型 "try this action again as-is; don't rewrite it"，而 `maxTurns` 没有默认值。三样叠在一起，**默认配置就是一个死循环**。「能连上 DeepSeek」不等于「行为一致」。

成本账上还有两处和 L15 冲突：分类器的花费不入账，fork 的累计值从父会话接着算。按会话汇总成本，父会话的钱会被算两次。

### 9.3 要显式设的几项

- `permissionMode` 显式传。无人值守的服务用 `dontAsk`，原文 "every call that would otherwise prompt is denied"，最接近 L14 的 deny 优先；或者 `default` 加 `allowedTools`、`canUseTool`，`default` 下没有回调就是拒
- 被拒不改变 `result.subtype`（E5-A3 里连你自己进程内注册的 MCP 工具也被拒了，`subtype` 仍是 `success`），要看 `result.permission_denials`，注释说它 "is the authoritative record"
- `maxTurns` 和 `maxBudgetUsd` 都设，并且记住预算是事后检查
- `settingSources: []` 隔离文件系统上的配置；`env` 显式给，把需要的变量自己展开进去
- 接 DeepSeek 时，按 DeepSeek 给 Claude Code 的推荐配置覆盖全部四个模型槽位加子 agent 模型，漏一个就落到映射规则上
- 成本以你自己的账为准，`total_cost_usd` 在 DeepSeek 上不是账单

<CursorHook>

Cursor 和 Claude Code 是同一类东西：harness。循环、工具注册、审批、上下文压缩都是它们自己写的，默认值是为「一个人坐在屏幕前写代码」调的。

Claude Agent SDK 把其中一个 harness 打包成了库。你 import 进来的不是一个通用框架，是别人的产品连同它的默认值：没有轮数上限，分类器替你批工具调用，整段历史回放。这些默认值是一个 coding harness 的默认值，不是你那个没人盯着的后端服务的默认值。

</CursorHook>

## 十、平台：Dify、Coze Studio、n8n

这一节的结论都来自三个平台仓库里的原文件，**没有任何平台的运行时实测**。

### 10.1 什么时候该用平台

实验九：

```text
内部运营：查库存、出日报                平台
对外客服：按客户计费、能退款            平台做原型，DSL 当需求文档，手写上线（许可：Dify 多租户要书面授权）
coding agent 进 CI                      手写
把 n8n 流程打包卖给客户                 手写（许可：n8n 不能嵌进对外收费的产品）
```

判据是调研的经验法则，`choosePlatform` 的注释也写明它是推论，不是一手结论：**流程固定、工具只读、使用者是内部运营**，用平台；要 eval 门禁、按租户计费、写操作要审批、要进 CI，任一条成立就手写，流程固定时可以拿平台做原型。

| 维度 | 平台给你的 | 手写给你的 | 平台够用的条件 |
|---|---|---|---|
| 版本管理 | DSL 导出，夹带 UI 坐标；知识库和凭据不在里面 | 代码加 git 加锁定依赖 | 改动少，改的人不是工程师 |
| 测试与评测 | 平台内的调试面板；DSL 里没有放测试的位置 | L12 的回归集加 CI | 能接受「人工点一遍」当回归 |
| 可观测性 | 平台自带日志；n8n 的 Tools Agent 默认不返回中间步骤 | L13，span 去哪你决定 | 不需要和公司现有的 trace 打通 |
| 权限 | 平台的 workspace 和角色 | L14 的审批门、沙箱、服务端审批状态 | 工具都是只读或低风险 |
| 失败恢复 | 平台的重试配置，Dify 的 HTTP 节点默认关 | L08、L19 的幂等键与断点续跑 | 节点都是幂等的 |

平台自己也在用框架：Dify 新增的 `dify-agent/` 目录 README 原文 "Dify Agent runs Pydantic AI with native capabilities and toolsets."；Coze Studio 的 agent 和 workflow 运行时基于 CloudWeGo 的 Eino；n8n 的 AI 节点依赖十几个 LangChain JS 包，Tools Agent 默认 `maxIterations` 10、`returnIntermediateSteps` 为 `false`。

### 10.2 许可：三家三样

- **Dify** 是 "a modified version of the Apache License 2.0"。附加条件原文："Unless explicitly authorized by Dify in writing, you may not use the Dify source code to operate a multi-tenant environment."，并且 "one tenant corresponds to one workspace"。给每个客户开一个 workspace 的 SaaS 就需要书面授权。用 Dify 前端时不得去掉或修改 LOGO 和版权信息；贡献者要同意许可可以被收紧。「Dify 是 Apache 2.0」这个说法不准确
- **Coze Studio** 是 Apache-2.0，没有多租户条款。Go 后端加 React 前端，最近一次 release 是 v0.5.1（2026-02），活跃度没有查
- **n8n** 是 Sustainable Use License："You may use or modify the software only for your own internal business purposes or for non-commercial or personal use."。内部自用可以，**嵌进对外收费的产品不在许可范围内**；文件名带 `.ee.` 的另需企业许可

### 10.3 把 DSL 当需求文档读

Dify DSL 当前版本 0.7.0，导入时缺 `version` 当 `"0.1.0"`、缺 `kind` 补 `"app"`。导出时默认删掉工具节点的 `credential_id`，知识检索节点的 `dataset_ids` 用原租户 id 加密，webhook URL 清空。同一个节点里还混着 `position`、`width`、`selected` 这类画布字段，拖一下节点，git diff 就出现和语义无关的变化。所以 DSL 导到另一套环境，检索和凭据都是断的；但它是一份很好的需求文档：节点是步骤，边是控制流，`{{#node.field#}}` 是数据流。

实验八：

```text
version=0.7.0  kind=app  丢掉的画布字段：20 个
执行顺序：start → kr → route → llm → ticket → notify → answer → fallback
分支：route:true->llm  route:false->ticket
节点      类型                  标题      改写成代码时要补的
kr        knowledge-retrieval   知识检索  rebind-index
llm       llm                   回答      sliding-window-breaks-cache
ticket    http-request          建工单    no-retry idempotency-key
notify    tool                  发通知    reconnect-secret
数据流：llm<-kr.result  llm<-sys.query  ticket<-sys.query  notify<-ticket.body  answer<-llm.text  fallback<-ticket.body  fallback<-sys.query
问题：ref-not-upstream:ticket:llm.text
```

每个「要补的」都是前面某一节：

- `rebind-index`：`dataset_ids` 绑在原租户上，换成你自己的索引（L09）
- `sliding-window-breaks-cache`：LLM 节点开了 `memory.window`（size 10），和 Mastra 的 `lastMessages` 一样，每一轮滑动都改写前缀（L15）
- `no-retry`、`idempotency-key`：建工单是 POST，`retry_config.enabled` 是 `false`；改写成代码时要么不自动重试，要么带幂等键（L19 第五节）
- `reconnect-secret`：发通知的凭据导出时被删了，从你的密钥管理里重新接
- `agent` 节点（这份样例里没有）是一个 L05 的循环，要补步数上限和停止原因

## 十一、那篇论文到底说了什么

arXiv [2609.00006](https://arxiv.org/abs/2609.00006)，"Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents — A Source-Code Study of Eleven Systems"，研究对象是 Claude Code、Codex CLI、Gemini CLI、OpenHands、Aider、OpenCode 等十一个 coding agent 加 Databricks 的 Omnigent，源码锁定在 2026 年 7 月。它经常被引成「生产环境不用框架，所以别用 AI SDK」。原文是这样说的：

> "across roughly four million lines of Python, TypeScript, and Rust, no agent runtime imports a general-purpose agentic framework (LangChain, LangGraph, AutoGen, or a dozen others; Gemini CLI uses neither of Google's own), and none retrieves code with vector embeddings"

检查清单是 "LangChain, LangGraph, LlamaIndex, AutoGen, CrewAI, Pydantic AI, Genkit, Haystack agents, Semantic Kernel, Google's ADK, and several smaller libraries (Smolagents, Swarm, Agno)"。**清单里没有 AI SDK、Mastra、Claude Agent SDK、OpenAI Agents SDK**。而且论文专门写了 AI SDK：

> "And OpenCode delegates its inner LLM/tool plumbing to Vercel's AI SDK—a provider-abstraction layer, not an agent-orchestration framework, but the first corpus system whose inner loop plumbing is a third-party SDK at all"

所以它能证明的是：生产 coding harness 的循环都是手写的（"Every loop is hand-rolled in the host language's native primitives"），工具注册都围绕 Pydantic、Zod、TypeBox 这些 schema 库自建。它证明不了「别用 AI SDK」，反而把 AI SDK 归进了 provider 抽象层，正好对上这一节的结论：**拿 provider 层，编排层的默认值不要照单全收**。

论文的局限写得很老实："A company could in principle use LangChain inside a production SWE agent through a code path we did not inspect. We would be surprised, but not shocked." 它还有一个合流论点：一个 meta-harness 把 `claude-agent-sdk` 和 `openai-agents` 列为生产依赖，"harnesses did not adopt the frameworks; they replaced them, became importable themselves"。由此推出（推论）：harness SDK 正在成为新的框架，而它们的默认值是一个 coding harness 的默认值，第九节已经看过那是什么样子。

论文里转述 Gemini CLI 循环检测阈值的那几个数，是论文对别人源码的描述，这一节不拿来当依据。

## 十三、收尾

面试里被问「你们用什么框架」，可以这样答：

1. **先分层**。provider 层用 AI SDK 的 `streamText` 和 provider 包，这是真脏活；接 DeepSeek 的 Anthropic 端点时显式设 `maxOutputTokens`，否则被限到 4096。编排层的默认值不照单全收
2. **说出四家的默认值差多少**。同一个永远失败的工具，默认上限 1、20、5、10、无上限；撞上限时有的正常返回、有的抛、有的不停。停止原因我们自己算，approval、truncated、repeat 各是各的
3. **错误只信文本**。三家把带 key 的原始异常塞进上下文，一家抹掉还叫模型再试一次；DeepSeek 忽略 `is_error`。我们的错误出口是前缀加工具名加下一步，先脱敏再截断，接在 `execute` 包装和 `errorFunction` 上
4. **恢复只消费一次**。同一份 RunState 恢复两次执行两次，四家都不生成幂等键。先认领再执行，in-flight 不重跑、去外部系统对账
5. **历史以服务端为准**。`useChat` 的历史是客户端输入，审批默认不签名，UI 遮罩会改写下一轮。服务端持久化模型消息，客户端的只用来对账
6. **Claude Agent SDK 和平台各有位置**。要的就是一个 coding agent 时用 Claude Agent SDK，但显式关掉默认值：权限模式、轮数、预算、配置来源、环境变量；平台做原型，DSL 当需求文档。那篇 harness 论文证明的是生产 coding harness 的循环都是手写的，不是别用 AI SDK

<Note title="这一节刻意没有当事实讲的说法">

调研查不到一手来源的：DeepSeek 的 Anthropic 端点对 thinking `signature` 的要求，缺签名会不会 400，以及它对 `thinking: {type:'adaptive'}`、messages 里 `role: "system"` 的处理；`deepseek-flash` 能否稳定按 `<severity>N</severity>` 协议回答 Claude Code 的权限分类器；Claude Agent SDK 自动压缩的阈值和 `total_cost_usd` 用的价目表；Mastra 线上的 `is_error`、它的 `ee/LICENSE` 条款；Python 版 Agents SDK、Claude Agent SDK 的默认值；Dify 许可是否被 OSI 认定为开源；三个平台的运行时行为（都没有部署）。Mastra 文档没有提醒 `suspend()` 之前的副作用会重跑，这是调研对文档的解读；论文里关于 Gemini CLI 阈值的数字是二手转述。

</Note>

回头看前置课：L05 第四节「框架到底包装了什么」那张表，在这里展开成了第二节的对照表；L05 的 `AgentRun.reason` 变成了 `stopWhen` 上的适配器；L08 和 L19 的幂等键，是四家框架那一行全空的地方；L10 的 `isError`、L13 的 trace、L14 的审批、L15 的兼容层、L16 的 `reset-step` 和 `truncated`，每一处都在某个默认值上被反转了一次。L11x 教你读 Python 生态的代码，这一节教你读 TS 框架的默认值，方法相同：先找到它替你写了哪一段，再看那一段的默认值和你的不变量差在哪。
