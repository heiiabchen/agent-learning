你现在会写 agent 了。这一节要说的是：**你遇到的大多数需求不该用 agent。**

这不是保守。是因为 agent 的核心特征——让模型决定下一步——在你已经知道该怎么做的时候，是纯粹的成本。

<Key>
自主性不是一个功能，是**你为「不知道该怎么做」付的钱**。

知道该怎么做还上 agent，等于每次运行都花 token 让模型重新发现一遍你自己的流程图。而且每次发现的结果还不完全一样。
</Key>

## 一、五种模式其实是同一条轴

网上讲编排模式的文章通常列出五个图，五个图长得都不一样，看完记不住。

它们其实只在回答同一个问题：**谁决定下一步。**

| 模式 | 谁决定下一步 | 步数 | 成本方差 |
|---|---|---|---|
| **链式** | 你，全部 | 固定 | 零 |
| **路由** | 模型决定一次，之后是你 | 固定 | 接近零 |
| **并行** | 你决定拆法，模型填叶子 | 固定 | 零 |
| **编排-工作者** | 模型决定拆法 | 不定 | 中 |
| **评估-优化** | 模型决定什么时候停 | 有界不定 | 中 |
| **Agent** | 模型决定全部 | 不定 | 大 |

从上到下自主性递增，**而成本方差和调试难度跟着一起涨**。

这张表本身就是选型判据：**从上往下挑，够用就停。**

<CursorHook>

Cursor 里这几种模式你都用过，只是没有这些名字：

- **Tab 补全**是单次调用，连链式都不是。它快是因为它什么都不决定。
- **⌘K 编辑选中代码**是链式：读上下文 → 生成 diff → 应用。路径固定。
- **@Codebase 提问**是并行加整合：检索出若干片段，然后一次性合成答案。
- **Agent 模式**才是真 agent：它自己决定读哪个文件、要不要跑测试、跑完了要不要改。

注意一件事：**⌘K 比 Agent 模式快得多，也稳得多。** 因为它的路径是写死的。

Cursor 没有把所有功能都做成 agent，正是因为这一节讲的判断。你要改一个已经选中的函数，Agent 模式除了慢没有任何好处。

</CursorHook>

## 二、逐个过一遍：每种模式真正的难点

代码在 `shared/patterns.ts`（和 `.py`）里都有。这里只讲**每种模式最容易写错的那一处**——因为模式的骨架都很简单，价值全在防线上。

### 链式：关口

链式就是把上一步的输出喂给下一步。骨架三行。难点在于：

<Pitfall title="没有关口的链会把垃圾一路传到底">

一条典型的链：提取要点 → 检查完整性 → 翻译成英文。

第二步发现要点不完整。如果没有关口，这个发现会被第三步无声地吃掉——你最后拿到一份「翻译得很流畅的残缺要点」，而且**不知道是哪一步坏的**。

关口要做两件事：

```ts
{
  name: '检查完整性',
  prompt: (s) => `检查这份要点有没有遗漏：${s}`,
  gate: (out) => (out.includes('不完整') ? '要点不完整，后面的翻译没有意义' : true),
}
```

第一件是**中止**。第二件是**说清在哪一步、为什么**。

还有一个容易写错的选择：中止的时候要 `return` 而不是 `throw`。上游需要知道「走到哪一步停的」和「已经产出了什么」——抛异常只留一个栈，而栈里没有业务信息。

</Pitfall>

### 路由：不能相信模型给的标签

路由是**实践中投入产出比最高的一个模式**，因为它让你用便宜模型接住八成流量。

难点不在分类，在处理分类的结果。

你让模型只输出 `billing` / `tech` / `general` 三个词之一，它会输出：

```text
billing            ← 你期望的
  Billing          ← 带空格，大小写不同
billing/技术支持     ← 拿不定主意就都写上
"billing"          ← 加了引号
我认为这是一个关于产品定价策略的复杂问题，需要综合判断    ← 完全跑偏
refund             ← 编了一个你没定义的类
```

所以匹配必须宽松（大小写归一、剥掉标点、在句子里也能捞出来），但**宽松只能到「在已知枚举里找」这一步，不能到「猜一个」**。

<Key>
**兜底不能是「随便挑一个」，也不能是「挑最便宜的」。**

分类不确定意味着这条输入是边缘情况——而边缘情况恰恰最需要强能力。所以兜底应该指向**能力最强**的那条路径。

这一条和省钱的直觉相反，但线上事故都长这样：分类器不确定 → 兜底给了便宜模型 → 便宜模型处理不了边缘情况 → 用户看到一个荒谬的回复。
</Key>

两个实现细节，各有理由：

- **分类调用用 `temperature: 0`。** 分类要的是确定性，不是创造力。附带好处是低温让结果可缓存。
- **分类调用给一个很小的 `max_tokens`（16 就够）。** 给大额度它就开始解释了。

还有一个必须返回出去的字段：`fellBack`。它是**判断「分类器该不该重训」的唯一信号**。兜底率从 3% 涨到 20%，说明进来的流量分布变了，而你只能从这个数字上看出来。

### 并行：两种用法别混

并行有两种完全不同的用法，图长得一样但性质不同：

- **分片**——把一件事拆成互不相干的几块，各做一块，最后拼起来。
- **投票**——同一件事做 N 次，取多数。

<Drill title="为什么 temperature=0 的投票是纯粹的浪费">

投票的前提是**错误互相独立**。

`temperature=0` 跑五次，五个输出高度一致（L05x 讲过，不是完全确定但差异很小）。这时候投票在做什么？把成本乘以五，然后得到一个 100% 的置信度——**而这个置信度是假的**。五次跑的是同一条路径，错的时候也一致地错。

要让投票有意义，必须主动引入独立性，按有效性排序：

1. **换模型**——不同的训练数据，盲点最不相关
2. **换 prompt**——同一个问题问三种不同的问法
3. **调高温度**——最便宜但也最弱的一种独立性

这就是为什么 `vote()` 要返回 `confidence` 而不只是 `winner`：**3:2 和 5:0 是完全不同的结论**，只返回胜者会把这个差别抹掉，而下游正需要它来决定要不要升级给人工。

</Drill>

分片这边的难点是**一个失败不能拖垮整批**。用 `Promise.all` 的话，第二个分片挂了，前面三个成功的结果全丢——而钱已经花了。L00 那个 `pooled` 就是为这个存在的，在这里第一次真正用上。

<Pitfall title="Python 这边同一个坑更隐蔽">

`asyncio.gather` 默认在第一个异常处抛出，而**其余任务还在后台继续跑**。

也就是说你既没拿到结果，又照样付了钱，而且日志里看不到那些任务的下场。必须传 `return_exceptions=True`。

```python
await asyncio.gather(*tasks, return_exceptions=True)
```

TS 里 `Promise.all` 至少是"全丢"，语义直白。Python 这里是"全丢 + 静默烧钱"。

</Pitfall>

### 编排-工作者：计划必须校验

编排和并行的区别只有一处，但很关键：**拆法是模型定的。**

这一处差别把成本从「可预测」变成「不可预测」——模型可能拆成 3 个子任务，也可能拆成 40 个。40 个子任务就是 40 次调用。

三条校验缺一不可：

| 校验 | 不做的后果 |
|---|---|
| **非空** | 空计划静默降级成「直接做整个任务」 |
| **有上限** | 40 个子任务 = 40 次调用 = 账单事故 |
| **去重** | 模型很爱把同一件事换个说法列两遍 |

第一条最值得说：**静默降级是很诱人的**——反正模型也能直接做整个任务，为什么要报错？

因为那会把一次**编排失败**伪装成一次**正常运行**。你在监控里看不到任何异常，只看到质量莫名其妙地变差了，然后花两天排查。

<Key>
**把静默失败变成响亮失败。** 这条纪律在这门课里出现了第五次：L02 的未知模型不按 0 计价、L03 的截断输出不当成有效结果、L04 的未知工具不静默跳过、L06 的未知块类型要抛错、这里的空计划要报错。

它们是同一件事：**一个错误如果不报警，它就会以「质量下降」的形式出现，而质量下降是最难归因的现象。**
</Key>

### 评估-优化：无限打磨

生成一版 → 评审 → 按意见改 → 再评审。这是自主性最高的非 agent 模式，因为**模型自己判断够不够好**。

它有一个特有的失控方式，而且它不报错：

<Pitfall title="评估者永远能挑出毛病">

「还可以更清晰一点」——这句话对任何文本都成立。于是循环不停，而每一轮的实际改进趋近于零。

所以必须有两道闸：

- **轮数上限**——硬闸
- **改进检测**——软闸，分数不再上升就停

**只有轮数上限是不够的。** 那样你每次都跑满 `maxRounds`，白付 80% 的钱。而 `targetScore` 只要定得稍微高一点（这很常见），就等于每次都跑满。

`labs/l07/patterns.ts` 里的 `demoRefine` 把这笔账摆出来了：同一个分数序列（0.5 → 0.62 → 0.63 → 0.63 → 0.63），有停滞检测的跑 3 轮，没有的跑 5 轮，**最终分数一模一样**。

还有一条容易漏的：**要保留历史最优，不能无脑接受最后一版。** 打磨会让结果变差，这在实践中比想象的常见——而只留最后一版会把这件事完全藏起来。

</Pitfall>

<Drill title="生成者和评估者是同一个模型时，你在测什么">

这是评估-优化模式里最深的一个问题。

同一个模型，同一份权重，同一套训练数据形成的判断倾向。它作为生成者看不见的错误，换个角色当评估者也看不见——**盲点是相关的。**

于是自我评估会收敛到**自我满意**，而不是收敛到**正确**。分数一路涨到 0.9，而实际质量停在原地。

三个真实的缓解办法，按有效性排序：

1. **换模型当评估者。** 不同的盲点，才有独立的信号。
2. **给评估者一份显式的检查清单**，而不是「你觉得怎么样」。清单把主观判断变成逐条核对。
3. **让评估者能用工具去验证**——比如跑测试、查文档。这时候它的判断不再来自权重，来自事实。

第三条是最强的，也是 L12 讲 evals 时的核心思路：**能自动判定的东西不要交给模型判定。**

</Drill>

## 三、把「贵」这个字量出来

前面说 agent 的成本方差大。这句话不量化就只是个说法。

`labs/l07/compare.ts` 跑了 200 个客服工单（八成简单、两成复杂），三种架构各跑一遍：

| 架构 | 总花费 | p50 | p95 | 最坏 | p95/p50 | 均步 | 最多步 | 解决率 |
|---|---|---|---|---|---|---|---|---|
| 纯 workflow | ¥0.667 | 0.00334 | 0.00334 | 0.00334 | **1.0×** | 3.0 | 3 | 82% |
| 纯 agent | ¥22.36 | 0.06360 | 0.49164 | 0.65940 | **7.7×** | 6.1 | 20 | 95% |
| 混合 | ¥5.64 | 0.00334 | 0.10866 | 0.66012 | 32.6× | 4.0 | 21 | 98% |

<Note title="最该看的不是总花费">

**总花费只告诉你「贵了多少」，`p95/p50` 告诉你「贵得能不能预测」。**

workflow 是 1.0×——每个工单花的钱一模一样，可以直接写进报价单。agent 是 7.7×，最坏的那单是中位数的 10 倍。

后者才是分界线：能不能按次报价、能不能定 SLA、能不能给用户一个像样的进度条。

而且这个方差**不是模型不稳定造成的，是架构造成的**。agent 最少 3 步、最多 20 步；而每一步都要重发全部历史（L02），所以**步数线性增长，成本二次增长**。长尾在成本上被平方放大了一次。

</Note>

第二行最值得盯着看：**workflow 的解决率只有 82%，而它的账单看起来非常健康。**

复杂工单它照样跑完三步、照样产出一段通顺的回复，只是答非所问。

<Key>
**成本正常，质量失败**——这是最危险的一种失败模式，因为监控里看不见。

这也是 L12 evals 存在的理由：**成本你能自己测，质量不能。**
</Key>

第三行是这一节想让你先想到的形态：**混合架构在这批数据上同时赢了成本和质量。**

花费比纯 agent 省 75%，解决率还高三个点。它的 p50 就是 workflow 的 p50——**八成流量的成本完全确定。**

<Drill title="混合架构的解决率为什么会反超纯 agent">

这不是巧合，也不是我把数字调好看了。

**在 workflow 覆盖得住的路径上，确定性流程比 agent 更可靠。**

脚本里 agent 在简单工单上也有 3% 的概率把事情办歪——它有选择的自由，而这个自由在**不需要选择的时候只是风险**。它可能去查一个不需要查的订单，可能把模板回复改写成一个错误的承诺。

这条推论值得单独记住，因为它反直觉：**能力更强的架构在简单任务上表现更差。** 不是因为模型笨，是因为你给了它犯错的空间。

</Drill>

<Pitfall title="混合那一行的 p95/p50 是 32.6×，全场最高">

这不是它变差了，是**这个指标读不懂双峰分布**。

混合架构的成本不是一条曲线，是两个簇：八成挤在 0.00334，两成散在高位。p50 落在便宜簇里、p95 落在贵簇里，比值就被这个断层撑爆了。

正确的读法是**分簇分别看**：便宜路径方差为零，贵路径和纯 agent 同分布。

前面刚教你看 `p95/p50`，这里就告诉你它什么时候失效——这不是自相矛盾，是「**用一个指标之前先看分布形状**」这条纪律本身。L12 和 L13 会反复撞到它。

</Pitfall>

## 四、什么时候别用 agent

这一节最值钱的部分。

**能列出步骤就别用 agent。** 这句话覆盖了大多数情况。下面这些是它的具体形态：

<Note title="七条「别用 agent」">

**一 · 你能画出流程图。** 画得出来就写成代码。让模型每次运行重新发现一遍你的流程图，是在为一个你已经有的答案付费。

**二 · 路径有限且已知。** 三种工单类型 → 用路由。别让 agent 自己"探索"该怎么处理。

**三 · 错误代价高。** 数据库迁移、发邮件、转账、删文件。这里**不确定性本身就是不可接受的**，而不确定性是 agent 的定义特征。要用就在外面套人工确认。

**四 · 需要可预测的延迟或成本。** 上面那张表说明了理由。按次报价的产品、有 SLA 的接口，都不该把 agent 放在关键路径上。

**五 · 单次调用就够。** 翻译、摘要、分类、格式转换。给它工具和循环不会让结果更好，只会更慢更贵。

**六 · 你没法评估它。** 这条最容易被跳过：**没有 evals 的 agent 是不能上线的。** 你无法知道改一句 prompt 是让它变好还是变坏。而 workflow 每一步都能单测。

**七 · 用户需要看到中间过程并干预。** agent 的路径是它自己定的，你没法在中间插一个"确认这一步"——因为你不知道会有哪些步。

</Note>

<Drill title="第六条为什么最容易被跳过">

因为**没有 evals 的 agent 在 demo 里表现极好。**

你手动试十个例子，八个成功，感觉可以了。上线后你发现：

- 你不知道那 20% 失败的是什么类型的输入
- 你改了 prompt，不知道是变好了还是把别的场景搞坏了
- 有人报了个 bug，你复现不出来（路径每次不一样）
- 你想换个便宜模型，不敢换，因为没有基线

**Workflow 天然可测**——每一步固定输入固定输出，就是普通单测。这是它被严重低估的优势，比省钱重要得多。

而 agent 只能**统计着测**：跑一百次，看成功率和 `reason` 分布（L05 那个字段就是给这个用的）。这是 L12 一整节课，而且是这门课里"分水岭"级别的一节。

**所以第六条的完整表述是：如果你还没准备好写 evals，就还没准备好用 agent。**

</Drill>

### 反过来说：什么时候该用

三个条件要同时成立：

1. **步骤事先列不出来**——因为它取决于中间发现的东西
2. **需要根据结果改变路径**——不只是选一条已知的路
3. **错误代价可控**——出错了能撤销、能重试、能被人发现

三个都成立的典型例子：**修一个你还没定位的 bug。** 你不知道要读哪些文件（取决于代码结构）、不知道要读几个（取决于 bug 有多深）、改错了有 git 兜着。

这就是 Cursor 的 Agent 模式做的事，也是这门课的 capstone 要做的事。

## 五、实际项目长什么样

<Key>
**最常见的真实架构是：一个 workflow，里面有一个 agent 节点。**

不是因为它优雅，是因为它把不确定性关在了两成流量里。
</Key>

以那个客服系统为例：

```text
工单进来
  ↓
[分类]  ← 路由。便宜模型，temperature 0，16 token
  ↓
  ├─ 常见问题 → [模板回复]        ← 链式。固定两步，方差为零
  ├─ 账单问题 → [查账 → 回复]      ← 链式。步骤明确
  └─ 复杂问题 → [Agent]           ← 只有这里是 agent
                   ↓
              [人工审核]          ← 因为这条路径不确定，所以加闸
```

四个判断都能对上前面的判据：

- 分类是**已知的有限路径** → 路由
- 常见问题和账单问题**步骤能列出来** → 链式
- 复杂问题**列不出来** → agent
- agent 的输出**不确定** → 后面加人工审核

<CursorHook>

Cursor 的 Agent 模式也是这个结构，只是那道"闸"长得不一样：

- 改文件前给你看 diff（人工确认）
- 跑命令前问你（人工确认）
- 你能随时按停（取消，L05 那个 `signal`）

**它不是"更自主"，它是"自主 + 闸"。** 这两件事必须一起做——只有自主没有闸的产品上不了线，因为第一次它删错文件就是最后一次。

这也解释了一个你可能觉得别扭的体验：为什么 Cursor 有时候要问那么多次。因为每一次询问都是一道闸，而闸的密度是产品在"好用"和"不出事"之间选的位置。

</CursorHook>

## 六、这一节的纪律

1. **从最不自主的模式开始试，够用就停。** 自主性是成本不是功能。
2. **能列出步骤就写成代码。** 让模型重新发现你的流程图是纯浪费。
3. **链式必须有关口**，而且中止时要 `return` 不要 `throw`。
4. **模型给的标签不能直接用**，必须在枚举里查；兜底指向最强的那条路径。
5. **投票只在错误互相独立时有效**，而 `temperature=0` 的投票什么都不做。
6. **模型定的拆法必须校验**：非空、有上限、去重。
7. **打磨循环要两道闸**：轮数上限加改进检测，并保留历史最优。
8. **看 `p95/p50` 而不只看总花费**，但用之前先看分布是不是单峰。
9. **没准备好写 evals，就还没准备好用 agent。**

<PyMirror>

Python 版的三处真实差异，都不是语法糖：

**一 · `asyncio.gather` 的默认行为更危险。**

前面讲过：忘了 `return_exceptions=True` 会「全丢 + 静默烧钱」。这是 TS 那边 `Promise.all` 没有的问题。并发上限用 `asyncio.Semaphore`，比手写游标池干净。

**二 · `if not verdict` 和 `if verdict is not True` 不等价。**

链式的关口返回 `bool | str`。写成 `if not verdict` 的话，返回空字符串 `""` 会被当成"通过"——而返回空字符串正是"关口没通过但忘了写原因"这种情况。

Python 的真值判断比 TS 更容易在这里咬人，因为 `""`、`0`、`[]`、`{}` 全是 falsy。`l07/verify.py` 里有一条专门测这个。

**三 · 默认的投票 key 不能用对象本身。**

`dict` 和 `list` 都不可 hash，直接 `buckets[v]` 会 `TypeError`。TS 那边 `JSON.stringify` 天然绕过了这件事。参考实现用 `repr(v)`，`verify.py` 里有一条测它。

还有一个设计选择值得说：`Usage` 用了 `@dataclass(frozen=True)`，加法返回新对象而不是原地改。**原地改在 `gather` 并发下是 race**——而这种 bug 在小数据量下永远不复现。
