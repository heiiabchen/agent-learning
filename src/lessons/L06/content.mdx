L05 那个 agent 能跑了。现在让它做一件稍微大点的事——比如「读懂这个模块并改一个 bug」——它会在第七八步左右开始变蠢：忘了自己的目标、重复读同一个文件、给出和前面矛盾的结论。

不是模型不行。是**上下文满了**。

<Key>
Agent 和单次对话的根本区别在这里：**单次对话的上下文是你给的，agent 的上下文是它自己长出来的。** 每一步的工具结果都要拼回去，长度单调递增，而且增得比你想象的快。

管理这个增长，就是上下文工程。这一节是整个阶段二的地基。
</Key>

## 一、先把账算清楚

L02 讲过 API 是无状态的：每一步都要把全部历史重发。L05x 讲过为什么这既贵又让模型变笨。现在把两件事合起来算。

一个典型的代码 agent，跑十步：

| 步 | 新增内容 | 累积输入 | 这一步的输入费 |
|---|---|---|---|
| 1 | system + 工具定义 + 任务 | 2.5K | ¥0.005 |
| 2 | + read_file 结果（一个 300 行文件） | 6K | ¥0.012 |
| 3 | + search 结果（20 个匹配） | 9K | ¥0.018 |
| 4 | + read_file 结果 | 13K | ¥0.026 |
| 6 | + 两次工具结果 | 22K | ¥0.044 |
| 8 | + 两次工具结果 | 31K | ¥0.062 |
| 10 | + 两次工具结果 | 42K | ¥0.084 |

十步下来输入总量约 **200K token**，而实际"信息"只有 42K——**同样的内容被重发了平均五次。**

<Note title="两个数字要分清楚">

**峰值上下文**（42K）决定「会不会撞窗口上限」和「模型会不会变笨」。

**累积输入**（200K）决定「花多少钱」。

它们是不同的问题，需要不同的手段：

- 峰值问题靠**压缩**和**外置**——把内容挪出上下文。
- 累积问题靠**prompt 缓存**——内容还在上下文里，但不重复付全价。

**这两件事经常被混着讲，然后学的人就用错药。** 一个常见的错误是「我加了 prompt 缓存，成本降下来了，那上下文就不用管了」——缓存一分钱不省注意力，模型该变笨还是变笨。

顺带一个反直觉的推论：**缓存和压缩有轻微冲突。** 压缩会改写历史，而改写就意味着前缀变了，缓存作废（L05x 第 3 题）。所以压缩不能太频繁——每一步都压一次，缓存永远命不中。

</Note>

## 二、上下文预算：像分配内存一样分配它

不要等撞上限了再想办法。**开工前先给每一类内容划定额度。**

一个 128K 窗口的合理起点：

| 分区 | 额度 | 装什么 | 满了怎么办 |
|---|---|---|---|
| **系统区** | 3K | system prompt、工具定义 | 不该增长。增长了说明工具太多了 |
| **任务区** | 2K | 用户的原始请求、约束 | 不动。这是唯一不能压的东西 |
| **工作区** | 60K | 工具结果、中间产出 | 压缩或换出 |
| **摘要区** | 8K | 被压缩掉的历史的摘要 | 二次压缩 |
| **留白** | 55K | 给输出和意外留的余量 | —— |

<Pitfall title="留白不是浪费，是三重必需">

新手最容易犯的错是把窗口填到 90%。三个理由说明为什么不行：

**一 · 输出也占窗口。** 128K 是输入加输出的总额。你留 5K，模型想写一份 8K 的报告，直接被 `max_tokens` 截断。

**二 · 单次工具结果可能突然很大。** 你以为 `read_file` 平均 3K，然后模型读了一个 40 行注释加 9000 行生成代码的文件。**工具输出的分布是长尾的**，按平均值做预算必然会炸。

**三 · 注意力在 70% 之后明显衰减。** 这不是硬上限，是渐变。L05x 讲过原因：注意力零和加位置分布不均。实践中，**上下文用到 60% 就该开始压了**，等到 95% 已经晚了——那时候模型已经在犯错。

</Pitfall>

<Drill title="为什么工具定义算在「系统区」而且不该增长">

工具定义是每一步都要重发的固定成本。十个工具、每个 200 token，就是 2K × 步数。

但更重要的不是钱，是**注意力**。二十个工具定义摆在 system prompt 里，模型选错工具的概率显著上升——它要在二十个描述里判断哪个最相关，而这些描述都在抢同一份注意力。

这给出一条工程判据：**工具数量超过 10 个左右，就该考虑分组**。做法是按任务阶段只暴露相关的子集：

```ts
// 而不是永远暴露全部 20 个
const tools = phase === 'explore'
  ? [readFile, listDir, searchCode]
  : [readFile, writeFile, runTests]
```

这就是 L10 讲 MCP 时会遇到的同一个问题的另一面：**一个 MCP server 挂上来可能带 30 个工具，全暴露给模型是有代价的。**

</Drill>

## 三、三类手段，按代价从低到高

上下文工程的手段其实只有三类。**顺序很重要——很多人直接跳到第三类，结果做了大量无用功。**

### 手段一：一开始就别放进来（零成本）

最便宜的优化是不产生垃圾。这一类占了实际收益的大头，但常被跳过。

<Key>
**裁剪工具输出。** 这是收益最高的一条，因为它作用在源头。

`read_file` 返回整个 9000 行文件，是 agent 上下文爆炸的头号原因。L04 那个 `truncate` 就是干这个的，但光有它不够——还要给工具加分页参数。
</Key>

具体清单，按收益排序：

1. **工具结果加上限**（比如单次 4K），超了截断并明确告诉模型「还有多少、怎么拿下一段」
2. **给读取类工具加 `offset` / `limit`**，让模型自己分页，而不是你替它猜
3. **搜索结果只返回摘要**（文件名 + 行号 + 一行上下文），要细节让它再读
4. **删掉重复的空白和无意义内容**——格式化后的 JSON、大段缩进
5. **别把工具的原始报错整个塞回去**，堆栈信息里只有第一行有用

<Pitfall title="截断时必须给出路，否则你造了个死循环">

这是 L04 那条纪律的直接延续，但在这里后果更严重。

坏的截断：

```text
[内容过长，已截断]
```

模型不知道少了什么、也不知道怎么拿到剩下的，于是它可能**再读一次**——得到同样的截断，再读一次。这就是 L05 那个「重复调用」防线要拦的场景，而根源在这里。

好的截断：

```text
[前 200 行，共 1240 行。要看后面用 read_file(path, offset=200)]
```

**判断标准是一句话：截断信息里必须包含"下一步怎么做"。** 这条纪律在这门课里第三次出现了（L04 的工具错误、L05 的循环拦截、这里的截断），因为它是同一件事：**模型只能看到你给它的东西，你不给出路它就没有出路。**

</Pitfall>

### 手段二：把内容挪出去（低成本）

内容还需要，但不需要一直在上下文里。

**外置到文件系统。** 这是 coding agent 的标准做法，也是最优雅的一种：

```text
不好：把 3000 行分析结果留在上下文里
好：  写到 notes.md，上下文里只留「分析结果在 notes.md，
      结论是 X」，需要细节时再 read_file
```

为什么这个做法好：**文件系统本来就是外部记忆，而且 agent 已经有读写工具了。** 你不需要新造任何机制。

**外置到结构化状态。** 任务清单、已完成项、待办项这类东西，放在一个结构化对象里，每轮只渲染当前状态而不是全部历史：

```ts
// 上下文里放这个（几十 token）
<progress>
  已完成：定位 bug（src/auth.ts:142）、写复现测试
  进行中：修复
  待办：跑全量测试、更新 CHANGELOG
</progress>

// 而不是把「定位 bug」那三步的全部工具调用和结果都留着
```

这是 L08 记忆与状态那一节的入口。这里先记住一条：**状态和历史是两回事。** 历史是发生过的事，状态是现在的样子。**模型需要的通常是状态。**

### 手段三：压缩历史（有成本，有风险）

到这一步才开始动已经在上下文里的东西。之所以放最后，因为它有三个真实代价：

- **要花钱**：压缩本身是一次模型调用
- **会丢信息**：而且你不知道丢了什么
- **毁缓存**：改写历史让前缀失效

三种做法，各有适用场景：

| 做法 | 怎么做 | 适合 | 风险 |
|---|---|---|---|
| **滑动窗口** | 只留最近 N 轮 | 短任务、对话 | 早期的关键决定丢了 |
| **摘要压缩** | 让模型总结前 N 轮，用摘要替换 | 长任务 | 摘要漏掉关键细节 |
| **分层压缩** | 老的压得狠、近的留全文 | 很长的任务 | 实现复杂 |

<Drill title="摘要压缩的三个必须">

摘要压缩最容易做坏。做坏之后的表现是 **agent「忘了」自己已经做过某件事，然后重做一遍**——而且这个失败很难归因，因为它看起来像模型笨。

三条必须：

**一 · 摘要要有固定结构，不能自由发挥。**

「总结一下前面的对话」得到的是一段散文，模型下一步没法用。要这样：

```text
把下面的历史压缩成结构化摘要。必须包含：
<goal>原始任务，一字不改地保留</goal>
<done>已完成的事，每条带结论</done>
<found>发现的关键事实（文件路径、函数名、行号要保留）</found>
<failed>试过但失败的方法，以及失败原因</failed>
<next>下一步计划</next>
```

**二 · `<failed>` 这一节最容易漏，而它最重要。**

没有它，agent 会把失败过的方法再试一遍。这是长任务里最常见也最贵的浪费——它不只是重复，还会陷入循环：试 A 失败、试 B 失败、忘了、再试 A。

**三 · 原始任务永远不压。**

用户那句原话必须原文保留在上下文里。**摘要摘要摘要之后，目标最容易漂移**——第三次压缩后的 agent 常常在做一件和最初请求只有远亲关系的事。

顺带一个实现细节：**压缩的时机要用「触发线 + 保留量」两个参数**，不要压到一半就停。比如「用到 60% 时压到 30%」，而不是「用到 60% 时压掉 10%」——后者会让你在 60% 附近反复压缩，每次都毁一遍缓存。

</Drill>

<Note title="sub-agent：另一种压缩，而且往往更好">

有一个手段常被忽略：**把子任务扔给一个新的 agent，只把结果拿回来。**

```text
主 agent 上下文：
  「让 sub-agent 去调查登录流程」
  ← 只拿回来 300 token 的结论

而 sub-agent 内部烧掉的 30K 上下文，主 agent 一个字都不用看。
```

这本质上是**用进程隔离换上下文**。它比摘要压缩好的地方在于：**丢弃是发生在信息产生的地方**，由那个真正理解细节的 agent 决定什么值得报告——而摘要压缩是事后由一个只看到文本的模型来猜什么重要。

代价也要说清楚：

- 多一次完整的 agent 启动开销（system prompt、工具定义重新发一遍）
- sub-agent 看不到主上下文，可能问出已经回答过的问题
- **调试难度上升**：出问题时你要看两层 trace

L11 会专门讲多 agent 的成本陷阱。这里只提一条判据：**当子任务的中间过程你确定不需要看时，用 sub-agent；否则别用。**

</Note>

## 四、把「变笨」变成可观测的

上面所有手段都需要一个前提：**你得知道现在的上下文长什么样。** 而绝大多数人是靠感觉的——「好像变笨了」。

最小的可观测性，三个数字：

```ts
interface ContextStats {
  tokens: number          // 当前总量
  ratio: number           // 占窗口比例
  breakdown: {            // 各分区占用
    system: number
    task: number
    toolResults: number
    summary: number
  }
}
```

<Key>
`breakdown` 是关键。总量告诉你「快满了」，但只有分区占比能告诉你「该压哪一块」。

**实践中八成的情况是 `toolResults` 一块占了 70% 以上**——而这一块正是手段一（源头裁剪）能处理的。你去做摘要压缩就是用错药了。
</Key>

<CursorHook>
你在 Cursor 里应该见过上下文用量的提示。现在你知道它为什么重要了。

也可以反过来观察：当你的对话变长、Cursor 开始「忘了」你前面说的约束时，那就是这一节讲的现象。而 Cursor 内部做的事和你要写的差不多——裁剪工具输出、压缩历史、必要时开 sub-agent。

一个可以立刻用上的习惯：**长对话里，如果发现它开始重复或者偏题，最有效的操作不是继续解释，而是开新对话并把关键约束重新说一遍。** 这就是手动执行一次「压缩到干净状态」。
</CursorHook>

## 五、几个反直觉的地方

<Drill title="为什么「把所有相关代码都放进去」通常是错的">

直觉是：给模型更多信息，它做得更好。

实际上有一个明确的拐点。原因有两个，都在 L05x 讲过：

1. **注意力被稀释**——真正相关的那 200 行，混在 20000 行里
2. **无关信息会误导**——模型看到一个名字相似但无关的函数，可能就用了它

这解释了一个实践观察：**精确的 2K 上下文常常打败泛泛的 50K 上下文。** 也解释了为什么 L09 的检索质量比检索数量重要得多——召回 50 个片段里有 3 个相关，效果可能不如只给那 3 个。

但也别过度反向：上下文太少时模型会猜，而猜出来的东西看起来和真的一样。**这里没有普适的最优值，只有一条可操作的方法：把上下文量当成一个可调参数，用 evals 量出你这个任务的拐点在哪。** 这是 L12 的活。

</Drill>

<Pitfall title="压缩之后忘记更新缓存断点">

如果你在用 prompt 缓存（L02），压缩会把缓存全部作废——因为历史被改写了，前缀变了。

这带来一个容易被忽略的后果：**压缩之后的那一次调用会特别贵**，因为要重新 prefill 全部内容。如果你在一个循环里频繁压缩，可能出现「为了省钱做压缩，结果比不压更贵」。

判断方法是算一笔账：

```text
压缩省下的：(原长度 - 压后长度) × 后续步数 × 输入单价
压缩花掉的：压缩调用本身 + 缓存失效导致的一次全额 prefill
```

**当剩余步数少的时候，不压更便宜。** 所以压缩的触发条件应该看「预计还要走多少步」，而不只是看当前长度。这也是为什么 L05 那个 `runAgent` 要返回 `steps` 和 `usage`——这些数字不是给人看的，是给决策用的。

</Pitfall>

## 六、这一节的纪律

1. **先算账，再动手。** 峰值和累积是两个问题，压缩和缓存是两种药。
2. **开工前划预算。** 系统区、任务区、工作区、摘要区、留白。
3. **手段按代价排序：源头裁剪 → 外置 → 压缩。** 大多数人跳过前两步。
4. **截断必须给出路。** 否则你造了个死循环。
5. **原始任务永不压缩。** 目标漂移是长任务的头号失败模式。
6. **`<failed>` 是摘要里最重要的一节。** 没有它就会重复失败。
7. **看 breakdown 而不只是总量。** 不知道该压哪块就是在瞎压。
8. **上下文量是可调参数，靠 evals 定，不靠感觉。**

<Lab title="本节的三个任务">

```bash
# TypeScript 主通道
pnpm budget       # 任务一：上下文计量与预算分区
pnpm compress     # 任务二：三种压缩策略 + 结构化摘要
pnpm longrun      # 任务三：让 L05 的 agent 跑一个长任务，四种策略对比
pnpm verify:l06

# Python 副通道
uv run python -m l06.budget
uv run python -m l06.compress
uv run python -m l06.longrun
uv run python -m l06.verify
```

任务三是这一节的重点，也是第一次你能**量出来**上下文工程的价值。它把同一个长任务跑四遍：什么都不做、只压缩、只裁剪、两个都做。

先看峰值上下文那一列，再看最后一轮的压缩次数。它是 0——把源头裁剪做够之后，压缩根本没到触发线。这就是「手段按代价排序」的意思，而大多数人跳过第一档直接做第三档，于是一边漏水一边擦地。

</Lab>

<PyMirror>

这一节的 Python 侧有一个真实的坑：**token 计数。**

TS 里你大概会这么算：

```ts
const tokens = Math.ceil(text.length / 2.5)  // 粗估
```

Python 里很容易顺手装个 `tiktoken` 然后觉得精确了：

```python
import tiktoken
enc = tiktoken.encoding_for_model("gpt-4")
tokens = len(enc.encode(text))   # 看起来精确，其实不对
```

**它算的是 OpenAI 的分词器，而你用的是 DeepSeek。** 两者对中文的切分差异可以到 20% 以上（L01 讲过 BPE 的语料依赖）。用它做预算控制，会在你最不希望的时候差出几千 token。

正确的做法有两条，按可靠性排序：

1. **用服务端返回的 `usage`。** 这是唯一权威的数字。代价是它只在调用之后才有——所以做**事后校准**：用估算值做决策，用真实值修正估算系数。
2. **实在需要事前精确值时，找对应模型的官方分词器。** DeepSeek 有开源的 tokenizer 配置。

而 lab 里我用的是第 1 条加一个粗估函数。因为对预算控制来说，**估算误差 10% 是可以接受的（留白就是为这个准备的），而"以为自己精确其实差 20%"是不可接受的**——它会让你在 breakdown 里看到一个假数字，然后做出错误的压缩决策。

这是一个更普遍的教训：**一个带着已知误差的估计，比一个假装精确的错误值有用得多。**

---

还有两个坑不在"计数准不准"这条线上，但更容易让你的代码直接崩。它们都出自同一个源头：**Python 的 SDK 返回的是 pydantic 模型对象，不是 dict。**

L05 的 `run_agent` 把 `res.content` 原样放回历史里（必须原样，否则模型看不到自己要求过什么）。于是 `messages` 里 assistant 那条装的是**对象**，而你手写的 user 那条装的是 **dict**。同一个 list 里两种形态混着。

```python
for block in content:
    kind = block.get("type")   # SDK 对象没有 .get() → AttributeError
```

坏在哪：你造测试数据的时候一定用 dict，所以这个 bug 单元测试全绿，跑 demo 也全绿，**只有接上真 agent 才炸**。而且它炸在计量函数里——一个本来只是"数几个 token"的辅助函数，把整个任务干掉了。

`shared/context_budget.py` 里那个 `field_of` helper 就是为这个存在的。TS 那边完全不需要，因为 SDK 的块本身就是普通对象。

第二个坑是它的连带伤害：

```python
json.dumps(block["input"])
# ensure_ascii 默认 True → 一个汉字变成 \uXXXX 六个字符，估算翻六倍
# 入参里混进一个非 JSON 类型 → 直接抛 TypeError
```

两个参数都要传：`json.dumps(v, ensure_ascii=False, default=str)`。前者关乎准确，后者关乎别崩。

顺着这条线往下想会得到一条通用的判断：**在动态语言里写要遍历外部数据结构的代码时，"这个字段一定存在、一定是这个类型"是靠人记的，不是靠编译器保证的。** 所以这类函数要么显式兼容多种形态，要么在入口处收窄一次。选哪个都行，但不能不选。
