到这里为止，模型只能说话。这一节让它伸出手。

先破除一个幻觉，因为它会影响你后面所有的设计判断：**模型不会执行任何东西。** 它只会输出一段结构化的「我想调用 read_file，参数是这些」。真正去读文件的是你的代码。工具调用不是模型的能力，是**你给它的一个协议**。

<Key>
工具的描述文字就是 prompt，只是它长在 JSON Schema 里。你花在 `description` 字段上的功夫，比花在 system prompt 上的更值钱——因为它离决策点最近。
</Key>

## 一、一次工具调用的完整往返

四个回合，缺一不可。先把全貌看清楚，再看每一步的坑。

```text
① 你 → 模型     messages + tools 定义
② 模型 → 你     stop_reason: 'tool_use'，content 里有 tool_use 块
③ 你执行工具，把结果作为 tool_result 发回去
④ 模型 → 你     基于结果继续（可能再要工具，可能给最终答案）
```

代码形状：

```ts
// ① 带上工具定义
const res = await client.messages.create({
  model, max_tokens: 2048,
  tools: [{
    name: 'read_file',
    description: '读取一个文本文件的完整内容',
    input_schema: {
      type: 'object',
      properties: { path: { type: 'string', description: '相对于仓库根的路径' } },
      required: ['path'],
    },
  }],
  messages: [{ role: 'user', content: '看看 src/index.ts 写了什么' }],
})

// ② stop_reason === 'tool_use'，content 里有这种块：
// { type: 'tool_use', id: 'toolu_01ABC', name: 'read_file', input: { path: 'src/index.ts' } }

// ③ 关键：assistant 那一整条要原样放回历史，然后用 user 角色回填结果
messages.push({ role: 'assistant', content: res.content })
messages.push({
  role: 'user',
  content: [{ type: 'tool_result', tool_use_id: 'toolu_01ABC', content: '文件内容…' }],
})
```

<Pitfall title="第 ③ 步有三个必须同时做对的地方">

这三条我都见过有人写错，而且错法都不报错，只表现为「agent 有点笨」。

**一，assistant 的那条消息必须原样放回去，包括 `tool_use` 块。** 只把文本部分放回去、丢掉工具调用块，模型下一轮就看不到自己刚才要求过什么。它会重新要求一次，于是你得到一个死循环——而且是那种烧钱的死循环。

**二，`tool_result` 的角色是 `user`，不是什么特殊角色。** 这一点很反直觉：结果是你的代码产出的，怎么是 user 说的？因为协议里只有两个角色。**「工具的输出」在结构上属于「给模型的输入」，而给模型的输入就是 user。** 想通这一点，L05 的 agent loop 你就不会写错。

**三，`tool_use_id` 必须精确对应。** 模型靠这个 id 把结果和请求配起来。填错或者漏填，好一点的情况是 400，坏一点的情况是模型把结果配到错的调用上——那个 bug 你会查很久。

</Pitfall>

<Drill title="模型是怎么「学会」调用工具的">

值得知道，因为它解释了后面几乎所有的工具设计原则。

工具定义并不是走了什么特殊通道。SDK 把你的 `tools` 数组**序列化成文本，拼进了 prompt**（具体格式各家不同，但本质如此）。模型看到的大致是「你有这些工具可用，各自长这样」，然后它按训练时学到的格式输出一个工具调用。

这个事实推出四条结论，每一条都会在这节课后面出现：

**一，工具定义花 token，而且每轮都花。** 十个工具、每个描述两百字，就是每轮固定几千 token 的开销。L15 会专门算这笔账。

**二，`description` 字段是模型唯一的判断依据。** 它看不到你的实现，看不到你的注释，只能看到这段字符串。描述写得含糊，模型就选错工具——**这不是模型笨，是你没说清楚**。

**三，「模型编造不存在的工具」有了解释。** 它在续写一个模式。你提供了 `read_file` 和 `write_file`，它很容易「顺手」输出一个 `delete_file`——因为在训练数据里这三个总是一起出现。这不是幻觉发作，是**模式补全**。所以你的执行层必须假设工具名是不可信输入。

**四，工具越多，选择越差。** 这不是玄学，是注意力预算（L01）：二十个工具的描述互相竞争同一份注意力。经验阈值是十个左右，超了就该考虑分组或者分层（L11 的 sub-agent 就是一种解法）。

</Drill>

## 二、Schema 设计：模型看得见的部分

工具的 schema 是给模型看的**接口文档**，不是给 TypeScript 看的类型。这两者的写法要求不一样。

对比一下：

```ts
// ✗ 类型对了，但模型不知道怎么用
{
  name: 'search',
  description: '搜索',
  input_schema: {
    type: 'object',
    properties: { q: { type: 'string' }, n: { type: 'number' } },
  },
}

// ✓ 每个字段都在回答模型会有的疑问
{
  name: 'search_code',
  description:
    '在仓库里按正则搜索代码。返回最多 n 条匹配，每条含文件路径和行号。' +
    '只搜索已跟踪的文本文件，不搜 node_modules 和二进制文件。',
  input_schema: {
    type: 'object',
    properties: {
      pattern: { type: 'string', description: '正则表达式，语法同 ripgrep' },
      max_results: {
        type: 'integer',
        description: '返回条数上限，默认 20。超过 50 会被截断到 50。',
        minimum: 1,
        maximum: 50,
      },
    },
    required: ['pattern'],
  },
}
```

六条实操规则：

1. **名字用动词_名词。** `read_file` 而不是 `file` 或 `reader`。工具是动作。
2. **`description` 里写清「返回什么」。** 模型要靠这个决定拿到结果后干什么。
3. **写清边界和限制。** 「不搜 node_modules」这类信息能避免模型走进死路。
4. **`required` 要准确。** 标成必填的模型一定会给，没标的它可能省略——省略之后你的代码拿到 `undefined`。
5. **枚举优于自由字符串。** `{ enum: ['asc', 'desc'] }` 比描述里写「升序或降序」可靠得多。
6. **`minimum`/`maximum` 要写，但别指望它。** 模型**经常**越界。这是提示，不是校验——真正的校验必须在你的代码里。

<Pitfall title="Schema 里的约束不是校验">

这条是本节最容易被想错的地方，而且后果直达安全层。

`input_schema` 是给模型的**建议**。服务端不校验你的 schema 是否被遵守，模型也不保证遵守。你会实实在在地收到：

- `max_results: 500`，尽管你写了 `maximum: 50`
- 缺少你标了 `required` 的字段
- `path` 是 `"../../etc/passwd"`，尽管你在描述里写了「相对于仓库根」
- 多出来一个你没定义的字段

**所以每个工具的第一行代码都是校验。** 顺序永远是：先校验，再执行。

而且要意识到这是什么性质的输入。工具参数由模型生成，而模型的上下文里有用户输入、有检索回来的文档、有文件内容——**其中任何一个都可能是攻击者控制的**。所以工具参数在信任级别上等同于**未经处理的用户输入**。

L14 会正面讲这件事，但纪律现在就要立起来：**把工具参数当成 HTTP 请求体来对待。** 你不会直接把请求体里的路径拼进 `readFileSync`，这里也一样。

</Pitfall>

## 三、工具报错：返回给模型，不要抛出去

这是新手和熟手差别最明显的一处，而且改起来只要几行代码。

直觉写法：

```ts
// ✗ 工具失败就抛
async function readFile(input: { path: string }) {
  return await fs.readFile(resolve(root, input.path), 'utf8')  // 文件不存在 → throw
}
```

这样 agent loop 直接崩掉。但**失败是正常流程的一部分**——模型猜错文件名是完全预期的行为，它猜错了应该有机会重新猜。

正确写法：把错误变成 `tool_result`，并打上 `is_error`：

```ts
messages.push({
  role: 'user',
  content: [{
    type: 'tool_result',
    tool_use_id: id,
    is_error: true,
    content: `文件不存在：${input.path}。用 list_dir 看看这个目录下有什么。`,
  }],
})
```

<Note title="错误信息要给出路，这是 L03 那条纪律的复现">

对比两条错误信息：

```text
✗ ENOENT: no such file or directory, open '/repo/src/uitls.ts'
✓ 文件不存在：src/uitls.ts。用 list_dir 列出 src/ 看看实际的文件名。
```

第一条模型大概能看懂，但它的下一步动作是**重试同样的路径**，或者随机换一个猜法。第二条直接给了下一步。

这就是 L03 「约束要配一条出路」在工具层的样子。你的错误信息是给模型看的 prompt，**它的评价标准不是「准确描述了故障」，而是「模型读完知道该干什么」。**

顺便：第一条还泄露了绝对路径 `/repo`。上下文里的东西模型都可能在后面复述出来，敏感信息不要放进工具输出。

</Note>

那么什么时候才该真的抛错？判据很清晰：

| 情况 | 处理 | 为什么 |
|---|---|---|
| 文件不存在、命令返回非 0、参数不合法 | 回 `tool_result` + `is_error` | 模型能换个做法 |
| 工具名不存在 | 回 `tool_result` + `is_error` | 模型编的，告诉它有哪些真工具 |
| 路径越界、权限不足 | 回 `tool_result` + `is_error`，**同时记一条 warn** | 模型该知道被拒了；你该知道它试了 |
| 你的代码有 bug、数据库连不上 | 抛出去 | 模型无能为力，重试也没用 |

一句话：**模型能改变结果的，告诉它；不能的，别浪费 token 和轮次。**

## 四、并行工具调用

一条 assistant 消息里可以有**多个** `tool_use` 块。模型判断几件事互不依赖时会一次全要。

这是真实的性能优化——三次串行读文件是三个往返，并行是一个。但它带来两个必须处理对的地方。

**一，所有结果必须放在同一条 user 消息里。**

```ts
// ✓ 一条消息，多个 tool_result
messages.push({
  role: 'user',
  content: results.map((r) => ({
    type: 'tool_result' as const,
    tool_use_id: r.id,
    content: r.output,
  })),
})
```

分成多条会违反 L02 那条「必须严格交替」——连续两条 user。你的端点可能不报错（L02 的探测已经证明它不报），但这属于**面向协议编程**那条纪律，别赌。

**二，执行可以并发，但要有池子。**

L00 写的 `pooled` 这里就用上了。模型一次要八个文件读取，你不该一次开八个句柄——尤其当工具里有「跑测试」这种重量级操作时。

<Pitfall title="并行工具调用里的顺序陷阱">

`tool_result` 的**顺序**不必和 `tool_use` 一致（靠 id 配对），但有个实际影响容易忽略：

模型是按顺序读上下文的。如果你把八个结果按「谁先执行完谁在前」排列，那**每次运行的顺序都不一样**——同样的任务、同样的文件，两次跑出来的上下文不同。后果有两个，都不小：

1. **前缀缓存失效。** L02 讲过，缓存要求逐 token 一致。顺序抖动等于每轮都重新付全价。
2. **不可复现。** 出了问题你没法重跑同一个上下文。这会让 L13 的调试变成猜谜。

所以：**按 `tool_use` 在原消息里出现的顺序回填结果**，哪怕执行是乱序完成的。用 `Promise.all` 而不是逐个 push——`Promise.all` 保序，这是它和「谁完成谁先来」的关键区别。

</Pitfall>

## 五、工具粒度：这是架构决策

给模型一个 `run_shell_command` 还是给二十个专用工具？这个问题没有标准答案，但有清晰的权衡轴。

| | 粗粒度（`run_shell`） | 细粒度（`read_file`、`list_dir`…） |
|---|---|---|
| 模型的自由度 | 极高，能组合出你没想到的做法 | 受限于你提供的动作 |
| 可控性 | 极差，`rm -rf` 也在能力范围内 | 好，每个动作的边界是你写的 |
| token 成本 | 一个工具定义，便宜 | 十个定义，每轮都付 |
| 出错率 | 高，shell 语法本身容易错 | 低，schema 约束了形状 |
| 可观测性 | 差，你只知道跑了条命令 | 好，每个动作可以单独记录和统计 |
| 权限控制 | 几乎做不到 | 每个工具单独授权 |

我的判断，以及理由：

**从细粒度开始，按需合并。** 因为细粒度的错误是「模型做不到某件事」——它会告诉你，你补一个工具就行。粗粒度的错误是「模型做了你没预期的事」——你可能在事后才发现。

**这两类错误的代价不对称，所以默认值应该偏保守。**

<CursorHook>

Cursor 的工具集就是这个权衡的一个实际答案，而且它偏细：读文件、列目录、按正则搜、编辑文件、跑终端命令。

注意两件事：

**一，「跑终端命令」这个粗粒度工具存在，但它要你确认。** 这正是上面那张表的结论——粗粒度工具的可控性靠**人工审批**补回来。不是不给这个能力，是给它加一道闸。

**二，编辑文件是一个独立工具，而不是「用 shell 跑 sed」。** 因为独立工具能做三件 shell 做不到的事：给你看 diff、支持撤销、以及在写入前校验。

你自己的 agent 到 L17 会面对同一组选择。届时可以回来看这张表。

</CursorHook>

<PyMirror>

Python 这边工具定义的写法有个生态层面的差异值得知道：**大家几乎都不手写 JSON Schema。**

主流做法是用 Pydantic 定义模型，然后自动导出 schema：

```python
from pydantic import BaseModel, Field

class ReadFileInput(BaseModel):
    path: str = Field(description="相对于仓库根的路径")

# .model_json_schema() 直接产出 input_schema 需要的形状
```

这个做法的好处是真实的：**schema 和校验用的是同一份定义**，不会出现「schema 说 required 但代码没检查」这种漂移。而这个漂移在手写 schema 的项目里非常常见——我在 TS 那边就是靠 verify 里的测试去卡它。

代价是你多了一个依赖，而且 Pydantic 的错误信息对模型不太友好（一大坨嵌套的校验错误），通常要再包一层转成人话。

TS 这边的对等物是 `zod` + `zod-to-json-schema`，思路完全一样。这节课我故意手写，理由是**手写一遍你才知道模型看到的到底是什么**。第二遍就该上工具了。

L11x 会讲 Pydantic 为什么成了 Python agent 生态的地基——它不只是校验库，是整个类型契约层。

</PyMirror>

## 六、这节课的纪律

1. **工具参数是不可信输入。** 每个工具第一行代码是校验。
2. **`description` 是 prompt。** 写清返回什么、边界在哪。
3. **失败回 `tool_result`，不抛。** 除非模型无能为力。
4. **错误信息要给出路。** 判据是「模型读完知道干什么」。
5. **并行结果按原顺序回填。** 保缓存，保可复现。
6. **从细粒度工具开始。** 两类错误的代价不对称。

下一节把这些零件装进一个循环。你会发现 agent 的核心真的只有几十行——**难的不是循环，是循环的终止条件和预算控制。**
