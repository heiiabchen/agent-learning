你的 agent 现在能跑完一个任务。这一节要问的是两件事：**它跑到第 38 步崩了怎么办**，以及**它明天还认不认识你**。

这两件事听起来是同一个问题的两半，实际上是两个完全不同的工程问题——而把它们混在一起，是这一节最主要的坑。

<Key>
**状态和记忆不是一回事，混在一起会同时做坏两件事。**

- **状态**是「这次任务进行到哪了」。它必须精确、必须可恢复、任务结束就该扔掉。
- **记忆**是「关于这个用户/项目我知道什么」。它必须可疑、必须有出处、而且**它出错是永久性的**。

用同一套机制存两者的后果：状态里混进了推测（于是恢复恢复出一个错的现场），记忆里混进了临时数据（于是六个月后 agent 还记着你某天调试过的那个函数）。
</Key>

## 一、先打掉一个几乎人人都会犯的错

问「怎么做会话持久化」，十个人有九个的第一个答案是：**把 `messages` 数组存下来。**

这个答案的问题不在于它不工作，而在于它**看起来工作**。

<Pitfall title="transcript 是历史，不是状态">

存下 `messages` 之后，你手上有一串消息。现在回答这三个问题：

1. **「哪些操作真的执行完了」**——你可以数 `tool_result` 块。但**崩在 `tool_use` 和 `tool_result` 之间的那一次没有任何记录**。
2. **「同一个操作会不会被重复执行」**——没有幂等键，没法判断。
3. **「现在该从哪一步继续」**——只能数消息条数，而这个数会随压缩（L06）而改变。

第一条是致命的那条：**transcript 里「没做」和「做了但没记上」长得完全一样。** 而恰恰是这两者的区别决定了要不要重做。

再加上两条 transcript 天生的毛病：

- **它单调增长。** 存 transcript 等于把 L06 那个上下文爆炸问题搬到磁盘上。
- **它不可查询。** 「这个 agent 现在卡在哪」要靠人读一遍才知道，没法用代码判断，也没法做监控面板。

</Pitfall>

正确的做法是存**事件日志**加**派生状态**：

```text
日志（append-only，是事实）        状态（算出来的，是快照）
──────────────────────────       ─────────────────────────
task    "给三个客户发对账单"        task:      "给三个客户发对账单"
intent  1 send_email a@x.com      steps:     2
outcome 1 ok                      completed: { k1, k2 }
intent  2 send_email b@x.com      pending:   [ send_email c@x.com ]
outcome 2 ok                      finished:  false
intent  3 send_email c@x.com
        ← 进程死在这里
```

`state = reduce(events)`。这是个纯函数，任何时候重算都得到同一个结果。

<Note title="为什么 intent 和 outcome 必须是两条事件">

这是整个设计里唯一真正非平凡的决定。

写成一条（「第 3 步调用了 `send_email` 并成功了」）的话，你只有两种状态可表达：**做了**、**没记录**。而崩溃之后最常见的状态是第三种：**打算做，但不知道做没做。**

拆成两条之后，「有 intent 没有 outcome」这个组合就精确地表达了那个第三种状态。它对应的是进程死在下面这个窗口里：

```text
写 intent  ─────┐
                │  ← 副作用（写文件、发请求、扣款）在这个窗口里发生
执行工具        │
                │
写 outcome ─────┘
```

**这个窗口消灭不掉。** 你能做的只是让它变窄，以及在恢复时诚实地承认「这一条我不知道」。

</Note>

### 存储格式：JSONL，三条理由

一条比一条实用：

1. **追加是 O(1)。** JSON 数组每次都要读全文、改、写回全文。
2. **崩溃只损坏最后一行。** 数组格式崩溃之后整个文件都不是合法 JSON。
3. **能 `tail -f`。** 排查线上问题的时候这一条比前两条都实用。

<Pitfall title="读日志必须容忍坏行，但必须把坏行数出来">

崩溃的时候最后一行常常是写了一半的：

```text
{"seq":47,"at":1767225600,"t":"outcome","step":23,"idem":"a3f9","ok":true,"content":"..."}
{"seq":48,"at":1767225601,"t":"intent","step":24,"tool":"send_email","input":{"to":"c@x
```

为这一行放弃整个会话，等于**用一个小故障换一个大故障**。

但只做「跳过」是不够的——那样你永远不知道线上崩过多少次。所以要有一个 `corrupt` 计数，而且它要进日志和监控。

这就是那条纪律的第六次出现：**把静默失败变成响亮失败。**（L02 未知模型不按 0 计价、L03 截断输出不当有效、L04 未知工具不静默跳过、L06 未知块类型抛错、L07 空计划报错。）

</Pitfall>

### 幂等键：L05 那个坑的同一个版本

```ts
idemKey(sessionId, tool, input)   // → 'a3f91c...'
```

三个细节各有理由：

- **必须按 key 排序后序列化。** 直接 `JSON.stringify` 的话，SDK 换一版字段顺序，你的幂等防线就**静默失效**了。这和 L05 的 `repeatKey` 是完全同一个坑。
- **必须把 `sessionId` 拌进去。** 否则两个会话的相同调用会互相「跳过」对方的操作。
- **`sha256` 取前 16 位就够。** 它只需要在一个会话内唯一，不是密码学用途。

## 二、恢复：代码在某个位置上没有正确答案

有了日志和状态，恢复看起来只是「从 `pending` 那一步接着跑」。但 `pending` 里的操作**可能做了也可能没做**，所以要不要重放取决于**重放这个操作会不会出事**。

于是每个工具都必须声明一件事：

| 可重放性 | 含义 | 例子 | 恢复时 |
|---|---|---|---|
| `pure` | 没有副作用 | `read_file`、`search` | 直接重放 |
| `idempotent` | 有副作用但重复执行结果相同 | `write_file`（覆盖写） | 直接重放 |
| `once` | 重复执行会出事 | `send_email`、`create_order`、`git_commit` | **问人** |

<Key>
**这个分类必须由工具的作者声明，不能让恢复逻辑猜。**

猜的话，新加一个工具就是一次潜在事故——因为默认值总会在某一天用错。而这类事故的特征是：加工具的人根本不知道恢复逻辑存在。
</Key>

<Drill title="pending 里有一个 once 工具，你怎么处置">

这是这一节最重要的一道题，而它的答案是：**代码在这里没有正确答案。**

先看两个「聪明」的默认各自的后果：

| 默认行为 | 后果 |
|---|---|
| **都重做** | 客户收到两封对账单 / 下了两个单 / 多了一次转账 |
| **都跳过** | 该发的邮件没发，而**日志显示这一步「处理过了」** |

第二个更可怕，因为它是静默的。第一个至少客户会投诉。

而你**不能**通过「查一下到底做没做」来解决——线上那个状态你查不到，或者查得到但要等几分钟，或者要花钱查，或者对方系统的最终一致性还没收敛。

所以恢复计划必须有第三个出口：`ask`。**停下来，把这一条交给人。**

这不是偷懒。在这个位置上，`ask` 是唯一诚实的做法：你确实不知道，而假装知道会造成事故。

---

**但真正的工程解法是往上一层走，让这个问题不再出现：**

1. **让副作用本身幂等。** 发邮件时带一个去重键，服务端保证同键只发一次。这样 `once` 就降级成了 `idempotent`。
2. **把「发送」拆成「入队 + 消费」。** 入队幂等（同键覆盖），消费由队列保证恰好一次。

★ **恢复逻辑处理不了的问题，要在副作用的设计层面解决。**

这条推论比它看起来更普适：每次你发现「代码在这里必须猜」，正确的反应是回头看**这个位置为什么会需要猜**。

</Drill>

### 快照：加速，但不是事实来源

日志长了之后每次恢复都要 O(n) 回放。快照解决这个，但它有两个必须做对的地方：

<Pitfall title="快照必须记 upto，而且必须原子写">

**一 · 快照必须记 `upto`（覆盖到第几条事件）。**

没有它你没法把快照和日志拼起来——要么重复应用事件，要么漏掉事件，而**两者都是静默的**。

**二 · 写快照必须先写临时文件再原子替换。**

`rename` 在同一个文件系统内是原子的，所以读者永远看到完整的旧版或完整的新版。直接写目标文件的话，崩在中间会留下一个半截快照——

而**快照坏了比没有快照更糟**：你会从一个错误的状态继续跑，而这个错误状态看起来完全正常。

（Python 这边用 `os.replace` 而不是 `os.rename`，理由在下面的 `PyMirror` 里。）

</Pitfall>

所以要守住一条：**快照和日志必须是两个分开的文件。** 快照坏了就丢掉它、从日志重放。日志才是事实来源。

## 三、长期记忆：主要风险不是记不住

换个话题。上面讲的都是**这一次任务**的状态，现在讲**跨会话**的那部分。

大多数人对长期记忆的第一个担心是「怎么让它记住更多东西」。这个担心搞错了方向。

<Key>
**长期记忆的主要风险不是记不住，是记错。**

记不住只是效率损失——重新问一遍就行，代价是一次交互。

记错是**永久性的**：一条错误的事实写进去之后，每一次会话都会读到它、基于它做决定、并且**从它推导出新的（同样错误的）结论**。
</Key>

所以这个模块的大部分代码不是「怎么存」，是「什么不许存」。

### 一条真实的漂移链

```text
depth 0（观察）：用户说「这个项目用 pnpm」
depth 1（推导）：用户偏好现代工具链
depth 2（推导）：用户会接受激进的重构建议
depth 3（推导）：可以不问就改动构建配置
```

第四条已经是一个会造成事故的「事实」，而它和第一条在存储里长得**一模一样**——都是一行 `key = value`。

这就是为什么 `Fact` 要有 `kind` 和 `depth` 两个字段：

- `observed`——直接看到的，`depth` 是 0
- `derived`——推导出来的，`depth` 逐层加一

而 `maxDepth` 默认是 **1**，意思是：**不允许从推导结果再推导。**

这个限制看起来严苛，但**漂移是复合的**——每一层推导都把误差乘一次，放开一层就挡不住了。

### 四道闸

`remember()` 有四道闸，每一道对应一类污染：

| 闸 | 拦什么 | 失败方式 |
|---|---|---|
| **必须有 `source`** | 无法追溯的事实 | 抛异常 |
| **`observed` 必须有 `evidence`** | 把推测伪装成观察 | 抛异常 |
| **`depth` 不超上限** | 复合漂移 | 返回 `false` |
| **`confidence` 不低于下限** | 蒙的 | 返回 `false` |

<Note title="为什么前两道抛异常、后两道返回 false">

这个区分不是随手定的：

- **`source` / `evidence` 缺失 = 调用方写错了代码。** 抛异常，因为这是 bug，越早炸越好。
- **`depth` / `confidence` 不够 = 数据不够好。** 静静地不写，因为这是正常的运行时情况，每天发生几百次。

**代码 bug 要吵，数据不足要静静地不写。**

搞混的后果是两头都坏：bug 被吞掉（因为你 catch 了所有异常），正常情况刷爆了错误日志（于是没人看错误日志了）。

</Note>

第一道闸值得多说一句：**`source` 不是为了好看。**

它是唯一能让人（和模型）判断这条对不对的东西，也是**发现污染之后能顺着删掉一整批的唯一线索**。

一条错误的事实很少是孤立的——它通常来自同一次会话里的同一次错误抽取。有 `source` 你就能 `forget(f => f.source === 'session-42')` 一次清干净；没有的话你只能一条一条看。

### 冲突：两个默认都是错的

同一个 key 已经有一个**不同的** value，怎么办？

```text
静默覆盖 → 一次幻觉就能永久改掉一条正确的事实
静默忽略 → 用户真的换了包管理器，你永远记着旧的
```

**两个默认都错**，所以必须返回冲突让调用方显式决定，而且**这个决定要被记下来**。

还有一条真实的规则：**`observed` 可以覆盖 `derived`，反过来不行。**

推导出来的结论不该推翻直接观察到的事实。这一条就算调用方显式 `resolve: 'replace'` 也不放开——因为「拿推测改事实」这件事本身就是错的，不是调用方能授权的。

<Pitfall title="value 变了的时候 hits 不能继承">

`hits`（被召回过几次）是淘汰策略的主要依据。

一条事实的值从 `pnpm` 改成 `npm` 之后，旧值被用过 50 次这件事**不代表新值可靠**。继承 `hits` 的后果是一条刚写进来的（可能是错的）事实立刻获得了「常用」的保护，永远不会被淘汰。

反过来，值**没变**的时候要保留 `hits`——那是同一条事实，它的使用历史有效。

这是那种写的时候完全想不到、上线三个月后表现为「记忆里全是错的老数据」的 bug。

</Pitfall>

### 过期：标记，而不是隐藏

```text
project.node_version = 20   （出处：session-7；原话："我们用 Node 20"；★ 可能已过期，用之前确认）
```

<Key>
**过期的事实要返回并标记 `stale`，而不是直接藏起来。**

藏起来的后果是模型不知道自己曾经知道过什么，于是重新问一遍——而重新问一遍在很多场景里比「知道但不确定」更烦人。

标记之后，模型能说「我记得你之前是 Node 20，现在还是吗」——**而这句话正是防止污染扩散的那道人工闸。**
</Key>

### 遗忘是功能，不是 bug

不淘汰的记忆会累积过期事实，而**过期事实的危害和错误事实一样**——「用户偏好用 npm」在六个月后可能已经是错的，但它看起来和真的一样。

淘汰顺序：先过期的，再从没被召回过的，最后最旧的。

<Note title="为什么使用频率比置信度更可靠">

淘汰打分里 `hits` 的权重（×10）比 `confidence`（×5）高一倍，这是故意的：

- **`confidence` 是模型自己报的。** 它是一个自评，而自评可以很自信地错。
- **`hits` 是观察到的。** 这条事实真的被用上了 5 次，这是事实而不是判断。

**能观察到的指标优先于被报告的指标。** 这条在 L12 和 L13 会变成一条通用纪律。

</Note>

### 渲染进 prompt：必须带出处

因为**模型会把你给它的一切当成事实**。你写「用户偏好 pnpm」，它就当这是铁律，哪怕这条是三个月前从一句话推导出来的。

```xml
<memory>
  <observed>  <!-- 直接观察到的，可以当事实用 -->
    user.package_manager = pnpm  （出处：session-7；原话："我们项目用 pnpm"）
  </observed>
  <derived>  <!-- 推导出来的，用之前先确认 -->
    user.style = 偏好现代工具链  （出处：session-7；置信度 0.70）
  </derived>
</memory>
```

两个区块分开（XML 标签，L03），每条带出处、原话、置信度、`stale` 标记。

还有一个小但真实的细节：**空记忆要渲染成空字符串**，不要输出一个空的 `<memory></memory>`。那会白占 token，而且让模型以为「记忆是空的」是一条信息。

### 抽取：这里是最不能宽容的地方

从对话里抽事实的 prompt，最重要的部分不是「抽什么」，是「**不抽什么**」：

```text
**不要抽这些：**
- 一次性的信息（某个文件的当前内容、某次报错的细节）
- 临时状态（"现在在调试这个函数"）
- 你的推测（"用户可能是后端工程师"）
- 从上面几条推导出来的概括（"用户偏好现代工具链"）
```

让模型自由决定该记什么，是**记忆污染的头号来源**。

<Drill title="为什么这里的解析要严格，而 L03 那个要宽容">

L03 讲结构化输出的时候，纪律是「解析要宽容」：剥掉 markdown 围栏、忍受多余的解释文字、尽量把结果捞出来。

这里的纪律正好相反：**坏行跳过并记数，绝不猜。**

区别在于**错了之后会发生什么**：

| | L03 的解析 | 记忆的解析 |
|---|---|---|
| 解析的是 | 一次性的输出 | 要长期保存的事实 |
| 猜错的代价 | 这次结果不对 | **永久有效** |
| 修复方式 | 下次重来 | 得先发现它，而它看起来和真的一样 |

**宁可少记一条，不要记错一条。**

具体到校验，有一条特别值得说：**`kind` 写错的行要跳过，不能默认成 `observed`。**

默认成 `observed` 的后果是一条推测被当成事实永久存下来——而 `observed` 是 `derived` 覆盖不了的那一类，所以它还特别难改。

另一条是**强制 key 命名空间化**（必须含点号）。不强制的话，你三个月后会有 `pm`、`packageManager`、`package_manager` 三条互相矛盾的事实，而且它们各自都「正确」。

</Drill>

最后，抽取结果**写入前要检测自相矛盾**：模型在同一次抽取里就可能给出两条冲突的事实（对话里用户改了主意）。写入前检测比写入后靠冲突解决便宜得多。

## 四、把「崩溃」的账算出来

`labs/l08/resume.ts` 跑一个具体场景：读三个客户的数据、各发一封对账单、最后提交。在第 4 步崩掉。

```text
【一】不做持久化
  崩溃前     付费调用  4 · 工具执行累计  4 · 邮件 2 封 · ¥0.0008
  从头重跑   付费调用  8 · 工具执行累计 11 · 邮件 5 封（重复 2 封：a@x.com、b@x.com）

【三】事件日志 + 幂等键
  崩溃前     付费调用  4 · 工具执行累计  4 · 邮件 2 封 · ¥0.0008
  恢复后继续 付费调用  4 · 工具执行累计  7 · 邮件 3 封 · ¥0.0008
  最终邮件：a@x.com、b@x.com、c@x.com   ← 三封，不重不漏
```

两笔代价，一笔比一笔严重：

- **钱**：崩溃前那 4 次调用全部白付。这在 40 步的任务里是 38 次白付。
- **副作用**：两个客户收到了两封对账单。**这一笔没法用钱补。**

<Key>
恢复要靠**两个机制配合**，缺一不可：

- **`resumeFrom`** 让 loop 不从第一步开始（省钱）
- **幂等键**让「万一还是重放了」的那些操作直接拿旧结果（防重）

只有第一个的话，压缩（L06）改了消息数就会算错起点。只有第二个的话，你要重放全部历史，钱照付。
</Key>

## 五、这一节的纪律

1. **存事件日志，不存 transcript。** 前者是事实，后者是历史；状态从日志算出来。
2. **`intent` 和 `outcome` 拆成两条事件。** 否则「打算做但不知道做没做」这个状态无法表达。
3. **JSONL，容忍坏行，但把坏行数出来。**
4. **幂等键按 key 排序后哈希，并拌入 `sessionId`。**
5. **每个工具声明可重放性**，`pure` / `idempotent` / `once`。
6. **`pending` 里的 `once` 工具交给人。** 代码在这里没有正确答案；真正的解法是让副作用本身幂等。
7. **快照记 `upto`、原子写、和日志分开存。** 快照坏了比没有快照更糟。
8. **长期记忆的四道闸**：有出处、观察要有原话、深度有上限、置信度有下限。
9. **冲突不静默覆盖也不静默忽略。** `observed` 可覆盖 `derived`，反之不行。
10. **过期的事实标记而不隐藏；淘汰按 `hits` 而不是 `confidence`。**
11. **记忆的解析要严格。** 宁可少记一条，不要记错一条。

<PyMirror>

Python 版有五处真实差异，都不是语法糖，而且每一处都对应一个会丢数据的场景。

**一 · `os.replace` 而不是 `os.rename`。**

两者在 POSIX 上都是原子的，但 **`os.rename` 在 Windows 上目标文件已存在时会抛 `FileExistsError`**，而 `os.replace` 两个平台都能覆盖。

快照是要被反复覆盖的，所以这里必须用 `os.replace`。这是那种「跨平台」细节里真正会咬人的一个——它在你的 mac 上永远不出问题，在用户的 Windows 上第二次写快照就炸。

**二 · 追加写要显式 `flush`，落盘还要 `fsync`。**

Python 的文件对象有自己的缓冲，`with` 块结束才写出去；而操作系统还有一层页缓冲。崩溃恢复的场景下**这两层缓冲就是一段丢失的日志**——而且丢的正好是崩溃前那几条，最关键的那几条。

```python
with self.path.open("a", encoding="utf-8") as fh:
    fh.write(json.dumps(ev, ensure_ascii=False) + "\n")
    fh.flush()          # 出 Python 的缓冲
    os.fsync(fh.fileno())  # 出操作系统的缓冲
```

`fsync` 很慢（每次都要等磁盘），所以生产环境常常只 `flush` 不 `fsync`，接受「进程崩了能救、机器断电救不了」这个折中。**这是个显式的取舍，不是可以忽略的细节。**

**三 · `json.dumps` 默认 `ensure_ascii=True`。**

中文会被转成 `\uXXXX`：文件体积涨三倍，而且 `tail` 出来的日志人看不懂。JSONL 的第三条理由（能 `tail -f`）就这么被抹掉了。

这是 L06 那个坑的第二次出现，而这次的后患更长——日志文件会留在磁盘上几个月。

**四 · `float("nan")` 和 `float("inf")` 不抛异常。**

解析置信度的时候，`float("高")` 会抛 `ValueError`，但 `float("nan")` **不会**——它是一个合法的 `float`。

所以除了 `try/except` 之外还得显式检查 `0 <= c <= 1`（`nan` 的任何比较都是 `False`，正好被挡掉）。漏了这一条，一个 `nan` 置信度会绕过闸四直接写进长期记忆。TS 那边用 `Number.isFinite` 做同一件事。

**五 · `remember` 不要原地改传进来的 `Fact`。**

用 `dataclasses.replace(incoming, ...)` 造一个新对象。调用方可能还拿着原来那个（打日志、重试、放进批次列表），原地改的后果是它手上那个对象的时间戳莫名变了。

`verify.py` 里有一条专门测这个，TS 那边因为用了对象展开（`{...input}`）天然没这个问题。

</PyMirror>
